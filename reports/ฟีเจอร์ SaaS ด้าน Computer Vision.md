# LabelDesk v2 ครอบคลุม ML loop แล้ว แต่ชั้น SaaS ยังขาด

LabelDesk v2 SDLC (`docs/sdlc/10-labeldesk-v2-sdlc.md`) ครอบคลุม ML loop หลักครบในระดับเดียวกับ Roboflow แล้ว ได้แก่ ingest, health check, version ที่ immutable, training หลาย family, evaluation บน test split เดียวกัน, inference path เดียว, CCTV stream และ active learning บางส่วน ในหลายจุดออกแบบไว้ดีกว่า Roboflow ด้วย เช่น การ replay preprocessing recipe ตอน inference, leaderboard ที่ติดป้าย "not directly comparable" และการ evaluate บน test อย่างเดียว ในขณะที่ Roboflow ปน valid เข้าไป ([Roboflow Evaluate](https://docs.roboflow.com/models/evaluate/evaluate-trained-models)) ช่องว่างใหญ่อยู่สองที่ ที่แรกคือ **ข้อเท็จจริงทางเทคนิค 4 จุดที่ต้องแก้ก่อนเดโม** วันนี้ vLLM ถอด `guided_json` ออกไปแล้วตั้งแต่ v0.12.0 ([vLLM Structured Outputs](https://docs.vllm.ai/en/latest/features/structured_outputs.html)) และ sleep mode ต้องตั้ง `VLLM_SERVER_DEV_MODE=1` ด้วย ([vLLM Sleep Mode](https://docs.vllm.ai/en/latest/features/sleep_mode.html)) กล่องจาก VLM 7B หลวมเกินกว่าจะใช้เป็นแหล่ง geometry หลัก ([RF100-VL](https://arxiv.org/pdf/2505.20612)) และ family หลักทั้งหมดในเอกสาร (YOLO, RT-DETR และ YOLO-World ที่รันผ่านแพ็กเกจ `ultralytics`) อยู่ภายใต้ AGPL-3.0 ซึ่ง Ultralytics ตีความว่าผูกถึง SaaS/API และ weights ที่เทรนได้ ([Ultralytics License](https://ultralytics.com/license)) ที่ที่สองคือชั้น SaaS ทั้งชั้น ได้แก่ scoped API key, SSO, audit log, metering, BYO storage, retention และ PDPA สำหรับภาพ CCTV ส่วนนี้ถูกจัดเป็น non-goal หรือ [later] เกือบทั้งหมด สำหรับเดโมไม่เป็นปัญหา แต่ถ้าจะเรียก LabelDesk ว่า "Roboflow-like SaaS" ส่วนนี้คือ must-have เพราะ Roboflow, Encord และ CVAT ขายสิ่งเหล่านี้เป็นแกนของแต่ละ tier ([Roboflow Pricing](https://roboflow.com/pricing); [CVAT Pricing](https://www.cvat.ai/pricing/cloud)) รายงานนี้จัด tier ฟีเจอร์ทุก subsystem เทียบกับเอกสาร design แล้วสรุปเป็นรายการแก้ไขที่ลงมือได้ทันที

**วิธีอ่านตาราง:** Tier คือ **M** = must-have, **S** = should-have, **D** = differentiator ส่วนสถานะใน design แบ่งเป็น **ครบ**, **บางส่วน** และ **ขาด** อ้างอิงหัวข้อในเอกสาร design ด้วยเครื่องหมาย § ส่วนที่เอกสาร design ไม่ได้พูดถึงและอาจมีอยู่แล้วใน v1 จะเขียนว่า "ไม่ระบุ" ทีมควรตรวจกับโค้ดใน `apps/` ก่อนสรุปว่าขาดจริง

## สี่จุดที่ต้องแก้ในเอกสารก่อนวันเดโม

**ข้อแรก: structured output ของ vLLM** §3.4 เขียนว่า prompt ขอ JSON `[{"label","bbox_2d"}]` ถ้า parse ไม่ผ่านให้ retry หนึ่งครั้ง แล้วคืนผลว่าง วิธีนี้ใช้ได้แต่เปราะ vLLM รุ่นปัจจุบันบังคับ output ได้ทั้ง choice, regex, JSON schema (รวมถึง schema จาก Pydantic), EBNF grammar และ structural_tag ผ่าน backend `xgrammar` หรือ `guidance` เรียกใช้ทาง OpenAI API ด้วย `response_format={"type":"json_schema",...}` หรือ `extra_body={"structured_outputs": {...}}` ส่วนพารามิเตอร์ `guided_json`, `guided_regex`, `guided_choice`, `guided_grammar` และ `guided_decoding_backend` **ถูกถอดออกแล้วใน v0.12.0** และ `lm-format-enforcer` ถูก deprecate ใน v0.33.0 ([vLLM Structured Outputs](https://docs.vllm.ai/en/latest/features/structured_outputs.html)) ข้อนี้เกี่ยวกับเดโมโดยตรง เพราะ §3.4 สั่งให้ pin vLLM รุ่นที่รองรับ Qwen2.5-VL ซึ่งน่าจะเป็นรุ่นหลัง v0.12 โค้ดตัวอย่างบนอินเทอร์เน็ตที่ยังส่ง `guided_json` มาจึงใช้ไม่ได้ ข้อแนะนำคือให้ grounding ใช้ `response_format` json_schema ที่กำหนด `label` เป็น `enum` ของ class list ไปเลย จะได้ไม่ต้องมีขั้น "drop labels not in the class list" และให้ VQA ของ stream rule ใช้ `structured_outputs` แบบ `choice: ["yes","no"]` แทนการ parse token แรก (§3.4, FR-7) ส่วน retry ให้คงไว้เป็นทางสำรองเท่านั้น

**ข้อสอง: sleep mode** §3.6 และ Phase 6 เขียนไว้แค่ `--enable-sleep-mode` แต่เอกสาร vLLM ระบุว่าบน server ต้องตั้ง **`VLLM_SERVER_DEV_MODE=1` ควบคู่กับ `--enable-sleep-mode`** endpoint ที่ได้คือ `POST /sleep?level=1|2`, `POST /wake_up` (ใส่ `?tags=weights|kv_cache` ได้), `GET /is_sleeping` และ `POST /release_kv_cache_memory` โดย level 1 ย้าย weights ไปไว้ใน CPU RAM และทิ้ง KV cache ส่วน level 2 ทิ้งทั้งคู่ ([vLLM Sleep Mode](https://docs.vllm.ai/en/latest/features/sleep_mode.html)) ถ้าไม่ตั้ง env นี้ smoke test ใน Phase 5 จะล้มเหลว แล้วระบบจะตกไปใช้ fallback 3B โดยไม่จำเป็น และเพราะเป็น dev-mode endpoint จึงต้อง bind vLLM ไว้ที่ `127.0.0.1` เท่านั้น ห้ามเปิดออก network ข้อนี้สำคัญเพราะ Phase 6 รัน API ที่ `--host 0.0.0.0` ใน WSL เดียวกัน ทีมควรเพิ่มบรรทัดนี้ใน Phase 6 ข้อ 2 และเพิ่ม `GET /is_sleeping` ใน GPU smoke test ส่วนเวลา wake-up ไม่มีตัวเลขในเอกสาร vLLM จึงต้องวัดเองใน Phase 5 ตามที่ §3.6 วางแผนไว้แล้ว

**ข้อสาม: กล่องจาก VLM หลวมเกินกว่าจะเป็น geometry หลัก** benchmark RF100-VL (100 datasets, 164,149 ภาพ) พบว่า MLLM ทั่วไปอย่าง Qwen2.5-VL และ Gemini 2.5 Pro ทำ object detection ได้แย่กว่า open-vocab detector เฉพาะทางอย่าง Grounding DINO และตัวเลข ODinW ที่ Qwen รายงานเองใช้ protocol แบบ referential grounding ซึ่งเทียบตรงกับ mAP ของ detector ไม่ได้ ([RF100-VL](https://arxiv.org/pdf/2505.20612)) ปัญหากล่องไม่แน่นก็ชัดเจน มีโมเดล VLM ตัวหนึ่งได้ >80% ที่ IoU 0.5 แต่เหลือ <5% ที่ IoU 0.9 ([Chain-of-Caption](https://arxiv.org/pdf/2602.08211)) และ benchmark ปัจจุบันยังวัด grounding hallucination (กล่องของวัตถุที่ไม่มีอยู่จริง) ได้ไม่ดีพอ ([CVPR25 REC](https://cse.hkust.edu.hk/~gchan/papers/CVPR25_REC.pdf)) ตาราง Risks ของ design เข้าใจเรื่องนี้แล้ว ("SAM 3.1 stays the primary auto-labeler") แต่ FR-2 และ §3.3 ยังให้ VLM grounding เป็น provider ระดับเดียวกับ SAM 3.1 และ §3.3 refine ด้วย SAM เฉพาะใน segmentation project เท่านั้น ใน detection project กล่องดิบจาก VLM จึงถูกบันทึกเป็น annotation ตรง ๆ ข้อแนะนำมีสามส่วน ส่วนแรกคือส่งกล่อง VLM เข้า SAM 3.1 เป็น box prompt ทุกครั้ง แล้วใช้ bounding box ของ mask เป็นกล่องจริง ไม่ว่า project จะเป็นชนิดไหน ส่วนที่สองคือ annotation ที่มาจาก VLM ล้วนต้องติดป้าย `source=vlm` และขึ้นไปอยู่บนสุดของ Review queue ส่วนที่สามคือเปลี่ยนบทบาทหลักของ VLM เป็น **verifier** และ **prompt parser** ตามแบบ SAM 3 ซึ่งใช้ Llama 3.2 ที่ fine-tune เป็น "AI verifier" ตรวจคุณภาพและความครบของ mask จนได้ throughput ราว 2 เท่าของการให้คนตรวจล้วน และใช้ MLLM แปลงคำขอซับซ้อนให้เป็น noun phrase สั้น ๆ ในรูปแบบ "SAM 3 Agent" ([SAM 3](https://arxiv.org/html/2511.16719v1)) นอกจากนี้ควรเพิ่ม `max_pixels` (เช่น 768×768) ใน `mm_processor_kwargs` ตาม recipe ของ vLLM เพื่อคุม token ต่อภาพบนการ์ด 12 GB ([vLLM Recipes Qwen2.5-VL-7B](https://recipes.vllm.ai/Qwen/Qwen2.5-VL-7B-Instruct)) เมื่อลด `max_pixels` ภาพจะถูก resize ต่างจากเดิม จึงต้อง rescale กลับด้วย `smart_resize` (factor 28) ซึ่ง §3.4 ทำไว้ถูกต้องแล้ว ([zenn.dev](https://zenn.dev/liushuzhi/articles/5936def67dbdf4))

**ข้อสี่: AGPL-3.0 ของ Ultralytics** §3.2 ให้ family `ultralytics` ครอบทั้ง YOLOv8/11/26, RT-DETR และ YOLO-World ทั้งหมดจึงอยู่ภายใต้ license "AGPL-3.0 and an Enterprise license" ([YOLO26 docs](https://docs.ultralytics.com/models/yolo26/)) Ultralytics ระบุว่า trained model ก็อยู่ใต้ AGPL-3.0 และข้อกำหนดนี้ครอบคลุมการให้บริการแบบ SaaS/API ด้วย เว้นแต่จะซื้อ Enterprise License ([Ultralytics License](https://ultralytics.com/license)) Roboflow ซึ่งเป็น authorized licensor ก็ยืนยันว่า custom-trained Ultralytics model ยังเป็น AGPL-3.0 ([Roboflow: Ultralytics](https://roboflow.com/ultralytics)) ตัว license มาตรา 13 กำหนดว่าถ้าแก้ไขโปรแกรมแล้วเปิดให้ผู้ใช้ใช้งานผ่าน network ต้องเปิดให้ผู้ใช้เหล่านั้นได้รับ source ของเวอร์ชันนั้น ([GNU AGPL-3.0](https://www.gnu.org/licenses/agpl-3.0.en.html)) ข้อที่ว่า weights ถูก AGPL ผูกไปด้วยนั้นเป็นการตีความของ vendor และยังไม่ได้ข้อยุติทางกฎหมาย ส่วนนี้ต้องให้ฝ่ายกฎหมายตรวจ แต่ในเชิงสถาปัตยกรรมมีทางเลือกอยู่สามทาง ทางแรกคือเปิด source ของ backend ที่ link กับ `ultralytics` ภายใต้ AGPL ทางที่สองคือซื้อ Enterprise License ทางที่สามคือย้าย Ultralytics ไปอยู่ใน pip worker ที่ผู้ใช้ติดตั้งและรันเอง แล้วแจ้งชัดว่าภาระ AGPL ตกอยู่กับผู้ใช้ ข้อแนะนำสำหรับ design คือเพิ่มฟิลด์ `license` ใน `RegistryModel` (§3.7) และแสดงเป็น badge ในหน้า Train แล้วตั้ง **family ที่เป็น Apache-2.0 เป็นค่า default** ของ SaaS ตัวเลือกได้แก่ RF-DETR ขนาด N–L (ทั้ง detection และ segmentation โดย XL/2XL อยู่ใต้ PML 1.0 ซึ่งต้องซื้อ Enterprise add-on ถ้าจะ self-host เชิงพาณิชย์) ([RF-DETR docs](https://rfdetr.roboflow.com/llms-full.txt)), D-FINE ซึ่งมีใน HF Transformers ([HF D-FINE](https://huggingface.co/docs/transformers/model_doc/d_fine)), RT-DETRv2 จาก repo ต้นฉบับหรือ HF ([Supervisely RT-DETRv2](https://ecosystem.supervisely.com/apps/rt-detrv2/supervisely_integration/train)) และ RTMDet บน MMDetection ซึ่งเป็น Apache-2.0 ([MMDetection](https://github.com/open-mmlab/mmdetection)) ส่วน Ultralytics ให้อยู่ในหมวด "bring your own license" ควรเลื่อน RF-DETR และ D-FINE จาก Phase 7 ขึ้นมาเป็น P1 แทน RTMDet ด้วย เพราะ RF-DETR-M ได้ 54.7 AP ที่ 4.4 ms บน T4 TensorRT FP16 ([RF-DETR docs](https://rfdetr.roboflow.com/llms-full.txt)) ในขณะที่ MMDetection มีความเสี่ยงเรื่องติดตั้ง mmcv ตามที่ design เขียนไว้เองใน Risks และสถานะการดูแล repo ยังไม่ได้ตรวจ license ของ YOLO-World repo ต้นฉบับ (AILab-CVC) ก็ยังไม่ได้ยืนยันว่าเป็น GPL-3.0 ตามที่จำไว้หรือไม่ ([YOLO-World GitHub](https://github.com/AILab-CVC/YOLO-World)) จึงต้องตรวจก่อนนำไปใช้เชิงพาณิชย์

## ชั้นข้อมูลแข็งแรงกว่าคู่แข่งหลายราย แต่ยังขาด connector และการตรวจ label error

ชั้นข้อมูลของ design (§3.10 P1–P3) ตรงกับ reference design ของ Roboflow แทบทุกจุด Roboflow ถือว่า version คือ snapshot ที่แช่แข็งจาก split + preprocessing (ทำทุก split) + offline augmentation (ทำเฉพาะ train) ([Roboflow: Create a dataset version](https://docs.roboflow.com/datasets/create-a-dataset-version); [Roboflow Preprocessing](https://docs.roboflow.com/datasets/dataset-versions/image-preprocessing)) ส่วน design ทำ manifest ที่มี SHA-256 และ `version_hash` ไว้แล้ว จุดอ่อนจริงมีสามเรื่อง เรื่องแรกคือการเชื่อมต่อ cloud storage ซึ่งคู่แข่งทุกรายมีเป็นพื้นฐาน เรื่องที่สองคือ health check ที่ใช้ embedding เรื่องที่สามคือการตรวจ label error ด้วยโมเดล งานวิจัยชี้ว่าเรื่องที่สามนี้มีค่าที่สุดสำหรับงาน detection การ re-annotate COCO, VOC, Cityscapes และ KITTI พบว่า **ความผิดพลาดส่วนใหญ่คือกล่องที่หายไป** และการ annotate ใหม่เพิ่มวัตถุได้ถึงราว 40% บน COCO และราว 60% บน KITTI ส่วนใหญ่เป็นวัตถุเล็ก ถูกบัง หรืออยู่หนาแน่น ([Penquitt et al. 2026](https://arxiv.org/abs/2609.21822)) ส่วน test set มาตรฐานมี label error เฉลี่ย 3.3% ซึ่งมากพอจะสลับอันดับโมเดลได้ ([Northcutt et al. 2021](https://arxiv.org/abs/2103.14749))

## Auto-label ควรใช้ SAM 3.1 สร้างกล่อง และใช้ VLM เป็นผู้ตรวจ

ช่วงปี 2025–2026 auto-label แบบ text-prompt ทั้ง dataset ด้วย SAM 3 กลายเป็นมาตรฐานแล้ว Roboflow เปิด "Auto Label with SAM 3" เมื่อพฤศจิกายน 2025 ([Roboflow changelog](https://docs.roboflow.com/changelog/explore-by-month/november-2025/auto-label-data-with-sam-3)) และ Encord ใช้ SAM 3 ทำ labeling คู่กับ SAM 2 ทำ tracking ([Encord SAM](https://docs.encord.com/platform-documentation/Annotate/automated-labeling/annotate-sam)) SAM 3 ได้ zero-shot LVIS mask AP 48.8 เทียบกับ 38.5 ของ SOTA ก่อนหน้า และมี presence head ที่แยกการตอบว่า "มี concept นี้ในภาพหรือไม่" ออกจากการหาตำแหน่ง ([SAM 3](https://arxiv.org/html/2511.16719v1)) แต่ Roboflow เตือนเองว่า SAM 3 ไม่เหมาะกับ fine-grained variant อย่างชนิดของรอยร้าวหรือ defect เฉพาะผลิตภัณฑ์ และวัตถุเล็กหรือ defect ที่พบน้อยยังต้อง annotate ด้วยมือ ([Roboflow Auto Label](https://docs.roboflow.com/datasets/ko/annotate/annotate/ai-labeling/auto-label.md)) ข้อนี้กระทบงาน IC defect ของโปรเจกต์โดยตรง ส่วนตัวเลขความเร็วที่อ้างได้ งานศึกษาแบบควบคุมพบว่า pre-label ลดเวลาได้ราว 35% ในงานวิดีโอ ([arXiv 2510.21798](https://arxiv.org/pdf/2510.21798)) และราว 78% ในงาน segmentation อุตสาหกรรมที่ sample เล็ก ([arXiv 2606.19934](https://arxiv.org/pdf/2606.19934)) ในขณะที่ตัวเลข 95% ของ Roboflow เป็นคำอ้างของ vendor เอง ([Roboflow AI labeling](https://docs.roboflow.com/datasets/annotate/annotate/ai-labeling)) เวลาเดโมจึงควรพูดถึงช่วง 30–60%

## Training และ evaluation ใกล้ระดับ Roboflow แต่ต้องใช้ evaluator ตัวเดียว

สัญญาของ adapter ใน §3.2 (`probe/load/predict/train/export`) ตรงกับรูปแบบที่ระบบ multi-framework ที่ทำงานจริงใช้กัน Supervisely TrainApp กำหนดให้มี `models.json`, `hyperparameters.yaml`, `@train.start` ที่ต้องคืน `best_checkpoint` และ hook `export_onnx`/`export_tensorrt` และรันแต่ละ trainer เป็น app แยกกัน ([Supervisely custom training](https://docs.supervisely.com/neural-networks/custom-model-integration/integrate-custom-training)) ส่วน TAO แยกแต่ละ framework ไว้ใน NGC container ของตัวเอง ([TAO overview](https://docs.nvidia.com/tao/tao-toolkit/6.25.10/text/overview.html)) design แยก env ของ MMDet ไว้แล้ว และมีตาราง normalised metric key ซึ่งดี แต่ step 8 ของ §P4 ยังคำนวณ metric จาก `val()` ของ Ultralytics และจาก `coco/bbox_mAP` ของ MMDet นิยาม mAP ของแต่ละเครื่องมือไม่เหมือนกัน Encord ระบุว่า mAP ของตัวเองอาจต่างจาก pycocotools และ TorchMetrics เพราะนับ class ที่ไม่มี GT ในภาพด้วย ([Encord evaluate detection](https://docs.encord.com/docs/active-evaluate-detection-models)) leaderboard ข้าม family จึงต้องให้ทุก adapter ส่ง raw prediction บน test split ที่แช่แข็งไว้ แล้วคำนวณด้วย pycocotools ตัวเดียว ซึ่งใช้ IoU 0.50–0.95 ทีละ 0.05, area S < 32², L > 96², maxDets 1/10/100 และ recall 101 จุด ([pycocotools cocoeval](https://raw.githubusercontent.com/cocodataset/cocoapi/master/PythonAPI/pycocotools/cocoeval.py)) ส่วนค่าที่ framework รายงานเองให้แสดงเป็น "training-time val" เท่านั้น ยังไม่พบเอกสารที่วัดว่า validator ของ Ultralytics กับ pycocotools ให้ผลต่างกันเท่าไรเมื่อใช้ prediction ชุดเดียวกัน ทีมจึงควรวัดเองใน Phase 5

## Inference, stream และ GPU scheduler ออกแบบรัดกุม แต่ยังขาดเครื่องมือฝั่ง deploy และ privacy

Inference path ใน §P5 กับ scheduler ใน §3.6 สอดคล้องกับงานวิจัย Clockwork แสดงว่าการ schedule แบบรวมศูนย์ที่รันทีละโมเดลต่อ GPU ทำให้ tail latency คาดเดาได้ ([Clockwork OSDI'20](https://www.usenix.org/conference/osdi20/presentation/gujarati)) ส่วน VRAM ledger กับ LRU evict ก็คือ Triton EXPLICIT mode ฉบับย่อ ([Triton Model Management](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/user_guide/model_management.html)) design เลือกไม่ใช้ MPS และไม่หวังพึ่ง MIG ซึ่งถูกต้อง เพราะ RTX 3080 Ti รองรับแค่ time-slicing ซึ่งไม่มีทั้ง memory isolation และ fault isolation และ MIG มีเฉพาะการ์ด datacenter ([NVIDIA GPU sharing](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/gpu-sharing.html)) ฝั่ง stream ก็เลือกตามแนวของ Roboflow InferencePipeline คือ grabber เก็บเฉพาะเฟรมล่าสุด, จำกัด `max_fps` และ reconnect อัตโนมัติ ([Roboflow InferencePipeline](https://docs.roboflow.com/reference/inference/inference-python/inference-pipeline)) แต่ประสบการณ์จาก DeepStream 7.1 บอกว่า reconnect ในตัวเพียงอย่างเดียวไม่พอ มีกรณี `nvurisrcbin` วน reconnect ไม่จบจนต้อง restart app ([NVIDIA forum DS 7.1](https://forums.developer.nvidia.com/t/deepstream-7-1-nvurisrcbin-fails-to-recover-from-rtsp-disconnection-and-enters-infinite-reconnection-loop/379718)) และกรณีกล้องตัวเดียวค้างถาวรหลัง network สะดุดครู่เดียว ([NVIDIA forum stuck](https://forums.developer.nvidia.com/t/nvurisrcbin-reconnect-logic-gets-permanently-stuck-after-a-brief-rtsp-network-blip-one-camera-freezes-for-good/376544)) StreamManager จึงควรมี watchdog แยกจาก backoff ถ้าเฟรมล่าสุดไม่เปลี่ยนเกิน N วินาที ให้ kill grabber thread หรือ capture แล้วสร้างใหม่ ไม่ต้องรอ exception

## Conclusion

เดิมคาดว่าความเสี่ยงหลักของ LabelDesk v2 คือ VRAM 12 GB แต่ผลการเทียบชี้ว่าความเสี่ยงจริงอยู่ที่สมมติฐานสองข้อในเอกสาร ข้อแรกคือการถือว่า VLM 7B เป็นแหล่งกล่องที่ใช้แทน detector ได้ ข้อสองคือการถือว่าแพ็กเกจ `ultralytics` เป็นฐานของ model hub ที่ใช้ได้เสรี ทั้งสองข้อแก้ได้ด้วยการเปลี่ยนบทบาท ไม่ต้องเพิ่มฟีเจอร์ VLM ย้ายไปเป็น verifier และ prompt parser ที่อยู่หน้า SAM 3.1 ซึ่งตรงกับ data engine ของ SAM 3 เอง ส่วน Ultralytics ย้ายไปเป็นตัวเลือก "bring your own license" ข้าง family ที่เป็น Apache-2.0 จุดแข็งของ design อยู่ที่ lineage, recipe replay และ leaderboard ที่ซื่อตรงกว่า Roboflow แต่จุดแข็งนี้จะมีความหมายก็ต่อเมื่อ evaluator เป็นตัวเดียวและ test split ปลอดจาก near-duplicate leakage ข้อ 6 และ 7 ในตารางแก้ไขจึงสำคัญกว่าที่เห็น

ข้อได้เปรียบที่คู่แข่งตามได้ยากที่สุดไม่ได้อยู่ที่จำนวน model family หากอยู่ที่ loop CCTV → event → dataset → retrain บน GPU ในประเทศ ซึ่งใส่ privacy ตาม PDPA ไว้ตั้งแต่ต้น (face blur, retention, audit การเปิดดู footage, data residency ในไทย) Roboflow ให้ residency ได้เพียง US/EU และ guideline CCTV ของ PDPC กำลังจะออก ทีมที่วาง privacy ไว้ใน design ก่อนจึงจะพร้อมเมื่อ guideline ออกจริง ส่วนคำถามที่ยังไม่มีงานวิจัยตอบ คือ active learning ยังให้ผลคุ้มหรือไม่เมื่อ label ตั้งต้นมาจาก SAM 3 และ pre-label ของ SAM 3 ช่วยประหยัดเวลาได้จริงเท่าไรในงาน bbox detection เป็นสองการทดลองที่ LabelDesk วัดได้เองจากข้อมูลของผู้ใช้ ถ้ามี metric automation efficiency ตามข้อแนะนำ และผลที่ได้จะใช้เป็นหลักฐานทางการตลาดที่ตรวจสอบได้
