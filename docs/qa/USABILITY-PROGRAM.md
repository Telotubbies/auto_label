# Usability test program (no real users)

Owner request 2026-11-17: full usability testing with no participant pool, no recruiting and no
sessions to schedule. Everything here runs on the machine, from a script, against the shipped app with
mocked workers and fakes. It measures **task success, steps, time, errors, accessibility, performance,
copy and state coverage**; it cannot measure delight, comprehension or trust, and §12 says so out loud.

The program is built once by wave Q (`docs/research/roboflow-parity/backlog/INDEX.md` §13), then run
per quorum (four implementation cards) and per wave by R13/R19/R20 in the cadence in `docs/ORG.md`.

---

## 1. Method in one page

| Layer | Question it answers | Instrument | Pass rule |
| --- | --- | --- | --- |
| Journey tests | Can the task be completed at all, in how many steps and how long? | Playwright specs in `apps/frontend/e2e/journey-*.spec.ts` | success 100 %, steps ≤ target + 2, time ≤ 2× target |
| Heuristic evaluation | Where does the interface break a known rule? | Nielsen's 10 heuristics scored 1–5 per screen, plus the `uxui-law` 30 laws as pass/fail | no heuristic < 3, mean ≥ 4 |
| Persona walkthrough | Would this persona know what to do next? | 5 persona scripts over the same journeys, 4 questions per step, SUS-8 self-score | no dead end, SUS ≥ 75 at release |
| Accessibility | Can it be used without a mouse and by a screen reader? | axe on every route, keyboard-only runs, contrast sampling, 200 % zoom | 0 critical/serious, keyboard completes every core journey |
| Performance | Is it fast enough to work at shift speed? | Playwright traces + a bundle report | every budget in §7 met |
| Copy review | Does it say the right thing, in English and Thai? | a copy lint plus a written pass | no machine Thai; every string flagged for a native reviewer |
| State coverage | Does every screen explain empty, loading, error and no permission? | forced states through the stub layer | every screen has all six states |

**Evidence rule.** A finding without a spec name, a screenshot, an axe output or a measured number is
not a finding. "Feels slow" is not a finding; "save p95 1,240 ms against a 500 ms budget, trace
`trace.zip#L120`" is.

## 2. Personas

Five personas, taken from `design/labeldesk-v3/REDESIGN.md` §2 and the owner's request. A persona is a
walkthrough script and a scoring sheet, not a demographic.

| P | Persona | Context | First 3 seconds | Success for this persona |
| --- | --- | --- | --- | --- |
| P1 | **New labeler** (Thai-first shift worker) | 6–8 h at a desk, keyboard-heavy, paid per approved image | the next image, how many are left, the class hotkeys | labels one image in ≤ 20 s, never loses work, never leaves the keyboard |
| P2 | **ML engineer** | trains, compares, exports, watches metrics | which version is clean, what to train, whether the last run won | freezes a version, starts a run, reads whether it beat the last one |
| P3 | **Factory QA lead / reviewer** | owns label quality, approves batches, checks balance | what is waiting, what the model disagrees with, one action to accept | reviews a batch without approving blind; disagreement is visible before the decision |
| P4 | **Workspace admin** | members, keys, usage, audit, compliance | usage and governance without entering a project | invites a member, issues and revokes a key, reads usage and audit |
| P5 | **AI agent through MCP** (non-human) | a host model calls tools over one key | the workspace, the scopes, the tool list | reads a project, proposes labels, runs a dry-run spend prompt, never exceeds its key |

Each persona has a walkthrough script listing the journeys it owns, the decision it makes at each step,
and the sentence it must be able to answer without documentation.

## 3. Journey tests

One Playwright spec per core journey. A **step** is a deliberate user action (click, key press, field
submit); page loads generated by that action do not count. **Time** runs from the first action to the
success assertion, excluding fixture upload and the fixed fake-job wait, which is a constant the harness
subtracts. Every spec asserts the target and writes a `journey-result` annotation.

| # | Journey | Spec (exclusive to its card) | Target steps | Target time | Tag |
| --- | --- | --- | --- | --- | --- |
| J1 | Sign up, verify, sign in, wrong-password recovery | `journey-auth.spec.ts` | 8 | 120 s | smoke |
| J2 | Create a project and land on upload | `journey-project.spec.ts` | 5 | 45 s | smoke |
| J3 | Upload: files, a URL import, and video frames | `journey-upload.spec.ts` | 7 | 90 s | smoke (video part `@nightly`) |
| J4 | Annotate: box, polygon, SAM assist, save, reload | `journey-annotate.spec.ts` | 9 | 120 s | `@nightly` |
| J5 | Review and approve a batch, with the confirm sheet | `journey-review.spec.ts` | 6 | 60 s | smoke |
| J6 | Create a version and export COCO + YOLO | `journey-versions.spec.ts` | 8 | 120 s | `@nightly` |
| J7 | Train a model and compare it with the previous run | `journey-train.spec.ts` | 8 | 120 s | `@nightly` |
| J8 | Deploy and test: sample image, boxes, threshold, snippet | `journey-deploy.spec.ts` | 6 | 60 s | smoke |
| J9 | A stream: create, start, event, send to dataset | `journey-streams.spec.ts` | 8 | 120 s | `@nightly` |
| J10 | Settings: invite, key with one-time reveal, usage | `journey-settings.spec.ts` | 7 | 90 s | smoke |
| J11 | MCP: list tools, search, read labels, write with confirm, dry run | `apps/backend/tests/test_mcp_journey.py` | 5 calls | 60 s | `@nightly` |
| J12 | Inference hub: calculator, engine plan, model, segmentation → auto-label | `journey-inference.spec.ts` | 8 | 120 s | `@nightly` |
| J13 | Admin: audit filters, platform console, flags, policy | `journey-admin.spec.ts` | 7 | 90 s | `@nightly` |

Rules:

- **The smoke set stays under 10 minutes**: `npm run e2e` = `playwright test --grep-invert @nightly`;
  `npm run e2e:nightly` runs everything. If the smoke set grows past 9 minutes, the newest long journey
  moves to `@nightly`; the set never shrinks.
- **Fakes, not hardware.** The backend runs the test entrypoint in `apps/backend/e2e/` with deterministic
  adapters and instant job handlers; MJPEG is a fixture frame; no GPU, vLLM, SAM, network import or
  Ollama is touched.
- **One journey per spec file**, one owner card per file. Shared setup comes only from
  `apps/frontend/e2e/fixtures/harness.ts` (auth, seeded ids, flag switch, step/time recorder, axe,
  stub routes).
- **A journey never asserts on another journey's state**; each starts from the seeded demo workspace or
  creates its own project, and cleans up what it creates.
- **The journey is the usability unit**: no assertion may hide a failure behind a shorter path (for
  example, calling the API where the user would click).

## 4. Heuristic evaluation

Per screen, R13 and R14 score Nielsen's ten heuristics 1–5 with one evidence line each (screenshot or
spec step). 1 = blocks the task, 3 = works but costs a detour, 5 = no friction.

| # | Heuristic | What a 3 looks like here |
| --- | --- | --- |
| H1 | Visibility of system status | a job shows progress but not what is being processed |
| H2 | Match between system and the real world | "instances" where the labeler says "objects" |
| H3 | User control and freedom | undo exists but not next to the action |
| H4 | Consistency and standards | the same status under two words on two screens |
| H5 | Error prevention | a destructive bulk action without a count |
| H6 | Recognition rather than recall | a hotkey only in a modal, never on the control |
| H7 | Flexibility and efficiency | no keyboard path for a repeated action |
| H8 | Aesthetic and minimalist design | two filled primaries in one view |
| H9 | Error recovery | "something went wrong" with no retry or reference |
| H10 | Help and documentation | an empty state with no "what next" |

**The laws layer.** The `uxui-law` skill's 30 laws are checked pass/fail where they apply, not scored:
Fitts and target size, Hick on control counts, Miller on grouped choices, Jakob on familiar patterns,
Doherty on feedback under 400 ms, Goal-Gradient on progress, Zeigarnik on unfinished work, Von Restorff
on the one primary, Tesler on what the system absorbs, Postel on input tolerance, Occam on one path,
Prägnanz on visual grouping, Aesthetic-Usability on the first screen. A violation is a finding with the
law named.

**Scoring.** Per screen, the minimum heuristic decides its grade: A ≥ 4 mean and no score < 3; B = mean
≥ 3.5; C = any score < 3. A C screen cannot ship in a wave without a fix card or a written owner
exception. The scoreboard lives in the wave's findings file.

## 5. Persona cognitive walkthroughs

Each persona walks its journeys as a scripted sequence. At every step the evaluator answers four
questions and records a yes/no plus one sentence:

1. Will the persona try to achieve the right outcome here?
2. Will they notice the control that does it?
3. Will they connect the control's label to the outcome they want?
4. After acting, will they see progress and know it worked?

A "no" on 2, 3 or 4 is a finding. A "no" on 4 across a journey is S2 even when the task completes.

**SUS-style self-score.** After each walkthrough, eight statements are scored 1–5 by the evaluator
acting as the persona (not by the builder), alternating positive and negative. The eight-item score is
`(((sum of odd items − 4) + (20 − sum of even items)) / 32) × 100`, so 0–100 with the same shape as the
standard ten-item instrument:

1. I would use this screen regularly.
2. I found it unnecessarily complex.
3. I thought it was easy to use.
4. I would need technical support to use it.
5. I found the parts worked well together.
6. I thought there was too much inconsistency.
7. I would imagine most people learn it quickly.
8. I found it awkward to use.

Target ≥ 75 at a wave release, ≥ 68 acceptable for an internal wave, < 68 is an S2 finding. The score is
recorded per persona per wave; a drop of 10 points between waves is a regression finding even if the
absolute number is acceptable.

## 6. Accessibility protocol

R19 runs this on every wave, on the wave's screens; the per-area audit cards run it first.

- **axe-core on every route**, light and dark: 0 critical and 0 serious. `moderate` and `minor` are
  recorded; `color-contrast` with result `incomplete` counts as a failure until pixel-sampled.
- **Keyboard only**: Tab/Shift-Tab, Enter/Space, Escape, arrow keys. Every browser journey (J1–J10 and
  J13) must complete with no pointer. Focus is visible, never hidden behind the top bar, the job tray or
  a sticky action; focus order follows reading order; no trap outside a modal.
- **Contrast**: text ≥ 4.5:1, large text and controls/focus ≥ 3:1, measured on the painted colours
  (not the token table). Glass surfaces are measured on the tint, never on the blur.
- **Breakpoints**: 375, 768 and 1440, in light and dark. At 375: no horizontal document scroll; the
  primary action reachable; no clipped tab or chip; editor is explicitly desktop-only with a readable
  preview.
- **Preferences**: `prefers-reduced-motion`, `prefers-reduced-transparency`, `prefers-contrast: more`
  and forced colours each checked once per area; motion is opacity/transform only.
- **Zoom**: 200 % at 1440, manual, on the editor, dataset grid, train and settings. No lost control, no
  overlap, no horizontal scroll on a work surface.
- **Charts** have a table view and a text alternative; colour is never the only signal.
- **Limits**: no screen reader is automated here. R19 keeps a manual NVDA/VoiceOver checklist per wave
  and marks it "manual, not measured" in the report; the program never claims otherwise.

## 7. Performance budgets

Measured on the reference machine, against `npm run build` + `vite preview`, warm cache unless stated.
T-1221 pins the baseline; a budget may be tightened freely and raised only by owner ruling.

| Metric | Budget | Instrument |
| --- | --- | --- |
| Initial JS, gzip | ≤ 350 kB | build report (`scripts/perf-budget.mjs`) |
| Any lazy route chunk, gzip | ≤ 120 kB | build report |
| CSS, gzip | ≤ 60 kB | build report |
| LCP, p75, 1440 | ≤ 2.5 s | Playwright trace, throttled CPU ×4 |
| INP | ≤ 200 ms | Playwright interaction timing |
| CLS | ≤ 0.1 | Playwright layout-shift observer |
| Route transition, cached data | ≤ 300 ms | navigation timing in the spec |
| Route transition, cold chunk | ≤ 1.0 s | navigation timing, first visit per route |
| Click → visible feedback | ≤ 100 ms | recorder in `harness.ts` |
| Annotation save, p95 | ≤ 500 ms | API timing from the editor |
| Canvas pan/zoom frame | ≤ 32 ms | 60-frame trace |
| Dataset grid, 200 tiles, first paint | ≤ 1.0 s | spec timing |
| API read, p95, local | ≤ 300 ms | backend access log in the e2e run |

A miss over 20 % is S2; a miss under 20 % is S3 with the number recorded. A regression between two waves
is a finding even inside budget: the wave note names the commit and the cause or says "unattributed".

## 8. Copy review (English and Thai)

R15 runs it on every screen in the wave, against the message catalogue (`lib/i18n.ts` once T-600 lands,
JSX literals before that).

- **One word per concept**: status, stage, action and object names come from one list; the UI-AUDIT's
  "Dataset / Approved / Ready" for one status is the reference failure.
- **Tool voice**: no marketing words in the product, no exclamation, no filler, no repeated sentence
  under every empty state. Every error names what failed, what survived, the retry and a reference id.
- **Thai is real Thai**: no transliteration, no machine translation shipped, no `slice()` truncation,
  line-height 1.6, Anuphan/Noto Sans Thai, numbers and dates through the shared formatters.
- **Every Thai string is flagged for a native reviewer.** R15 writes the list to the wave's findings;
  the reviewer's sign-off is an owner decision, not an agent one. The UI-AUDIT's `ยัวจระเข้` is the
  standard for "not acceptable": fluent-looking nonsense is worse than English.
- English and Thai are checked for the same meaning, length and tone; a layout that only works in one
  language is an S2.

## 9. Error, empty and loading states

Every screen must show all six states, each with a way out:

| State | Rule | How the test forces it |
| --- | --- | --- |
| Empty (new) | what this is for, one primary, one shortcut | a fresh workspace / project |
| Empty (no match) | "no results for these filters" + clear filters, distinct from empty | a filter that matches nothing |
| Loading | skeleton matching final geometry, no page spinner | 800 ms delayed route in the stub layer |
| Error | what failed, what survived, retry, reference id | 500/503 response, then a retry that succeeds |
| Permission | dimmed control + reason + request access, never a silent redirect | a labeler session on an admin route |
| Offline / API down | top-bar banner, actions disabled with a reason | aborted API route |

The per-area audit cards own the screen list and the first pass; R13 re-runs it per wave. A missing state
is S2 when the screen is on a core journey, S3 otherwise.

## 10. Severity, findings and fix cards

| Sev | Meaning | Examples | Response |
| --- | --- | --- | --- |
| **S1** | The task cannot be completed, data is lost or exposed, or a legal/public claim is false | save loses a box; workspace A reads B; every upload fails; a WCAG A block on a core journey | blocks the next merge batch and the wave release; owner informed the same day |
| **S2** | The task completes only with a workaround, an AA failure, or a target missed by more than 2× | approve requires a hidden menu; Thai breaks the layout; save 1.2 s | fix card before the next wave; the area's next implementation card waits |
| **S3** | Friction, or a target missed by less than 2× | three clicks where one would do; a skeleton at the wrong size | fixed in the next wave or accepted in writing |
| **S4** | Cosmetic, copy or consistency | a stray label, a spacing drift | batched into the next copy/design pass |

**Finding format.** Every finding is a row in the wave's `docs/qa/findings/wave-q<N>.md`:

```text
Q2-A3-07 · S2 · P1 · journey-annotate · /:ws/p/:project/annotate/:id · build <sha>
Expected: one click selects the polygon and shows its vertices.
Actual: the first click only focuses the canvas; the second selects.
Rule: H7 flexibility, Fitts (handle 8 px)
Measure: 2 clicks vs 1; task 96 s vs 90 s target
Evidence: test-results/annotate/step-4.png, trace.zip
Fix card: <id>
```

**Finding → fix card.** The triage card (T-1223…T-1226) dedupes by root cause, assigns severity, and
writes one ready-to-dispatch card per S1/S2 in the same findings file, in the `_BRIEF.md` template, sized
≤ 3 agent-hours, naming exclusive files. R12 numbers it and R0 queues it ahead of new implementation
cards. S3 findings for one area become one batched card per wave; S4 goes to the copy/design pass. Nothing
is "fixed in the test": the spec's assertion stays and the product changes.

**Release rule.** A wave releases when: every journey passes, no S1 or S2 is open, axe has no
critical/serious, every budget is met or attributed, and the Thai list is with the native reviewer.

## 11. Metrics and reporting

| Metric | Definition | Target |
| --- | --- | --- |
| Task success | journey completed unaided / attempts | 100 % smoke, ≥ 90 % first attempt nightly |
| Steps | deliberate actions from start to success | ≤ target + 2 |
| Time on task | first action → success, fake waits subtracted | ≤ 2× target; median ≤ target |
| Error count | validation retries, dead ends, wrong turns per journey | 0 blocking; ≤ 1 recoverable |
| SUS-style score | 8 statements → 0–100, per persona per wave | ≥ 75 release, ≥ 68 acceptable |
| Heuristic grade | per screen, min and mean of the 10 | no heuristic < 3; mean ≥ 4 |
| Accessibility | axe critical/serious, keyboard completion | 0; 100 % of core journeys |
| Performance | every budget in §7 | met, or attributed |
| Copy | new strings reviewed, Thai flagged | 100 %; 0 machine Thai |

Reports are per wave, not per run: the wave note (`docs/qa/releases/q<N>.md`) carries the metric table,
the S1/S2 list, the accepted S3s and one paragraph on what changed since the last wave. The per-area
audits (`docs/qa/audits/area-<n>.md`) hold the screen-level detail. No dashboard is built; the files are
the dashboard.

---

## 12. Honest limits

- No real users, so no measure of comprehension, trust, delight or willingness to pay. The persona
  walkthrough is a proxy and is labelled as one.
- One evaluator plays all five personas; a shared blind spot is possible. R6/R7 and the owner read the
  findings, not only the score.
- Fake workers mean job timing, GPU behaviour and long-run stability are out of scope. Real GPU claims
  stay with the owner's hardware runs.
- Screen-reader and 200 % zoom are manual and are never reported as automated passes.
- Thai copy is flagged, never signed off, by an agent.
- Mobile is checked at 375 for layout and reachability; the editor is desktop-only by design.
