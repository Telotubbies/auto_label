## User story
As a video annotator, I want to see exactly how many frames a sampling choice will produce, with a
trimmed range and hand-picked frames included, so that a 30-minute clip does not silently create 2,000
images.

## UX flow (LabelDesk words)
1. **Video** — after choosing a mode, the form shows the plan line "Every 2 s from 00:30 to 04:00 ·
   106 frames" while the user drags the interval. [loading: the line reads "Calculating…" and the
   primary waits] [error: trim end before start → "Trim end must come after the start", primary
   disabled]
2. **Video** — a picked moment (00:37.5) is appended to the plan: "106 frames · 3 hand-picked"
   (duplicates removed). [error: a pick outside the trim range is refused with the timestamp named]
3. **Video** — pressing Upload stores the plan with the video, the job runs and the tray row reads
   "Extracting frames · 34%". [error: the window is empty → "That range has no frames at this interval"]
   [empty: the container reports 0 frames → "This video has no decodable frames", nothing queued]

## Backend changes
- Models/schema: none — `Video.params` and `Job.params` already carry JSON.
- Routers: `apps/backend/app/routers/videos.py`
  - `POST P/videos/{vid}/plan` body `{mode, target_fps, every_s, scene_threshold, start_s, end_s,
    picks_s: list[float]}` → `200 {frames, sample: list[int] (first 24), startFrame, endFrame, capped}`;
    `400` for an invalid mode/interval/range; `409` when the video is not `ready`. Picks arrive in
    seconds because the browser cannot read the source frame rate; the route converts with the probed
    `Video.fps`.
  - `POST P/videos` gains `start_s: float = 0`, `end_s: float = 0` (0 = end of file),
    `picks_s: str = ""` (comma-separated seconds); validation mirrors the plan route; values stored
    in `Video.params` and the job params.
- Services/jobs:
  - `apps/backend/app/services/video.py` — `plan_frames(...)` gains `start_frame=0, end_frame=None,
    picks=()`: sampled indices inside the window, explicit picks unioned in (sorted, de-duplicated),
    thinned to `max_frames` (2,000, unchanged), first kept frame always inside the window.
  - `apps/backend/app/handlers/streams.py` — `run_extract_frames` reads the window and picks, stops
    reading at `end_frame` (no full decode of the tail), and only stores planned indices; scene mode
    ignores `picks` (documented 400 at the route).
- Permissions + workspace isolation: `c.need("reviewer")` unchanged for upload and the plan route;
  `_get_video` already scopes by project + workspace, so a foreign video is 404.
- Secrets/safefetch: none.
- OpenAPI: yes — one new route and three form fields.

## Acceptance criteria
- [ ] The plan route returns the exact frame count for a mode, window and picks, and writes nothing.
- [ ] Trim and picks are stored and honoured by the job; frames outside the window are never decoded
      into storage.
- [ ] Invalid mode, interval, range or pick returns 400 with the offending value named; an unready video
      is 409.
- [ ] The existing 2,000-frame cap and the plan/storage quota checks still hold (unchanged).
- [ ] Empty, loading and error states above render (plan line, range error, empty-window error).
- [ ] Flag off ⇒ the whole video surface is 404, as today.
- [ ] Workspace A cannot see or change workspace B's data (404 for a foreign video or project).

## Notes for the implementer
`plan_frames` stays pure and allocation-light: the route only needs the count and the first 24 indices,
so do not return all 2,000 indices over the wire. Scene mode plus picks is refused rather than silently
ignoring the picks.
