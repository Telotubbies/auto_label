## User story
As a labeler, I want the editor to open an image I cannot change and tell me why, so that a forbidden drag does not end as a mystery toast.

## UX flow (LabelDesk words)
1. **Opening an image the caller may not edit** — the editor renders normally (image, shapes, zoom) with a persistent bar under the header: **View only** and the reason — "Assigned to Somchai", "Your project role is view-only", "Approved and in the dataset", or "This consensus job is merged". Every drawing tool, the class chip row, the assist entries and Delete are dimmed with a lock and a tooltip carrying the same reason.
2. **Attempting an edit anyway** — a dimmed control explains itself instead of doing nothing silently; the server still refuses the write (403) and the editor re-reads the image rather than pretending it saved.
3. **Approved images** — opening an approved image is view-only by default with an **Ask a reviewer to reopen** line; a reviewer gets a **Reopen for editing** button that returns it to `annotating` (audited) and unlocks the canvas in place. [error: reopening an image in a merged consensus job → read-only stays, with its own reason]
4. **Empty project** — the Annotate board's empty state reads "No images yet" with "Upload images to start labelling" and an **Upload** button; the review lane's empty state says "Nothing waiting for review" and the approved lane's "Nothing approved yet". [empty: a project with a batch but no images in a lane keeps today's per-lane empty rows]
5. **No image to open** — a deep link to an image that no longer exists returns the existing "Can't open this image" screen with a Back link to the board, and the board never links to a deleted image.
6. **Server truth** — `canEdit` comes from the server; the client never derives it from a role it happens to know, because the effective project role is decided server-side.

## Backend changes
- Models/schema: none.
- Routers: `GET /api/images/{image_id}` payload gains `canEdit: bool` and `readOnlyReason: str | null`, computed in `_image_with_annotations` from the same rules `save_annotations` already enforces (`labeling_ops.assigned`), plus: role `viewer` → "view-only"; `status == "done"` → "approved"; a merged consensus assignment → "merged"; `PUT /annotations` keeps returning 403 for the same cases (no relaxation).
- Routers (reopen): `POST /api/images/{image_id}/reopen` → `project.review`, sets `status = "annotating"`, clears `review`, audits `image.reopen`, refuses a merged consensus job (409) and an image still in `unassigned` (400).
- Services/jobs: none beyond the one helper `read_only_reason(c, img)` in `services/labeling_ops.py` so the payload and the write path cannot disagree.
- Permissions + workspace isolation: the reason helper reads the caller's effective project role; cross-workspace image ids stay 404 through `image_ctx`.
- Secrets/safefetch: none.
- OpenAPI: yes — two fields and one route.

## Acceptance criteria
- [ ] An image the caller cannot edit opens view-only with a reason bar and every mutating control dimmed with the same reason.
- [ ] The server refuses the same writes with 403; the client never reports a save it did not make.
- [ ] A reviewer can reopen an approved image, which returns it to annotating and unlocks it without a reload.
- [ ] The three board lanes have distinct empty states with the upload action where it applies.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] No flag: the state is server truth; there is no flag-off variant to hide.
- [ ] Keyboard-only path: open a read-only image → Tab through the rail → each control announces its reason.

## Notes for the implementer
`read_only_reason` must be the single source for both the payload and the write guard — two copies of these rules will disagree within a release. Reopening is audited because it changes what a reviewer already accepted.
