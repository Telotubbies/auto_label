## User story
As a QA lead at a customer who has to show an auditor who approved the model inspecting their parts, I want a promotion to be a request a second person signs off, so that the live alias is an auditable decision rather than one admin's dropdown change.

## UX flow (LabelDesk words)
1. **Model page** (`/:ws/:project/models?model=<id>`) — `Request promotion` opens a dialog: target stage (`staging` / `production`), a written reason, and the evaluation that justifies it, shown read-only from the model's stored metrics. [error: the model is not ready, or was deleted between opening the dialog and sending ⇒ "That model is no longer available to promote." and the dialog closes with the queue refreshed]
2. **Deployments** (`/:ws/deployments`) — the alias card shows `Waiting for approval` beside the current holder when a request is open, with both models' numbers in the request row. [empty: "No promotion requests waiting."] [loading: the request list keeps the alias card visible and shows two skeleton rows]
3. **Approver** — opens the request, compares it against what is live, then `Approve` or `Reject` with a note. The response moves the alias and appends the event in one transaction; a rejected request keeps its note and disappears from the queue. [error: the requester tries to approve their own request ⇒ 409 "You cannot approve your own request."]
4. **History** — the alias card's event list names the requester, the approver, both models and the request text.
5. **Rollback** — unchanged in shape: still a new event pointing at the previous model.

## Backend changes
- Models/schema: `PromotionRequest` (`id, workspace_id, project_id, alias, model_id, from_model_id, target_stage, reason, status, requested_by, decided_by, decision_note, created, decided`) in a new `app/models/governance.py`; `DeploymentEvent` gains `note` (VARCHAR(1024) DEFAULT '') and `request_id` (VARCHAR(32) DEFAULT '') via an `ADD COLUMN` block in `app/schema/training.py` registered in `schema.apply`; the new table needs no column upgrade (created by `create_all`).
- Routers: new `app/routers/promotions.py` — `POST …/promotions` `{alias, model_id, reason}` (201), `GET …/promotions?status=open`, `POST …/promotions/{id}/approve` `{note}` and `POST …/promotions/{id}/reject` `{note}`; 409 for a duplicate open request on the same alias, 422 for an empty reason.
- Services/jobs: `app/services/promotions.py` (new) — `request(db, project, body, user_id)`, `decide(db, request_id, approve, note, user_id)` calling the existing `deployments.switch()` inside the same transaction so the alias and the event commit once; the event carries `note` and `request_id`.
- Permissions + workspace isolation: `c.need("admin")` to request and to decide; the requester may not equal the approver; a request id from another workspace or project answers 404.
- Secrets/safefetch: none.
- OpenAPI: yes — regenerate both generated files.

## Acceptance criteria
- [ ] A promotion is a stored request with target stage, reason, requester and the model it names.
- [ ] Only a second admin can approve or reject; the alias moves only on approval.
- [ ] The approval writes one append-only event carrying the request text, the requester and the approver.
- [ ] A request naming a deleted model is refused with a reason, never a 500.
- [ ] Empty, loading and error states above all render as API states: an alias with no request returns an empty list, a duplicate is a stated conflict.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no promotion routes, and the existing alias switch/rollback behave exactly as today.

## Notes for the implementer
One open request per alias per project; approving supersedes nothing — a newer request cannot exist while one is open, so the queue can never show two answers for the same stage. Store the alias as the short name (`production`, `staging`) exactly as `DeploymentAlias.alias` does, and never accept an alias outside `services/deployments.ALIASES`.
