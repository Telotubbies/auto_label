## User story
As an admin, I want to record who owns a key and what it serves, so that rotation is not archaeology six months
later.

## UX flow (LabelDesk words)
1. **Create / edit key → `Notes`** — `Add field` adds a key/value row, up to 20 pairs; keys ≤ 100 chars, values
   ≤ 500; a pair can be removed. [empty: the section is collapsed to one `Add field` button]
2. **Owners** — a member picker (`Owners can roll this key`); leaving it empty shows
   `No owners — everyone with key access will be notified about this key.`
3. **Table** — once any key in the workspace has metadata, a `Notes` column appears showing `3 fields` with a
   hover list; the column is absent while every key has none.
4. `[error]` a duplicate key name in metadata → `That field already exists.`; the row stays editable.

## Backend changes
- Models/schema: none — `metadata JSON` and `owner_ids JSON` ship in T-388.
- Routers: `POST /api/ws/{ws}/keys` and `PATCH /api/ws/{ws}/keys/{kid}` accept `metadata` (object) and `owner_ids`
  (list of member user ids); `400` for > 20 pairs, a key > 100 or a value > 500 chars, and for an owner id that is
  not a member of this workspace.
- Services/jobs: `services/keys.py` — `validate_metadata(pairs) -> dict` and `owner_rows(db, key) -> list[dict]`.
- Permissions + workspace isolation: `workspace.keys`; owner ids resolve inside `c.ws.id` only, so a foreign user
  id is a 400 and never a cross-tenant name leak.
- Secrets/safefetch: metadata values may hold a cost centre, never a secret — the field hint says so and the API
  rejects a value that looks like a key (`lkd_` prefix) with `Do not store key material in notes.`
- OpenAPI: yes.

## Frontend changes
- Route: `/:ws/settings/api` (existing).
- Components: `features/settings/keys/KeyNotes.tsx` (new) — pair editor + owners picker, used inside the create
  dialog and the edit dialog; `features/settings/keys/notesSummary.ts` (new) — `summary(metadata)` pure helper for
  the column cell.
- API client: `keysApi.create/patch` accept the two fields.
- Feature flag: `task_key_metadata`; off ⇒ no `Notes` section, no `Notes` column, the two fields are ignored.

## Acceptance criteria
- [ ] Up to 20 note pairs and a set of owners can be stored on a key and edited later.
- [ ] The `Notes` column appears only once a key in the workspace has notes.
- [ ] Key material is refused in notes, and an owner outside the workspace is refused without leaking a name.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no notes UI and both fields are ignored by the API.
