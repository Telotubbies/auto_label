## User story
As a workspace admin, I want the sync button to explain its cooldown, a hard hourly cap, and a daily
schedule I can switch on, so that a bucket poll cannot become a surprise bill or a stuck button.

## UX flow (LabelDesk words)
1. **Settings · Datasources** — the row's play button is disabled with a countdown tooltip
   "Available again in 12:41" after a run that changed something. [error: clicking during a run →
   "A sync is already running", nothing queued]
2. **Settings · Datasources** — a run that found nothing leaves the button enabled: "Last run found no new
   objects — you can run again now."
3. **Settings · Datasources** — after 10 manual runs in an hour the button reads "Hourly limit reached —
   next manual run at 14:05"; scheduled runs are unaffected.
4. **Settings · Datasources · History** — a table: started, trigger (manual/scheduled), listed, added,
   duplicates, failed, orphans removed, duration, error. [empty: "No runs yet — press play to test the
   configuration."] [loading: 3 skeleton rows]
5. **Settings · Datasources** — "Run automatically every day" switch (off by default) shows the next run
   time when on.

## Backend changes
- Models/schema: `SyncRun` in `models/storage.py` (Shared): `id, connector_id FK, workspace_id, trigger
  String(16) manual|scheduled, status queued|running|done|failed, listed, uploaded, duplicates, failed,
  skipped_filter, orphans_removed, error Text, started, finished`; created by `Base.metadata.create_all`.
- Routers: `apps/backend/app/routers/connectors.py`
  - `POST /projects/{project}/connectors/{cid}/sync` gains the guard chain and returns `409` with
    `{reason: "running"|"cooldown"|"hourly-cap", retryAt, message}`.
  - `GET /connectors/{cid}/runs?limit=20` → newest first.
  - `PATCH /connectors/{cid}` accepts `config.schedule = "off"|"daily"`.
- Services/jobs: `apps/backend/app/services/mirror_runs.py` (new) —
  `guard(db, conn) -> None | {reason, retryAt}` (running; 15 min cooldown unless the last run had zero
  enqueued or all failed or the config `updated` moved; 10 runs/rolling hour, `trigger="scheduled"` is
  exempt), `open_run(db, conn, trigger) -> SyncRun`, `close_run(db, run, result)`,
  `due(db) -> list[Connector]` (schedule daily and `last_run_at < now-24h`),
  `enqueue_due(db)` creating one job per due connector. `services.connectors.sync_job` writes the run row
  (open on start, close in `finally`).
  `apps/backend/app/worker.py` — `_schedule_ops` calls `mirror_runs.enqueue_due(db)` next to the drift
  scheduler (one line).
- Permissions + workspace isolation: `workspace.connectors`; runs are listed by connector id scoped to
  `c.ws.id` (404 otherwise).
- Secrets/safefetch: none new.
- OpenAPI: yes — one route + `409` shape + schedule field.

## Acceptance criteria
- [ ] Cooldown, zero-result skip, config-change skip, failure skip and the 10-per-hour cap all match the
      table above, and each refusal carries a retry time.
- [ ] A scheduled run only enqueues once per 24 h per connector and is exempt from cooldown and cap.
- [ ] History shows every run with its trigger and counts; empty and loading states render.
- [ ] No run can start twice concurrently (a second request is 409, not a second job).
- [ ] Empty/loading/error states above render.
- [ ] Flag off ⇒ no guard, no history, no schedule; the play button works as today.
- [ ] Workspace A cannot see or change workspace B's data (404 for a foreign connector or run list).

## Notes for the implementer
Store the run row, not a cache: the guard reads the last run from the table, so a process restart cannot
reset the cooldown. `trigger="scheduled"` bypasses cooldown and cap but still refuses to run twice.
