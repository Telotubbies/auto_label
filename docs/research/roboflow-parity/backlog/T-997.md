## User story
As a workspace owner, I want every admitted agent action to leave one audit row naming the tool, and I want
the API's existing limits to be the agent's limits too, so that "what did the agent do last night" is a
filter on the existing Audit screen, not a new investigation.

## UX flow (LabelDesk words)
1. **Settings → Audit log** — an agent's `run_auto_label` appears as `mcp.tool` with its target path and the
   tool name in the row's detail; the existing filters (action, user, window) already find it.
2. **A key at the ceiling** — the 601st request in a minute answers 429 with `Retry-After`, and the agent
   surfaces "too many attempts — try again shortly". [error: the tool result is `isError`, not a crash].
3. **Credits gone** — 402 with the plan's own sentence, unchanged. [error: readable, retryable never].
4. **Nothing hidden** — the tool result, the log line and the audit detail carry no key, no prefix, no
   `Authorization` header.

## Backend changes
- Models/schema: none — `Audit` already has `action`, `target` and a JSON `meta`.
- Routers: none.
- Services/jobs:
  - `app/apikeys.py` — `resolve_key` (lines 79-91) gains, after the key is resolved and only when
    `request.headers.get("x-mcp-tool")` is present, one row:
    `audit(db, k.workspace_id, None, "mcp.tool", request.url.path, tool=<header value [:64]>,
    method=request.method)` — written before the existing `db.commit()`, so it shares the commit that
    already records `last_used`. The existing `apikey.use` throttle stays as it is; this row is per call on
    purpose, because that is what the owner asked for, and an MCP call is a conversation turn, not a poll.
  - `packages/sdk/labeldesk/client.py` — `call(..., headers=None)` merges caller headers into the request
    (already added by T-992; this card only proves the stamp reaches the API).
- Permissions + workspace isolation: the audit row is written with the key's `workspace_id`; a key can only
  ever produce rows in its own workspace.
- Secrets/safefetch: the header value is truncated to 64 chars and stored as metadata; the key, its prefix
  and the `Authorization` header are never part of a row. A caller could forge `x-mcp-tool`; the blast radius
  is a mislabelled row in that key's own workspace, which R7 accepts and the card documents.
- OpenAPI: no.

## Acceptance criteria
- [ ] One `mcp.tool` row per admitted MCP call, in the key's workspace, with the tool name and path.
- [ ] A plain `/api/v1` call writes no such row; `apikey.use` keeps its one-per-minute throttle.
- [ ] 429 and 402 reach the agent as readable tool errors with the API's own wording.
- [ ] No key, prefix or `Authorization` value appears in a row, a log line or a result.
- [ ] Empty, loading and error states above all render as described.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ the endpoint is refused before `resolve_key` is reached, so no rows appear.
- [ ] `ruff check apps/backend` clean; the full serial API suite passes.

## Notes for the implementer
The header is client-asserted; that is acceptable because the row lands in the caller's own workspace and
the key boundary still records the real request. Do not add a second audit table, a queue or a sampler —
one row per call, in the table the Audit screen already reads.
`resolve_key` is called by the hosted upload and predict routes too; the row must be written once per HTTP
request even when the route resolves the key directly (`key_ws`), which it does through this same function.
