## User story
As an ML engineer choosing a model, I want the frontier drawn on the metric that fits my task and the stale scores called out, so that I never pick a winner from an out-of-date evaluation.

## UX flow (LabelDesk words)
1. **Models → Compare** — a metric selector above the scatter: detection offers *mAP@50:95*, *mAP@50*, *mAP@75*, *Precision*, *Recall*, *F1*; instance segmentation adds *mask mAP* and *boundary AP*; classification offers *F1* and *accuracy*. The default follows the task (mAP@50:95 for detection, mAP for segmentation, F1 for classification).
2. **The frontier moves with the metric** — hollow dots are dominated on the selected metric; the tooltip names the metric and its unit.
3. **Needs an update** — a panel under the chart: "2 models need an evaluation update" with *Run*, *Update* and *Update all*; queued and training models are excluded and listed as "waiting". [empty: every model current ⇒ the panel is absent, not empty]
4. **Before any result** — the tab states the next step instead of an empty chart: *Train a model* (no model), *Run evaluations* (models have none), *Update evaluations* (all stale).
5. **A model with no evaluation** — appears in the picker dimmed with "no evaluation", never as a zero-AP dot.

- **States** — [empty: a project with no evaluated model returns `needs_update` for each one and no dots]. [loading: the compare payload returns the last cached result while a stale model is re-evaluated] [error: an evaluation enqueue failure is a 409/402 with a sentence the compare panel prints].

## Backend changes
- Models/schema: `METRICS_VERSION = 2` lives in `services/evaluate.py`; every stored eval gains `metric_version` at write time (no column — it rides the existing `metrics.eval` JSON).
- Routers: `GET {P}/insights/compare?models=&metric=` gains `metric` (`map|map50|map75|precision|recall|f1|mask_map|boundary_ap|accuracy`), validated against the task of the first model (**400** "precision is not comparable for classification" style, naming the valid set). Response gains `metric`, `metric_label`, `needs_update: [{id, reason}]`, `waiting: [id]`. `POST {P}/models/evaluate` body `{model_ids: [str] = [], all: bool = false}` → `{queued: [str], skipped: [{id, reason}]}`; skips `queued|training` models and models with an evaluation job already active; **400** when neither field is given.
- Services/jobs: `services/insights.compare` — `METRIC_KEYS` map per task, `_pareto(models, key)` on the chosen key (default `AP50` today becomes the task default), `staleness(m) -> str | None` returning `"no evaluation"`, `"evaluated before the dataset changed"` (compare `eval.evaluated_at` to `data_stamp`), or `"older metric format"` (`eval.get("metric_version", 0) < METRICS_VERSION`). New job kind `eval_model` in `handlers/training.py::HANDLERS` + `LOCAL_JOB_KINDS`; `run_eval_model(job)` loads the model, calls the same `finalize.evaluate_and_announce` path the train handler uses, and emits `model.ready`.
- Permissions + workspace isolation: compare = `project.models` (unchanged); `POST /models/evaluate` = `c.need("admin")` (it spends GPU time via metering `gpu_seconds`? evaluation is CPU/GPU-light — charge nothing, but still call `metering.check(..., "gpu_seconds", 0)`? No: evaluation is part of a run's cost; here it is a re-run — reserve `quote` of one image pass, one `metering.check` with the evaluated split size and no credit charge, documented in the card's tests). Foreign ids → 404.
- Secrets/safefetch: none.
- OpenAPI: yes — regenerate both files.

## Acceptance criteria
- [ ] The frontend can ask for any task-valid metric and the Pareto frontier follows it.
- [ ] Stale evaluations are named with a reason and can be re-run individually or in bulk; active runs are skipped, not queued twice.
- [ ] A re-run writes `metric_version` so the stale flag clears.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ AP50-only compare, no staleness panel, no evaluate route.

## Notes for the implementer
`metric_version` is the cheap answer to "older evaluations lack new metrics": bump the constant when T-285/T-286 add mask and boundary numbers, and every old eval becomes stale in one place. Do not add a column.
