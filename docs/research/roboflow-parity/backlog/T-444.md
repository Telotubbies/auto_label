## User story
As a customer, I want to close my account and have my data erased, so that leaving the product needs no support ticket.

## UX flow (LabelDesk words)
1. `DELETE /api/me` `{confirm_email, password}` → `202 {job_id}`. The account gets `status="deleting"`:
   sign-in fails with `403 This account is being deleted.`
2. What happens, in order: every workspace the person solely owns is purged (T-443's job), every membership elsewhere is
   removed with the reason `account_deleted`, and the user row keeps only `{email_hash, created, deleted_at}` so the
   audit log's actor column still resolves to "deleted member".
3. `409` when the caller solely owns a workspace that still has other members:
   `Transfer ownership or remove the other members of “Site A” first.` (ownership transfer is not supported, so removal
   is the only path — the sentence says both).
4. `403` for a platform operator (`LD_SUPERADMINS`) — an operator account is disabled by another operator.
5. `[error]` a purge that cannot erase a file stops with `Some files could not be deleted; retry.` and the account stays
   `deleting`, so a retry resumes.
6. **Erasure scope** — sessions, refresh tokens, email tokens, TOTP seed, uploads, annotations authored, comments,
   invocations recorded against the member; a `privacy.erasure` audit row summarises counts.

## Backend changes
- Models/schema: `User.status VARCHAR(16) DEFAULT 'active'`, `User.deleted_at FLOAT | None`,
  `User.email_hash VARCHAR(64) | None`; `ADD COLUMN` additions to `USERS` in `app/schema/identity.py`.
  Email is replaced with `<hash>@deleted.invalid` on completion so the unique index frees the address.
- Routers: `app/routers/account.py` (new) — `DELETE /api/me`, `GET /api/me/deletion` (status for a signed-in account that
  is still `deleting`); `deps.current_user` refuses a `deleting` account.
- Services/jobs: `app/services/account_delete.py` (new) — `preflight(db, user) -> dict` (owned workspaces, blocking
  memberships), `start(db, user, actor) -> Job`, `run(job)` (owned workspaces through `workspace_delete.run`, then
  memberships, then token rows, then the anonymise step), `resume`; uses `mailer` to send one confirmation to the
  original address before anonymising.
- Permissions + workspace isolation: a person may delete only their own account (`c.user`), never another user's; the
  preflight counts only workspaces they own.
- Secrets/safefetch: TOTP seed and recovery codes are deleted with the row; no secret survives.
- OpenAPI: yes.

## Acceptance criteria
- [ ] An account can be deleted with a password and exact-email confirm, and loses access immediately.
- [ ] Owned workspaces are purged first, and a blocked one names the members in the way.
- [ ] Sessions, tokens, TOTP and the email address are erased; audit rows still resolve to a deleted member.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no routes and no danger-zone card.

## Notes for the implementer
The audit log must survive the person: keep an id row and a hash, never the email. Ownership transfer is unsupported, so
the preflight sentence names removal as the only unblock — do not invent a transfer flow here.
