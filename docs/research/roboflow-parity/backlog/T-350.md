## User story
As an ML engineer, I want to say how many production images are kept per day and how often they are bundled for review, so that active learning is a policy I set once instead of a job I remember to run.

## UX flow (LabelDesk words)
1. **Project settings → Active learning → Collection limits** — four numbers and two switches: `Sample rate (%)`, `Cap per minute`, `Cap per hour`, `Cap per day`, `Also keep images with no detections`, `Keep the predictions with the image`. Defaults come from the server: 0 %, 5, 60, 25, on, on. [empty: active learning off → the section is read-only with one line, "Turn active learning on to collect images."] [loading: the summary strip shows skeletons] [error: a cap above the daily maximum → inline "The daily cap is limited to 200 on this plan." and Save is disabled]
2. **Batch cadence** — one select: `Daily`, `Weekly`, `Monthly`, `Never`. The selected cadence states when the next bundle is due: "Next bundle: tomorrow, 02:00." `Never` means images keep collecting into one batch that a person assembles by hand.
3. **Today's usage** — one line under the numbers: "12 of 25 kept today · 61 this week", read from the existing summary.
4. **What a change does** — saving shows "Saved. Collection starts with the next request." — the policy is read per request, so no workflow version is created and nothing is redeployed.

## Backend changes
- Models/schema: none — the policy lives in `projects.settings.active_learning` alongside today's `enabled`, `below`, `sample_pct`, `include_empty`.
- Routers: `apps/backend/app/routers/ops.py` — `PUT /active-learning/settings` accepting `{enabled, below, sample_pct, include_empty, caps: {minute, hour, day}, cadence: "daily"|"weekly"|"monthly"|"never", keep_predictions}` with validation (day ≤ 200, minute ≤ hour ≤ day, sample 0–100); `GET /active-learning` returns the policy and the cadence`s `next_due`.
- Services/jobs: `apps/backend/app/services/active_learning.py` — `cap(project, window)` replacing the single daily cap, `remaining(db, project, window="day")`, `used(db, project, window)`, `cadence(project) -> str`, `next_due(project, now) -> float | None`, `bundle_due(db, now) -> list[Project]` and `assemble(db, project) -> Batch` (renaming an open auto batch instead of creating a second one). `auto_offer` checks the minute, hour and day windows under the existing `_PICK_LOCK`. A scheduler entry in `services/drift.schedule_daily`'s pattern creates the `active_learning` job when a bundle is due.
- Permissions + workspace isolation: settings need `project.settings`; the run needs `project.review` as today.
- Secrets/safefetch: the offer path ingests bytes it already holds; no outbound call.
- OpenAPI: yes — one route and one body shape.

## Acceptance criteria
- [ ] Minute, hour and day caps all enforce, day being the ceiling, and an out-of-range or inverted cap is refused with the reason.
- [ ] A cadence of daily/weekly/monthly bundles once per period into one batch; `never` collects without bundling.
- [ ] The policy is read per request, so saving it needs no workflow redeploy.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ today's threshold/sample/include-empty fields and the single daily cap.

## Notes for the implementer
Windows are counted from the batch rows the job already creates, not from a new counter table — the existing `daily_used` query generalises to `used(window)`. The plan's ceiling lives in `config.AL_CAPS`, not in the card.
