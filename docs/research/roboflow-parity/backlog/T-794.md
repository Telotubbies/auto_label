## User story
As whoever decides between a bigger card and a fixed data pipeline, I want the run's GPU, VRAM and host lines beside its loss curves, so that "the run was slow" becomes a measurement instead of an argument.

## UX flow (LabelDesk words)
1. **Model page → System** (`/:ws/:project/models?model=<id>`) — a `System` section beside the metric charts: host, GPU model, VRAM total, and the sampled series for GPU utilisation, VRAM used, temperature, CPU and RAM. [loading: the section renders its skeleton chart while the first samples arrive] [empty: a run with no samples says "This run reported no host metrics. Update the worker to send them."]
2. **A finished run** — the series end at the last epoch and the run's peak VRAM is stated as one number.
3. **The hint** — when utilisation stays under 60% for the whole run, one line reads "The GPU stayed under 60%: the data pipeline is the limit, not the card." [empty: a GPU-less run states "This project trained on CPU." instead]
4. **Hover** — a tooltip names the epoch and the value; the chart legend follows the existing metric colours.
5. **A run still training** — the section follows the live samples and refreshes with the model poll. [error: the samples request fails ⇒ "System metrics could not be loaded" with a retry, the curves keep working]

## Backend changes
- Models/schema: `RunSample` (`id, workspace_id, job_id, model_id, epoch, created, gpu_util, vram_used_mb, vram_total_mb, temp_c, cpu_pct, ram_pct`) in a new `app/models/telemetry.py`, indexed on `(job_id, created)`; a new table needs no `ADD COLUMN`.
- Routers: `GET …/models/{mid}/system` in `routers/runs.py` returning `{host, gpu, vram_total_mb, samples:[…], peak_vram_mb, hint}`; `project.models` required.
- Services/jobs: `app/services/telemetry.py` (new) — `sampler(job, model)` context manager starting one daemon thread that writes a row every 10 s and on every epoch; GPU values from `torch.cuda.utilization()`, `torch.cuda.mem_get_info()` and `torch.cuda.temperature()` when present, host CPU/RAM from `/proc/stat` and `/proc/meminfo` when readable, otherwise null. `handlers/training.py` wraps the adapter call in it.
- Permissions + workspace isolation: `project.models`; a model id from another workspace answers 404.
- Secrets/safefetch: none.
- OpenAPI: yes — regenerate both generated files.

## Tests to write first

- `test_sampler_writes_one_row_per_tick` — a stubbed sampler with a fake clock → three ticks write three rows for the job.
- `test_missing_gpu_fields_are_null_not_zero` — a CPU-only environment → `gpu_util` and `temp_c` are `None`, `cpu_pct` is a number.
- `test_system_route_orders_samples_by_time` — rows inserted out of order → the payload is ascending by `created`.
- `test_peak_vram_is_the_maximum` — samples 900, 1500, 1200 MB → `peak_vram_mb` is 1500.
- `test_other_workspace_model_is_404` — workspace B reads A's model system → 404.
- `test_flag_off_is_404` — flag off → 404 and no samples are written during a train.
node — `apps/frontend/tests/system-panel.test.mjs`:
- `test_bottleneck_hint_needs_a_full_run_below_60` — ten samples at 45% → the hint; one sample at 80% → none.
- `test_empty_reason_names_the_worker` — no samples → the worker sentence, not "no data".
- `test_series_keeps_null_gaps` — a null temperature leaves a gap rather than a zero drop.
- `test_peak_formats_megabytes` — 1500 → `Peak VRAM 1,500 MB`.

## Acceptance criteria
- [ ] A run records GPU utilisation, VRAM used, temperature, CPU and RAM samples, and the section charts them by epoch.
- [ ] The section states the run's host, GPU model, VRAM total and peak VRAM.
- [ ] A sustained utilisation under 60% names the data pipeline as the limit; a CPU run says so.
- [ ] Empty, loading and error states above all render: no samples names the worker, a slow first sample shows the skeleton, a failed request leaves the curves.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no System section, no route, and training writes no samples.

## Notes for the implementer
Sample every 10 s and never more than once per epoch, cap one run at 5 000 rows (drop the oldest) so a week-long run cannot fill the disk. Null is the honest value when a metric is unavailable — never write 0, which would draw a false "GPU idle" line.
