## User story
As an ML engineer, I want to set 70/20/10 once and choose whether the system moves as few images as
possible, reshuffles everything, or balances each upload batch, so that a split is a decision I can explain.

## UX flow (LabelDesk words)
1. **Versions · Generate · Step 2 (Split)** — **Rebalance** opens percentages (train/valid/test, default
   70/20/10) plus a policy radio: **Move as few as possible** · **Shuffle everything** · **Balance each
   upload batch**, and an optional class scope ("Only images whose classes are all in…").
   [error: percentages that do not sum to 100 → "Percentages must add up to 100", apply disabled]
2. **Versions · Generate · Step 2** — **Apply** returns `202` with a job; the dialog can be dismissed and
   the tray row reads "Rebalancing splits · 48%". [loading: determinate bar]
3. **Versions · Generate · Step 2** — when done the summary reads "Moved 84 images · 412 train · 118 valid ·
   59 test", and the existing "keep current splits" option now produces exactly those ratios.
   [empty: a project with no approved images → the job is not queued and the dialog says "Nothing to
   rebalance yet — approve images first"]
4. **Dataset · Images** — the split badges reflect the new assignment; a project with images already in
   versions keeps those versions untouched (they froze their own split).

## Backend changes
- Models/schema: none (`Image.split` is the stored state).
- Routers: `apps/backend/app/routers/versions.py` — `POST /rebalance` body
  `{percentages: {train, valid, test}, mode: "fewest"|"shuffle"|"per_batch", classes?: list[str]}` →
  `202 {job}`; `400` when percentages do not total 100 or a mode is unknown; requires `project.review`.
- Services/jobs:
  - `apps/backend/app/services/rebalance.py` (new) — only live images with `status == "done"` and
    `deleted_at IS NULL`:
    - `target_counts(total, pct) -> {split: n}` with largest-remainder rounding so the sum is exact.
    - `fewest(rows, targets)` — start from the current split; move only from over-full splits to under-full
      ones, choosing images whose class counts keep the per-split distribution closest (reuse
      `versioning.stratified_split` only for the tie-break ordering, not to reassign everything).
    - `shuffle(rows, targets, seed)` — `versioning.stratified_split` over all rows (today's behaviour).
    - `per_batch(rows, targets)` — group by `batch_id`, apply `stratified_split` inside each group, merge.
    - `class_scope(rows, classes)` — keep only images whose class set is a subset of the chosen names; the
      rest stay put, which forces `fewest`.
  - Job kind `rebalance` in `handlers/versioning.py` (`params {project_id, percentages, mode, classes,
    seed}`), progress per 200 images, `jobs.check` for cancellation, one commit at the end.
- Permissions + workspace isolation: `c.perm("project.review")`; the handler re-reads the project inside
  its session and refuses a deleted or foreign one; rows filtered by `project_id`.
- Secrets/safefetch: none.
- OpenAPI: yes — one route.

## Acceptance criteria
- [ ] The three policies produce the documented behaviour: minimal moves, full reshuffle, per-batch ratios.
- [ ] Targets always sum to the image count and honour the requested percentages.
- [ ] Class scope restricts movement to the chosen classes and forces the minimal-move policy.
- [ ] The run is a cancellable job; a cancel commits nothing; existing versions are untouched.
- [ ] Empty/loading/error states above render (percentage error, progress, summary line).
- [ ] Flag off ⇒ no rebalance route; the version wizard keeps today's single behaviour.
- [ ] Workspace A cannot see or change workspace B's data (404 for a foreign project id).

## Notes for the implementer
Rebalance mutates the project, so it affects the *next* version only — never rewrite a `Version` row or an
existing manifest. Reuse `versioning.stratified_split` for the shuffle and per-batch modes rather than
writing a second class-balancing algorithm.
