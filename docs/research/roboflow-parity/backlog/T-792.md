## User story
As the person planning the next collection trip, I want to see which visual conditions the dataset covers densely and which it barely covers, so that I justify a second site instead of discovering it when the model fails there.

## UX flow (LabelDesk words)
1. **Data → Insights → Embeddings** (`/:ws/:project/insights?tab=embeddings`) — a `Coverage` panel under the scatter: clusters coloured by tag or batch, with counts and per-cluster share. [loading: "Embedding the project… {n} of {total}" with a `Stop` button on the project's first run] [error: the embedding scan fails ⇒ "Coverage could not be computed" with a retry; the scatter keeps its last points]
2. **Thin clusters** — a list of groups below the share threshold, each with its image count, its share and the tags that describe it. [empty: "Every cluster holds at least 3% of the images."]
3. **Click a cluster** — the scatter highlights its points and the list scrolls to its row; the images open in a sheet.
4. **Mark for collection** — writes a `collect` tag on that cluster's images, which the next upload can be checked against; the toast confirms the count. [error: the tag write fails ⇒ the count is unchanged and the sentence stays on the row]
5. **The limitations line** — one sentence phrased as a limitation, not a defect: "This data cannot separate rain from night — both appear only in the same few frames."

## Backend changes
- Models/schema: none — cluster membership is derived from the stored projection; marking uses the existing `Image.tags` JSON.
- Routers: `routers/insights.py` gains `POST …/insights/coverage/mark` `{image_ids, tag}` → `{updated}` (max 500 ids per call, `reviewer`); the existing `GET …/insights/embeddings` payload gains `coverage`.
- Services/jobs: `services/insights_embedding.py` — after `_projection()`, bucket the 2-D coordinates into a fixed 8×8 grid and return `coverage: {grid, clusters:[{id,cx,cy,count,share,tags,classes,brightness,thin}], thin, limitation, threshold}`; no new dependency, no second job kind, no re-clustering on read.
- Permissions + workspace isolation: `project.review` to read, `reviewer` to mark; a project id from another workspace answers 404.
- Secrets/safefetch: none.
- OpenAPI: yes — regenerate both generated files.

## Tests to write first
pytest — `apps/backend/tests/test_coverage.py`:
- `test_every_cluster_has_counts_and_share` — twelve projected points → shares sum to 1.0 within rounding and every cluster has its count.
- `test_thin_clusters_below_the_threshold` — a project of 100 images where one grid cell holds 2 → that cluster is `thin`, a 30-image cell is not.
- `test_small_project_suppresses_thin_judgement` — 20 images → no cluster is marked thin (the threshold needs a real sample).
- `test_mark_for_collection_adds_the_tag` — mark three ids → three images carry `collect` and the rest do not.
- `test_mark_is_capped_at_500` — 501 ids → 422 with the stated sentence, no tag written.
- `test_other_workspace_project_is_404` — workspace B reads coverage or marks ids → 404.
- `test_flag_off_is_404` — flag off → 404 on the mark route and no `coverage` key in the payload.
node — `apps/frontend/tests/coverage-panel.test.mjs`:
- `test_thin_clusters_are_sorted_by_share` — three thin clusters → ascending share.
- `test_share_text_never_prints_zero_percent` — a 1-image cluster of 4 000 reads `<1%`, not `0%`.
- `test_limitation_line_names_two_conditions_or_none` — a payload with two confusable tags produces the sentence; one condition produces no line.
- `test_cluster_label_falls_back_to_grid_cell` — a cluster with no tags renders `Cell 3,5`.

## Acceptance criteria
- [ ] Every cluster shows its image count, its share and the tags or classes that describe it.
- [ ] Groups below the share threshold are listed as thin, and a small project does not get the judgement.
- [ ] Marking a cluster writes the tag on exactly its images and reports the count.
- [ ] Empty, loading and error states above all render: no thin cluster says so, the first run shows progress with a stop, a failed scan keeps the scatter.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no Coverage panel and the embeddings payload is unchanged.

## Notes for the implementer
Bucket the coordinates into a fixed 8×8 grid on the *normalised* projection so the same dataset always produces the same clusters — k-means would drift between runs and a "thin cluster" that moves cannot be acted on. Threshold: thin when share < 3% and the project has at least 50 images; an absolute count below 5 is always thin.
