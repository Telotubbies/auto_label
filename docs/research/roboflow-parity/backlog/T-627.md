## User story
As a vendor manager, I want a new labeler to be scored against a fixed set with known answers before they touch a customer batch, so that the first delivery is not the audition.

## UX flow (LabelDesk words)
The screen is T-628; this card owns the trial and the gate.
1. **`POST /labeling/calibration`** — `{user_id, source: "pool"|"version", count, pass_mark}` creates a trial over approved answer-key images (or a named version's ground-truth images), assigns them to that person and returns the trial. [empty: no reference set → 400 "No reference set yet — add answer-key images first."] [error: "This person already has an open trial." (409)]
2. **`GET /labeling/calibration`** — trials with status, score, pass mark, per-class rows, the worst three images and a retry date.
3. **The labeler works** — the trial's images open exactly like queue work, with `trial: true` on the image detail so the editor can show a banner; the key is never visible to them.
4. **`POST /labeling/calibration/{id}/complete`** — scores every submitted image, writes `score`, `per_class` and `worst` (three image ids with their scores), then `passed` or `failed`; a pass upserts the `ProjectMember` with role `labeler`, a fail sets `retry_at` fourteen days out.
5. **A second attempt** — a new trial is allowed only after the retry date; before it, 409.

## Backend changes
- Models/schema: `app/models/workforce.py` gains `CalibrationTrial` (`id`, `workspace_id`, `project_id` FK CASCADE, `user_id` FK CASCADE, `image_ids` JSON, `pass_mark` Float, `status` in `open|passed|failed`, `score` Float nullable, `per_class` JSON default `{}`, `worst` JSON default `[]`, `retry_at` Float nullable, `created_by`, `created`, `completed`), `Index("ix_calibration_project_user", "project_id", "user_id")`. Table via `create_all`; no `ADD COLUMN` block.
- Routers: `routers/labeling.py` — `GET /calibration`, `POST /calibration`, `POST /calibration/{trial_id}/complete`; 400 for an empty reference set, 404 for a trial or user outside this project, 409 for an open trial or an early retry, 422 for `count` outside 1–100 or `pass_mark` outside 0.1–1.0.
- Services/jobs: `app/services/calibration.py` (new) — `create(db, c, user_id, source, count, pass_mark)` (round-robin assignment like `create_honeypot`, one `CalibrationTrial` row, audit entry), `scorecard(db, trial)` (per image: `answer_key.match` against the honeypot key at the class threshold, overall mean, per class, worst three), `complete(db, c, trial)` (writes the scorecard, upserts `ProjectMember`, sets `retry_at`), `gate_open(db, project_id, user_id)`. No worker job.
- Permissions + workspace isolation: `POST` needs `manager` and `complete` allows that manager or the trial's own user; the target user must be a `Member` of this workspace (404 otherwise) and every image is checked against `c.project.id`.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Acceptance criteria
- [ ] A manager creates a trial over the answer-key pool for a named person, with a count and a pass mark.
- [ ] Completing it writes an overall score, per-class scores and the worst three images, then passes or fails it.
- [ ] A pass grants `labeler` on this project; a fail writes a retry date and grants nothing.
- [ ] Empty, loading and error states above all render where the surface exists: the no-reference-set 400, the open-trial and early-retry 409s, and 404 for a foreign user.
- [ ] Workspace A cannot create, read or complete workspace B's trial (404, not 403).
- [ ] Flag off ⇒ no calibration routes and the QA hub behaves exactly as today.

## Notes for the implementer
A pass must add a `ProjectMember` **only** if the person is already a workspace `Member`; never invite on their behalf. Score the trial with the same matcher and thresholds as production scoring, or the gate measures a different job than the one being hired for.
