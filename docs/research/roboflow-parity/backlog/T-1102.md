## Goal
Write `docs/verify/VERIFY.md`, an exact route that a fresh lane can follow to prove that a LabelDesk change works in the running app, not only in unit tests. Then **run it once from start to finish** and keep the evidence.

## Content (exact commands from this repository, nothing invented)
1. **Launch:** set up the backend venv/deps and the frontend `npm ci` inside the lane's own worktree, seed the demo data, start the API and the frontend on free ports, and say how readiness is checked (`/readyz`, the frontend port). Never use the main checkout, and never start a long-lived dev server outside the run.
2. **Doctor:** prove that the running instance belongs to this run (worktree path, port and `/readyz` JSON). Detect an unusable environment, such as a missing seed, an API that is down or a locked port, and stop with BLOCKED.
3. **Drive:** use the existing Playwright harness (`apps/frontend/e2e`, T-1200 fixtures). Map each feature to a spec, a route, selectors and an expected result.
4. **Evidence:** list the commands with their exit codes, the Playwright report, screenshots and trace, and the API log lines matched by request id (T-1300). Say where they are saved: `B:/02_Projects/ld-tmp/evidence/<card>/`.
5. **Cleanup:** stop only the processes this run started (record their PIDs at launch) and delete only this run's temporary state.

## Feature map
`docs/verify/features/`, one file per feature. Start with `auth.md`, based on `core-loop.spec.ts` sign-in step 1:
- the starting state, route, selectors, actions, expected result and failure conditions;
- the failure conditions include "wrong password shows `invalid email or password`".

Add `project-open.md` and `upload.md`.

## Tests / proof
- Run VERIFY.md once and paste the commands, exit codes and evidence paths into the report.
- Make the run show that invalid credentials produce the expected error.
- Do not change product code or weaken any assertion.
