## User story
As an operations lead, I want to merge two campaign projects into a new training project so that
consolidating does not mean re-uploading or re-labelling, and the sources stay intact.

## UX flow (LabelDesk words)
1. **Home · project row menu** — **Merge projects** opens a dialog with a checklist of projects (same
   workspace only) and a new name field. [empty: fewer than two projects → the menu item is absent]
2. **Merge dialog** — ticking two projects shows the union preview: "840 images · 12 duplicates will
   appear once · 4 classes". [loading: the preview count resolves per tick]
3. **Merge dialog** — **Merge** creates the project and returns to Home with a toast "Merging 2 projects —
   follow it in the job tray"; the tray row reads "Project merge · 62%". [error: a project changed
   mid-merge → the new project keeps the union as of the start and the result names the skipped rows]
4. **New project** — an images and classes summary shows the union with its classes mapped by name; both
   sources are untouched. [empty: both sources empty → the merge is refused with "Both projects have no
   images"]

## Backend changes
- Models/schema: none.
- Routers: `apps/backend/app/routers/projects.py`
  - `POST /merge` body `{source_slugs: list[str] (2–10), name, annotation_group?}` → `201 {project,
    job}`; `400` for fewer than two distinct sources or an empty union; `404` for a slug outside the
    workspace; `409` when the target slug already exists.
  - The new project is a normal `Project` row (same workspace, `settings` copied from the first source
    except review/active-learning) so every other screen works unchanged.
- Services/jobs: `apps/backend/app/services/merge.py` (new) —
  `preview(db, ws, sources) -> {images, duplicates, classes}`,
  `merge(db, ws, sources, name, annotation_group, user_id) -> Project` copying, per live source image:
  bytes into `projects/{new_id}/images/...` via `imaging.store` (physical copy so erasing a source never
  empties the merge), `sha256` union de-duplication inside the new project, tags, split, `meta`,
  `source_ref`, and annotations remapped to target class ids created by normalised name
  (`ensure_class`); batches recreated as `"<source> · <batch>"`; no `metering.record` (the workspace
  already paid for these bytes — mirror of the source product's "duplicate-backed merge").
  Job kind `project_merge` in `handlers/ops.py` (`run_project_merge`) with `params {project_id,
  source_ids}` and `progress` per image.
- Permissions + workspace isolation: `c.perm("workspace.project.create")` for the route; every source is
  resolved with `Project.workspace_id == c.ws.id` and `deleted_at IS NULL`, so a foreign slug is 404.
- Secrets/safefetch: none.
- OpenAPI: yes — one route + job kind.

## Acceptance criteria
- [ ] Two or more same-workspace projects merge into a new project holding the union as of the start.
- [ ] Duplicate content appears once; annotations, tags, split and metadata survive with classes mapped by
      name.
- [ ] The storage meter does not double count, and the sources remain intact (deleting a source later
      cannot empty the merge).
- [ ] The merge runs as a job with progress and a result naming anything skipped.
- [ ] Empty/loading/error states above render (source checklist, preview loading, refusal for an empty
      union).
- [ ] Flag off ⇒ no merge action, routes 404.
- [ ] Workspace A cannot see or change workspace B's data (404 for a foreign source slug).

## Notes for the implementer
Copy bytes with `imaging.store` rather than sharing a path: erasure (`erasure.delete_project_data`) deletes
files under the project's own directory, so a shared path would let one delete destroy the other. The merge
is a snapshot, never a live link.
