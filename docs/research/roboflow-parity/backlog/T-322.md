## User story
As a workflow author, I want to place blocks on a canvas and see their ports, so that a pipeline that is not a straight line can be built without reading a JSON file.

## UX flow (LabelDesk words)
1. **Workflows → editor** (`/:ws/:project/workflows/:id`) — the linear list is replaced by a canvas when `task_322` is on: nodes as solid cards on `--surface-container`, ports as labelled dots on their left and right edges, edges as 2 px curves. The block palette sits on the left, the config panel on the right, the run panel below the canvas. [empty: a new workflow opens with one `Model` node and one `Outputs` node already wired] [loading: the editor paints the canvas frame and four node skeletons] [error: the definition fails to load → the canvas is replaced by "This workflow could not be read." with "Open the last good version" pointing at T-330]
2. **Add a block** — "Add a block" opens the palette (one row per type, its `in`/`out` ports listed); the "+" under an existing node inserts the new node after it and, in Auto mode, wires the matching ports (T-323 does the wiring; this card renders the affordance).
3. **Select a node** — the right panel shows that block's fields, required ports first, then optional ones; the node gets a 2 px `--primary` ring and `aria-selected="true"`.
4. **Move a node** — drag moves it; arrow keys move the focused node by 8 px and `Shift`+arrow by 32 px, so the canvas is usable without a pointer. Positions persist per workflow in `localStorage` under `ld:wf-layout:<id>` and never travel to the server.
5. **The old list** — `task_322` off renders exactly today's `WorkflowBlocks` list, so nothing is lost and a reviewer can compare both.

## Tests to write first
pytest — `none: no backend surface`.
node — `apps/frontend/tests/workflow-graph.test.mjs`:
- `test_an_empty_definition_lays_out_a_model_and_an_outputs_node` — `orderedNodes({nodes: [], edges: []})` returns the two seed nodes in order.
- `test_edges_are_drawn_from_the_named_ports` — a `model:detections → filter:detections` edge produces a path whose start and end match those two port boxes.
- `test_positions_survive_a_reload_and_unknown_ids_are_dropped` — a stored layout with an extra node id still lays out the real nodes; a corrupt `localStorage` value falls back to auto layout without throwing.
- `test_a_disabled_node_renders_dimmed_with_its_id` — `layout` marks `disabled` nodes with `dimmed: true` and keeps their edges.
- `test_keyboard_moves_are_eight_and_thirty_two_pixels` — `arrow` → 8, `shift+arrow` → 32, and a move never pushes a node outside the canvas bounds.

## Acceptance criteria
- [ ] With the flag on, a workflow renders as nodes and edges with labelled ports, and an old linear workflow opens as a straight line.
- [ ] Adding a block from the palette inserts a node; the "+" under a node inserts after it; both keep the definition valid enough to save.
- [ ] Selecting a node opens its fields with required ports first; the node is focusable and its state is announced.
- [ ] Arrow keys move the focused node 8 px and `Shift`+arrow 32 px; nothing moves with `prefers-reduced-motion` beyond the instant position.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids) — saving goes through T-320's project-scoped route.
- [ ] Flag off ⇒ today's list editor renders, byte for byte.

## Notes for the implementer
Keep `WorkflowBlocks.tsx` as the per-block field renderer and mount it in the config panel rather than duplicating eleven field groups. Node positions are client state only: a shared workflow must not depend on where one person dragged a box.
