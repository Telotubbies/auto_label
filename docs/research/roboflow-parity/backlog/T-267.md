## User story
As a project manager, I want to delete a run and be told what stops serving, so that removing a model cannot take production down by surprise.

## UX flow (LabelDesk words)
1. **Models → row menu → *Delete run*** — the dialog names the run and the consequence: when the model is bound to `production`, "This is serving `production`. Deleting it stops new predictions on that alias until you deploy another model." When it is bound to `staging`, the same sentence with `staging`. When it is the only ready model, "This project will have no deployable model."
2. **Typed confirmation** — an input labelled *Type the run's name to confirm*; the primary stays disabled until the value matches exactly (trimmed, case-sensitive). [error: a mismatch states "The name does not match." without clearing the field]
3. **A running run** — the menu item is absent; the row's tooltip says "End the run before deleting it."
4. **Success** — the row leaves the list, the alias card on the Deploy page shows *Not deployed*, and a toast says "Run deleted. <alias> is not serving." [error: "Some files could not be deleted; try again" with a Retry — the row stays]
5. **Restorable window** — the dialog adds "You have 30 days to restore it from Trash." only once area 7's trash ships; until then the sentence is absent (see Notes).

- **States** — [empty: no alias is bound, so the serving sentence is omitted rather than shown as "none"] [loading: the primary shows a spinner while the delete is in flight].

## Backend changes
- Models/schema: none new — `TrainedModel` and `DeploymentAlias` exist. The delete path keeps the existing `erasure.delete_model_files` byte-first order.
- Routers: `DELETE {P}/models/{mid}` gains a required body/query `confirm_name: str` (mismatch ⇒ **400** "the name does not match") and returns `{ok: true, aliases_cleared: ["production"], served_next: {alias: model_id | null}}`; **409** while the model is `queued|training` ("end the run before deleting it") and **409** when files cannot be removed (today's message). A `DeploymentAlias` currently pointing at the model is set to `model_id = NULL` in the same transaction and a `DeploymentEvent(action="undeploy")` row is appended, so the Deploy page stops claiming a deleted model serves.
- Services/jobs: `services/deployments.detach(db, model_id) -> list[str]` — one function: find aliases pointing at the model, null them, append events; called from the delete route.
- Permissions + workspace isolation: `c.need("admin")` unchanged; foreign model id → 404.
- Secrets/safefetch: none.
- OpenAPI: yes — regenerate both files.
