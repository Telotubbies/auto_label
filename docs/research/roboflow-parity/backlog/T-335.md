## User story
As an ML engineer, I want one row per production request with its model, latency, detection count and average confidence, so that I can see what the endpoint actually did last week.

## UX flow (LabelDesk words)
1. **A hosted call** (`POST /api/v1/models/{id}/predict`, and the invoke route) — the response already carries the predictions; this card adds no field. Behind the scenes one row is written with `request_id`, model, workspace, project, status code, latency, prediction count, mean confidence and the optional saved image reference.
2. **Deliveries and refusals** — `[error]` a `402`, `413`, `422`, `429` or `503` is recorded with `billed: false` and no predictions, so the table can answer "did this cost me anything".
3. **Images are not stored by default** — one line in the monitoring page: "Request images are not saved. Turn this on per project to keep the frame beside the request." Toggling it writes `projects.settings.request_images = true`; the store then saves the frame under `snapshots/<project>/requests/<request_id>.jpg` with the same metering and erasure rules as a stream snapshot.
4. **Retention** — rows are deleted by the existing retention job after the project's retention window; `[empty]` a project with no traffic shows no rows at all (a model with no traffic is absent, not zero).

## Backend changes
- Models/schema: `request_log` (new model module `apps/backend/app/models/requests.py`, registered in `models/__init__.py` and `DOMAIN_MODULES`): `id` (the request id, 16 hex), `workspace_id` (indexed), `project_id` (indexed), `model_id` (nullable), `kind` (`hosted | workflow`), `status` (int), `latency_ms` (float), `n_predictions` (int), `mean_confidence` (float, nullable), `billed` (bool), `image_path` (varchar, default ""), `meta` (JSON: region, tile size, client), `created` (float, indexed). The table is created by the model module; no `ADD COLUMN` block is needed for a new table.
- Routers: `apps/backend/app/routers/monitor.py` (new) — `GET /api/ws/{ws}/projects/{project}/requests?from&to&model&status&billed&offset&limit` returning `{total, lookback_days, items}`; `GET /requests/{rid}` returning one row plus its image URL when saved. T-336 adds the aggregates to the same router.
- Services/jobs: `apps/backend/app/services/request_log.py` (new) — `record(db, ws, project, model, request_id, status, latency_ms, pred, billed, meta)`, `page(db, project, q)`, `one(db, project, rid)`, `save_image(db, ws, project, request_id, data) -> str` (path-joined, metered, refused when the setting is off), `purge(db, project_id, before)` called by the retention job.
- Permissions + workspace isolation: `project.models` to read (the eval report has the same rule); a foreign `rid` is 404; the write path is server-side only.
- Secrets/safefetch: no new outbound call; the saved image comes from the bytes already in memory.
- OpenAPI: yes — two routes.

## Acceptance criteria
- [ ] Every hosted and workflow invoke request writes one row with model, status, latency, prediction count and mean confidence.
- [ ] A refused request is recorded as unbilled with no predictions, and nothing is written when the flag is off.
- [ ] No image is saved unless the project opted in, and an opted-in image is metered, erasable and purged with the row.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ today's behaviour: no rows, no routes.

## Notes for the implementer
Reuse `metering.record` for the image bytes and the existing erasure/retention hooks rather than inventing a second store. Never store the request body, the key or the client's headers; `meta` is a closed vocabulary (`region`, `tile_size`, `client`).
