## User story
As an operator under pressure, I want a reversible pause next to the irreversible revoke, so that a suspected
leak does not force me to destroy a key and redeploy every consumer.

## UX flow (LabelDesk words)

*Screen this contract serves:* the **API keys** table in Settings (its row menu, dialogs and badges are T-389's
card). States the table must show: a protected key → lock badge and only `Unprotect` in the menu; a disabled key →
grey row with `Disabled` and an `Enable` action; the last key → `Revoke` disabled with the 409 sentence as its
tooltip; a refused action → the sentence inline on the row, not a toast that disappears.

1. `PATCH /api/ws/{ws}/keys/{kid}` `{name}` → 200 with the row; the value, scopes and state are unchanged.
2. `POST /api/ws/{ws}/keys/{kid}/protect` `{protected: true}` → a protected key answers
   `409 This key is protected. Unprotect it in the app first.` to every other mutation.
3. `POST /api/ws/{ws}/keys/{kid}/disable` → `disabled_at` set; every API call with that key answers
   `401 This key is disabled.` on the next request. `POST .../enable` clears it.
4. `DELETE /api/ws/{ws}/keys/{kid}` → `409 This is the workspace's last key — create a replacement first.` when it
   is the only non-publishable key; otherwise 200 and the row is gone.
5. `[error]` a protected key's disable/roll/revoke returns the same 409 sentence, and the audit row records the
   refusal's intent as `apikey.protect_refused`.

## Backend changes
- Models/schema: none (T-388).
- Routers: `routers/workspaces.py` — `PATCH /keys/{kid}`, `POST /keys/{kid}/protect`, `POST /keys/{kid}/disable`,
  `POST /keys/{kid}/enable`; `DELETE /keys/{kid}` gains the last-key guard. All `404` for a foreign id.
- Services/jobs: `services/keys.py` — `rename`, `set_protected`, `set_disabled`, `revoke`, `last_key(db, ws) -> bool`;
  each returns the row dict for the response and raises `KeyProtected` (mapped to 409 in the router).
- Permissions + workspace isolation: `workspace.keys`; `disabled_at` is honoured in `apikeys.resolve_key` so a
  disabled key cannot authenticate even if a caller caches it.
- Secrets/safefetch: none — the secret is never re-read.
- OpenAPI: yes.

## Acceptance criteria
- [ ] Rename, protect, unprotect, disable, enable and revoke each work and are audited by name.
- [ ] A protected key cannot be disabled, rolled or revoked from the app or the API until unprotected.
- [ ] The last non-publishable key cannot be revoked and the refusal names the fix.
- [ ] Empty, loading and error states above all render (409 sentences, 404 for a stale row).
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ only today's `DELETE` route exists.

## Notes for the implementer
`publishable` keys are excluded from the last-key count — a browser key cannot run a CI pipeline. Disable is
immediate: no grace window, because the whole point is to stop a leaked credential now.
