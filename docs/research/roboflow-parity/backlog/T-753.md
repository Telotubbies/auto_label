## User story
As a DPO, I want the facts our DPA already claims as rows I can filter and hand over, so that the second question in a review — "where is the basis written down" — has an answer with a date on it.

## UX flow (LabelDesk words)
No screen in this card (T-754 renders it):
1. **The register** — `GET /api/ws/{ws}/compliance/register` answers one row per live project, each auto-filled from the project's own settings (`retention_days`, `face_blur`, `biometrics`, `legal_basis`, the live image count) plus the manual fields: `purpose`, `data_categories`, `recipients`, `review_date`.
2. **A project with no purpose written** — the row carries `{complete: false, missing: ["purpose"]}` and the screen prints `"Purpose not recorded."` The register never invents a purpose from the project name.
3. **A biometrics project with no basis** — `{complete: false, missing: ["lawful_basis"], warning: "Biometrics is on and no legal basis is recorded."}` — the same fact that makes `PATCH /projects/{p}/privacy` refuse, stated where a DPO will see it.
4. **A transfer** — `POST /compliance/transfers {destination, recipient, basis, signed_on, doc}` records one row; the copy lists `Adequacy decision`, `Standard contractual clauses`, `Explicit consent`, `Contract necessity` and never selects one for the customer. [empty: "No transfers recorded." / "ยังไม่มีการบันทึกการโอนข้อมูล"]
5. **A consent record** — `POST /compliance/consents {subject_label, purpose, given, evidence}` records one; a withdrawal is a second row, never an edit, so the history is intact.
6. **Export** — `GET /compliance/register.csv` returns the register with a BOM and formula-safe cells, the same guard the audit export uses; the PDF the group file asks for is the browser's print of the screen (T-754), not a second renderer.

## Backend changes
- Models/schema: three classes appended to `app/models/compliance.py` — `ProcessingRecord(id, workspace_id, project_id UNIQUE per workspace, purpose TEXT, data_categories JSON, recipients JSON, cross_border BOOLEAN, review_date FLOAT null, updated, updated_by)`, `TransferRecord(id, workspace_id, destination VARCHAR(120), recipient VARCHAR(200), basis VARCHAR(32), doc_name VARCHAR(255), signed_on FLOAT null, created, created_by)`, `ConsentRecord(id, workspace_id, subject_label VARCHAR(200), purpose VARCHAR(200), given FLOAT, withdrawn FLOAT null, evidence VARCHAR(255), created_by)`. No `ADD COLUMN`.
- Routers: in `app/routers/compliance.py` — `GET /compliance/register`, `PATCH /compliance/register/{project}` (`purpose`, `data_categories`, `recipients`, `cross_border`, `review_date`), `POST /compliance/transfers`, `DELETE /compliance/transfers/{id}`, `POST /compliance/consents`, `GET /compliance/register.csv` (UTF-8 BOM, `text/csv`).
- Services/jobs: `app/services/register.py` (new) — `BASES = ("adequacy", "scc", "consent", "contract")`, `rows(db, ws) -> list[dict]` (joins `Project` settings with the stored record and computes `missing`), `upsert(db, ws, project_slug, body)`, `add_transfer(db, ws, body)`, `add_consent(db, ws, body)`, `to_csv(rows) -> str` (reuses `services.csvsafe.cell` and the BOM trick from `routers/audit.py`).
- Permissions + workspace isolation: `c.perm("workspace.update")` on the writes and `workspace.audit` on the export; a `project` slug resolves inside `c.ws.id`, so a foreign slug is 404 and a foreign transfer id is 404; rows are never joined across tenants.
- Secrets/safefetch: none — the transfer document is a file *name* recorded by the customer, not an upload; a document is attached through the shipped upload path only if one already exists, and this card stores no bytes.
- OpenAPI: yes — six routes and three row shapes.

## Tests to write first
pytest — `apps/backend/tests/test_processing_register.py`:
- `test_rows_are_autofilled_from_the_project` — a project with `retention_days = 90`, `face_blur = True` and 12 images produces one row carrying those values and `images: 12`.
- `test_a_missing_purpose_is_reported_not_invented` — a fresh project's row has `complete: false`, `missing` contains `purpose`, and `purpose` is the empty string, never the project name.
- `test_biometrics_without_a_basis_is_flagged` — `biometrics = True` with an empty `legal_basis` yields the warning sentence and `missing` contains `lawful_basis`.
- `test_a_purpose_is_stored_once_per_project` — two `PATCH` calls update one `ProcessingRecord`, not two.
- `test_a_transfer_needs_a_known_basis` — `basis: "friend"` is 422; `scc` is accepted and the row appears in the register read.
- `test_a_consent_withdrawal_is_a_second_row` — a withdrawal writes a new `ConsentRecord` and leaves the original `given` intact.
- `test_csv_has_a_bom_and_escapes_a_formula` — the export starts with `\ufeff` and a purpose beginning `=` is prefixed so a spreadsheet does not execute it.
- `test_flag_off_and_foreign_ids` — with the flag off all six routes are 404; a project slug or transfer id from another workspace is 404.

## Acceptance criteria
- [ ] One register row per live project, auto-filled from its privacy settings, with the manual purpose, categories and recipients editable.
- [ ] An incomplete row lists what is missing; a biometrics project with no basis is flagged with the same fact the API refuses on.
- [ ] Transfers and consents are rows that can be added and listed; a withdrawal never edits a prior consent.
- [ ] Empty, loading and error states above all render: an empty register before the first project, an empty transfer list, a 422 naming the bad basis.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no register rows, no transfer or consent route, and the Compliance page shows only Requests.

## Notes for the implementer
Owner-gated: which lawful basis each project relies on, which purposes are declared, and whether a transfer rests on an adequacy decision, standard clauses or consent — the controller decides with its adviser, and LabelDesk only records the answer (INDEX §4.3). Do not pre-select a basis for a new transfer: a default here becomes a claim in a document nobody re-read. The DPA renderer in `routers/privacy.py` stays the prose of record; this register is its structured evidence, and the two must not be allowed to disagree — read the same project columns, never a copy.
