## User story
As the operations lead who filed yesterday's ticket, I want to read what happened and subscribe to the next one, so that I learn it from the page instead of from a customer's phone call.

## UX flow (LabelDesk words)
1. **Public `/status` → `Past incidents`** — a list newest first: date, title, severity, duration and the state it ended in. An open incident appears at the top with its four lifecycle words and timestamped updates. [empty: "No incidents in the last 90 days."] [loading: two skeleton rows] [error: "The incident history could not load." with `Try again` and no fake empty state]
2. **One incident** (`/status/incidents/<id>`) — the facts, every update with its state and time, and, once published, a `Postmortem` section with cause, impact and follow-up actions.
3. **`Subscribe by email`** — one field; on success "Check your inbox — the confirmation link finishes the subscription." [error: "That address is not accepted — use the address you want us to reach."]
4. **The confirmation link** (`/status/confirm/<token>`) — reads "You are subscribed to status updates." or "That link has expired."
5. **An operator publishes an incident** — `/:ws/ops/incidents/<id>` gains `Publish to the status page`; publishing copies the public-safe fields only and writes one timeline entry. Unpublished incidents never appear publicly.

## Backend changes
- Models/schema: `StatusSubscriber(id, email, token, confirmed_at, created)` appended to `app/models/incidents.py`; `Incident` gains `published_at FLOAT` and `postmortem TEXT` in the same module.
- Routers: `app/routers/status_page.py` — `GET /api/public/status/incidents?days=90` (published only), `GET /api/public/status/incidents/{id}` (404 unless published), `POST /api/public/status/subscribe` (202; 422 on a malformed address; idempotent), `GET /api/public/status/confirm/{token}`; `app/routers/incidents.py` — `POST /api/ws/{ws}/incidents/{iid}/publish` (`workspace.audit`, sets `published_at`).
- Services/jobs: `app/services/status_subscribers.py` (new) — `subscribe(db, email) -> dict`, `confirm(db, token) -> bool`, `confirmed(db) -> list[str]`; `app/services/status_page.py` — `public_incidents(db, days)`, `public_incident(db, iid)`, both projecting only title, severity, states, update text, timestamps and postmortem.
- Permissions + workspace isolation: the public reads are published-only and carry no workspace id; publishing needs `workspace.audit`; an incident id from another workspace is 404 for the publish route.
- Secrets/safefetch: the confirmation token is `secrets.token_urlsafe(24)`, stored as given; no address is ever returned by a public endpoint.
- OpenAPI: yes.

## Tests to write first

- `test_an_unpublished_incident_is_invisible` — an incident with `published_at = None` → `GET /api/public/status/incidents` omits it and `GET …/{id}` is 404.
- `test_a_published_incident_carries_its_updates_and_no_tenant` — publish one → the public payload has the updates in order and no workspace slug, owner email or project name.

- `test_publishing_needs_workspace_audit` — labeler `POST …/publish` → 403; owner → 200 with `published_at` set and one timeline row.
- `test_flag_off_hides_the_history_routes` — with the flag off → every route on this card 404.

## Acceptance criteria
- [ ] Only published incidents appear on `/status`, with their updates in order and a postmortem once written.
- [ ] A subscription needs a confirmation and never sends twice to one address.
- [ ] Publishing is owner/admin only, and nothing tenant-identifying reaches the public payload.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no history, no subscribe, all routes 404, and incident handling is exactly as T-766 left it.

## Notes for the implementer
Owner-gated: how much of an incident is published, how long the history stays up, and who may publish (INDEX §4.3). The history list is the evidence T-774's uptime claim rests on, so an incident must never be deleted to improve a percentage. `StatusSubscriber` duplicates four fields of the trust subscription on purpose: sharing a table across two public surfaces would let one page's unsubscribe mail silence the other.
