# T-1314 — Workspace system-health endpoint

| Field | Value |
| --- | --- |
| Wave | O (security, monitoring, performance) |
| Area | Monitoring |
| Size | 2.5 agent-hours |
| Role | R3 backend |
| Skills | ponytail, test-driven-development, verification-before-completion |
| R7 security review | yes — aggregate data across a workspace boundary |
| Depends on | T-1301 (disk check helper), T-1302 (metric registry), T-1311 (worker/queue gauges) |
| Feature flag | none — owner/admin only |

## Problem
A workspace owner cannot see their own queue, their stuck jobs, the workers serving them, the disk or
the API's error rate. The existing health view is the **superadmin** console
(`routers/admin.py`, `features/admin/AdminConsole.tsx`), cross-workspace and unavailable to tenants, so
every "is it slow for me?" question lands on the operator.

## Design
`GET /api/ws/{ws}/system/health`, `owner`/`admin` only (`c.need("admin")`), one response, one query set:

```json
{"queue":{"queued":3,"running":1,"oldest_queued_s":42,"failed_24h":2},
 "jobs":[{"id":"j_…","kind":"export","status":"running","progress":61,"age_s":120}],
 "workers":[{"id":"gpu-1:4271","online":true,"heartbeat_age_s":4,"current_job":"j_…"}],
 "disk":{"free_gb":38.2,"used_ratio":0.74},
 "gpu":{"used_mb":6100,"budget_mb":8192,"leases":2},
 "api":{"requests_5m":812,"errors_5m":3,"p95_ms":180},
 "alerts":[],
 "version":"1.0.0"}
```

- Queue and job rows filter `workspace_id` (the same rule as every other query).
- `workers` lists the `Worker` rows whose `kinds` intersect this workspace's local kinds — i.e. the
  platform's workers, not per-tenant processes, because that is the truth; the field is documented as
  platform-scoped, and the response carries `workers_scope: "platform"`.
- `api` reads the in-process registry (`app/metrics.py`) when `LD_METRICS_TOKEN` is unset **or** the
  caller is on the same process; in a split deployment it returns `null` and the UI says
  "unavailable in this deployment" rather than a wrong number.
- `alerts` lists the four platform rules currently firing, read from the same evaluator the checker job
  uses (`services/system_check.evaluate(...)`, created by T-1317; this card may ship with an empty list
  until that lands, guarded by a `try/except ImportError` **only** if the merge order forces it).
- `disk` reuses the T-1301 helper; `gpu` reuses `gpu.scheduler.state()`.
- Bounded cost: five aggregate queries + one `limit 20` job list; p95 < 120 ms with 10 000 jobs.

## Tests to write first
`apps/backend/tests/test_system_health.py`:
- `test_counts_are_workspace_scoped` — workspace B's queued and failed jobs never appear.
- `test_jobs_list_is_capped_at_20_and_newest_first`.
- `test_member_is_403_and_labeler_is_403` — owner and admin are 200.
- `test_foreign_workspace_slug_is_404`.
- `test_disk_and_gpu_shapes` — numbers are plausible, GPU absent without a driver.
- `test_api_block_is_null_when_the_registry_is_unavailable` and `test_api_block_is_filled_in_process`.
- `test_response_carries_no_paths_or_dsns` — grep the JSON for `/`, the data dir, `postgres`: only the
  version string and ids may contain slashes.
- `test_cost_is_bounded` — with 10 000 seeded jobs the call issues ≤ 8 queries (query-count fixture from
  T-1323 if it has landed; otherwise a simple `before_cursor_execute` counter local to the test).

## Acceptance criteria
- [ ] Owner/admin of the workspace get the payload; member, labeler, billing and a foreign slug do not.
- [ ] Every count is workspace-scoped and the isolation test proves it.
- [ ] `api` is `null` when it cannot be measured, never a fabricated number.
- [ ] No filesystem path, DSN, secret or user email appears in the response.
- [ ] ≤ 8 queries and p95 < 120 ms with 10 000 jobs (number in the report).

## Notes for the implementer
This is not a second admin console: it answers "my workspace", the console answers "the platform". Do
not add a per-kind breakdown of the whole queue — `jobs[]` (20 rows) plus counts is enough for the page
and keeps the query plan simple. Reuse the T-1301 check functions instead of re-implementing a disk
probe.
