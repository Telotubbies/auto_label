## User story
As an ML engineer reading a search, I want the spread of candidates per epoch and a speed-versus-accuracy dot per candidate, so that "nearly as good and twice as fast" is a picture, not a table I have to sort.

## UX flow (LabelDesk words)
1. **Models → a search run → Results** — two charts and one table.
   - *Progress band*: for each epoch, a shaded band from the worst to the best candidate score with the front (best) line on top; hovering shows the epoch's best, median and worst with the candidate names. [empty: no epoch finished yet ⇒ "Waiting for the first epoch."] [loading: the band's axes with a shimmer inside] [error: "The search results could not be read" + Retry]
   - *Speed vs accuracy*: one dot per candidate, x = median latency, y = headline metric, dot size = credits used, lighter = faster. Dots outside the frontier are hollow. Clicking a dot selects its table row.
2. **Candidate table** — variant, family, score, latency, credits, state (done / failed / stopped / kept). A failed row prints its remedy.
3. **Keep** — the action from T-271 sits on the table row and on the selected dot's card; the action is disabled with "no weights were saved" when the candidate has none.
4. **A fast search (one candidate band)** — the band falls back to the ordinary line chart with a note "This search tried a single candidate." — never an empty band.
5. **Export** — both charts keep the existing `ChartCard` export affordances (CSV/JSON/table) so a result can leave the app.
