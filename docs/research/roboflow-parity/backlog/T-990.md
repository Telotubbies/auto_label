## User story
As the person wiring an agent or a script to LabelDesk, I want my workspace API key to read a project's
detail, search its images and read or write one image's annotations, so that the label loop can be driven
without a browser session and without a second permission model.

## UX flow (LabelDesk words)
This is an API surface; the "screens" are the four requests and the states each one returns.
1. **`GET /api/v1/projects/{project}`** — an agent reads the project before touching it. [empty: a project
   with no classes answers `classes: []` and `statusCounts: {}`, never 404] [error: an unknown or
   foreign slug answers 404 `project not found`].
2. **`GET /api/v1/projects/{project}/images?q=&split=&status=&class_id=&annotated=&sort=&offset=&limit=`**
   — the same filtering the Dataset screen has, so "find the unlabelled train images" is one call.
   [empty: `{total: 0, items: []}`] [error: `limit` above 1000 is clamped, not refused].
3. **`GET /api/v1/images/{image_id}`** — one image with its full annotation set. [empty: `annotations: []`]
   [error: an id from another workspace is 404 `image not found`, the same answer as an id that never
   existed].
4. **`PUT /api/v1/images/{image_id}/annotations`** — replace one image's annotations with a validated set.
   [error: a bad shape is 400 with the field that failed; a `classId` from another project is 400; a key
   without `write` is 403 `api_key lacks the 'write' scope`].

## Backend changes
- Models/schema: none. `API_SCOPES` in `app/models/common.py:14` gains `write` →
  `("read", "upload", "write", "train", "infer")`. No new column, no backfill.
- Routers — all in `app/routers/devapi.py` (key-authenticated, `Depends(key_ctx)`):
  - `GET /projects/{project}` `operation_id="get_project"`, `x-scopes: ["read"]` → `project_out(db, p,
    detail=True)` with the `settings` key removed (it can carry webhook/connector values).
  - `GET /projects/{project}/images` (existing operation `list_images`, extended in place — no new
    operation id) gains `q, split, status, class_id, tag, batch_id, annotated, sort` and **delegates** to
    `routers/images.list_images(...)` with `_ctx(k, p)`, so `_visible`, the honeypot masking and the
    `sort=review` ranking exist once.
  - `GET /images/{image_id}` `operation_id="get_image"`, `x-scopes: ["read"]` → resolve the image through
    the key's workspace, then `images._image_with_annotations(_ctx(k, p), img)`.
  - `PUT /images/{image_id}/annotations` `operation_id="write_annotations"`, `x-scopes: ["write"]` →
    `images._check_ann(...)` per annotation, `images._check_class_ids(...)`, then
    `labeling_ops.save_annotations(db, c, img, checked)`. The consensus-draft branch does not apply to keys
    and is not taken.
  - `GET /whoami` (existing operation, one field added) gains `"mcp": is_enabled("task_992", k.db, k.ws.id)`
    plus its `task_992` registry line. The MCP server asks `whoami` once per request for the key's scopes,
    so this one boolean is the workspace's on/off switch for the whole endpoint — for stdio and HTTP alike,
    and without a second route. Registering the key here rather than in T-992 is deliberate: T-992 consumes
    it and must not touch this file.
- Services/jobs: one new helper in `devapi.py`:
  `_writer_ctx(k: KeyCtx, p: Project | None = None) -> Ctx` — builds the write context with
  `user = db.get(User, k.key.created_by) or db.get(User, k.ws.owner_id)`. `label_events.user_id` is NOT
  NULL (`app/models/insights.py:123`), so a key's label write is attributed to the key's issuer; a key with
  no `created_by` falls back to the workspace owner. `_ctx` keeps `user=None` for every read route.
- Permissions + workspace isolation: scope checked by `k.need(...)`; the project comes from
  `k.project(slug)` (already `workspace_id + slug + deleted_at IS NULL`), the image from
  `Image.project_id == p.id`. A foreign id is 404, never 403.
- Secrets/safefetch: none on these routes; `get_project` drops `settings`, and nothing here echoes a key,
  a hash or a storage path.
- OpenAPI: yes — `python tools/export_openapi.py` and `npm run gen:api-types`; add the three new operation
  ids to `DEVELOPER_OPERATIONS` (`tools/gen_sdk.py:27-42`) and to `EXPECTED_SCOPES`
  (`apps/backend/tests/test_sdk_cli.py:26-39`, count 12 → 15), then `python tools/gen_sdk.py`.

## Acceptance criteria
- [ ] The requests above answer as described, with 200/403/404/400 in the cases listed.
- [ ] `list_images` keeps its `{total, items}` shape and its existing unfiltered behaviour byte for byte.
- [ ] A key-issued annotation write lands as one `LabelEvent` under the key's issuer, never a NULL user.
- [ ] `get_project` never returns `settings`.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag `task_992` is registered here and reported by `whoami`; off ⇒ the MCP endpoint refuses every
      call (T-992, T-996) and none of these routes changes behaviour for the SDK or the CLI.
- [ ] `python tools/gen_sdk.py`, `python tools/export_openapi.py` and `npm run gen:api-types` run clean;
      `ruff check apps/backend` is clean; the full serial API suite passes.

## Notes for the implementer
The `list_images` body is replaced by a delegation, not by a copy: if you find yourself re-typing a filter
clause, stop — every filter, the labeler scoping and the honeypot masking already live in
`routers/images.py:191-291`.
`_writer_ctx` is for write paths only. Do not hand a real user to `_ctx`: audit rows for reads must keep
`user_id=None`, which is how the audit screen already spells "API" (`routers/workspaces.py:297`).
