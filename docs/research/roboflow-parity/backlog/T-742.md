## User story
As a workspace admin, I want to allow only our office and VPN ranges, so that a password alone is not enough from anywhere in the world — and I want the refusal to say which range I am outside, so support can answer in one message.

## UX flow (LabelDesk words)
No screen in this card (T-743 draws the list editor):
1. **A member on a coffee-shop network** — every workspace request answers 403 whose body is `{"code": "ip_not_allowed", "ip": "203.0.113.9", "rule": {"kind": "ip", "ranges": ["49.228.0.0/16", "10.0.0.0/8"]}, "contact": "owner@acme.example"}`. [error: the screen prints `"This workspace is limited to its own networks. Your address 203.0.113.9 is not one of them."` / `"เวิร์กสเปซนี้จำกัดเฉพาะเครือข่ายขององค์กร ที่อยู่ 203.0.113.9 ของคุณไม่อยู่ในรายการ"`]
2. **The same member from the office** — nothing changes; no banner, no extra click.
3. **An admin saving a list that excludes themselves** — refused with `"Your own address is not in that list — you would lock yourself out. Add it first."`
4. **A list that cannot be parsed** — `"10.0.0.999 is not a valid address range. Use CIDR, for example 10.0.0.0/8."`
5. **An upload over the SDK with a key** — keys carry no session, so the same workspace check applies: the key's request is refused with the same body, never a silent 401.

## Backend changes
- Models/schema: `Workspace.ip_allowlist JSON` (nullable; `null`/`[]` = allow every address, so nothing changes on an existing workspace). One key in the `WORKSPACES` block of `app/schema/identity.py` (`"ip_allowlist": "JSON"`).
- Routers: no new route — `PATCH /api/ws/{ws}` (`WsPatch`) gains `ip_allowlist: list[str] | None`, owner/admin only; `GET /api/ws/{ws}` returns the list and the caller's `ip`. Both are refused 400 with the sentence above when the caller's own address is outside the saved list.
- Services/jobs: `app/services/netrules.py` (new) — `MAX_RANGES = 32`, `parse(ranges) -> list[IPv4Network | IPv6Network]` (accepts a bare address as a `/32`, rejects a malformed entry by naming it), `allows(networks, ip) -> bool` (unparseable caller address is refused, never allowed), `describe(networks) -> str` for the audit row. `app/deps.py::_workspace_ctx` takes `request: Request` and raises the 403 body above before any role resolution; `image_ctx` reads the same helper so the image routes are covered.
- Permissions + workspace isolation: the check runs before `Member` lookup — a non-member is still 403 `"not a member of this workspace"`, so the address rule cannot be used to enumerate memberships; a foreign slug is 404 as today.
- Secrets/safefetch: none — no URL is fetched and no credential is stored; `client_ip()` (already proxy-header aware) is the only input.
- OpenAPI: yes — `WsPatch`, the workspace payload and the 403 body shape.

## Tests to write first
pytest — `apps/backend/tests/test_ip_allowlist.py`:
- `test_an_address_inside_a_range_is_allowed` — allowlist `["10.0.0.0/8"]`, request from `10.1.2.3` → 200 and the member's own page loads.
- `test_an_address_outside_the_ranges_is_403_with_the_rule_and_the_ip` — request from `203.0.113.9` → 403, `code == "ip_not_allowed"`, `ip == "203.0.113.9"`, `rule.ranges` lists exactly what was saved.
- `test_an_empty_list_allows_everything` — `[]` and `null` both let the same request through, so an existing workspace is unchanged.
- `test_saving_a_list_that_excludes_the_caller_is_400` — `PATCH` with `["172.16.0.0/12"]` from `10.1.2.3` is 400 whose detail contains `lock yourself out`.
- `test_a_malformed_range_is_400_naming_the_entry` — `["10.0.0.999"]` is 400 and the detail contains that string; 33 entries is 400.
- `test_an_ipv6_range_works` — `["2001:db8::/32"]` allows `2001:db8::1` and refuses `10.0.0.1`.
- `test_flag_off_ignores_the_stored_list` — with the flag off a stored restrictive list does not block, and the `PATCH` is 400.

## Acceptance criteria
- [ ] A workspace stores up to 32 CIDR ranges; an empty list changes nothing for anyone.
- [ ] A request from outside every range is 403, names the caller's address and the ranges, and changes no data.
- [ ] Saving a list that excludes the caller's own address is refused before the write.
- [ ] Empty, loading and error states above all render: the empty list reads "every address is allowed" in T-743, the malformed-entry error names the entry, and the blocked screen shows the address.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no address is ever refused and the stored list is ignored.

## Notes for the implementer
`request.client.host` is already the real peer because uvicorn runs with `--proxy-headers` behind Caddy; do not read `X-Forwarded-For` directly, or a header any caller can set becomes the allowlist bypass. The check sits in `_workspace_ctx` (not middleware) because only a workspace can own ranges, and it must run before the membership lookup so the answer cannot be used to test whether an account belongs to a tenant. The "request access" button in the blocked view is a client-side mailto built from the owner's address in the 403 body — do not add an unauthenticated route for it.
