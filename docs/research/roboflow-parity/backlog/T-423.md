## User story
As an IT admin, I want to prove I control our email domain and store the IdP settings in one place, so that SSO
setup needs no support ticket.

## UX flow (LabelDesk words)
1. No screen in this card. It defines what the tab and the sign-in page read: a domain with a status
   (`pending` → `verified` / `failed`), a TXT record name and value, and one IdP configuration per workspace.
2. Several domains are allowed; the first verified one is the default for sign-in lookup.
3. `[empty]` no rows → the workspace has SSO switched off and every sign-in path is unchanged.
4. `[error]` a config write for a workspace with no verified domain is refused (`409 verify a domain first`).

## Backend changes
- Models/schema: new `app/models/sso.py` (new):
  `SsoDomain(id, workspace_id FK CASCADE, domain VARCHAR(255), status VARCHAR(12) default "pending",
  token VARCHAR(64) unique, last_checked FLOAT null, created)` with `UniqueConstraint(workspace_id, domain)`;
  `SsoConfig(workspace_id PK FK CASCADE, enabled BOOLEAN default false, provider_kind VARCHAR(24),
  issuer VARCHAR(512), client_id VARCHAR(255), client_secret TEXT, verified_at FLOAT null, updated FLOAT)`.
  Register in `models/__init__.py`.
- Routers: none in this card.
- Services/jobs: `app/services/sso.py` (new) — `TXT_PREFIX = "labeldesk-sso-verification="`,
  `new_domain(db, ws, domain) -> SsoDomain` (token = `secrets.token_urlsafe(24)`, lower-cased domain, rejects a
  public-mail domain list), `record_name(domain) -> str` (`_labeldesk-sso.<domain>`),
  `record_value(domain_row) -> str`, `status_of(db, row) -> str`, `set_config(db, ws, values) -> SsoConfig`
  (encrypts `client_secret` with `secretbox`, refuses without a verified domain), `active(db, ws) -> bool`,
  `by_email(db, email) -> SsoConfig | None` (exact domain match, verified only, enabled only).
- Permissions + workspace isolation: every function takes the workspace; `by_email` runs before a session exists, so
  it reads only `SsoDomain`/`SsoConfig` and never a member row.
- Secrets/safefetch: `client_secret` through `services/secretbox.py`; the DNS check is a resolver call, not an HTTP
  fetch, so `safefetch` is not used.
- OpenAPI: no (no route).

## Tests to write first
pytest — `apps/backend/tests/test_sso_model.py`:
- `test_new_domain_starts_pending_with_a_token` — status `pending`, token 32 chars.
- `test_domain_is_normalised_and_unique_per_workspace` — `Example.COM` and `example.com` collide; another workspace may reuse it.
- `test_public_mail_domains_are_refused` — `gmail.com` → `ValueError`.
- `test_config_requires_a_verified_domain` — pending only → `ValueError`; verified → stored.
- `test_client_secret_is_encrypted` — the column starts with `enc:v1:` and `decrypt` round-trips.
- `test_by_email_matches_only_verified_enabled_domains` — pending, disabled and a lookalike domain all miss.
- `test_flag_off_returns_no_config` — `by_email` is `None` and writes are refused.

## Acceptance criteria
- [ ] Multiple domains per workspace, each with a status and a stable TXT token.
- [ ] An IdP config can only be written once a domain is verified, and its secret is encrypted at rest.
- [ ] Email → config lookup matches only verified, enabled domains and never another workspace's.
- [ ] Empty, loading and error states above all render (no config, pending domain, refusal).
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no SSO resolution on any sign-in path.

## Notes for the implementer
The TXT record name is fixed (`_labeldesk-sso.<domain>`) so support can dictate it; the value carries the token. Do not
store a client secret in plaintext even temporarily — encrypt on write, in the same transaction.
