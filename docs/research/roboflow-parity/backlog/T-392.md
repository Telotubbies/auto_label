## User story
As an admin, I want to see what depends on a key before I roll it, so that rotation is one step instead of an
outage discovered by a camera gateway.

## UX flow (LabelDesk words)
1. `GET /api/ws/{ws}/keys/{kid}/dependents` → `{items: [{kind, id, name, detail}], complete: bool}`. Kinds this
   product knows: `default` (`This key is the workspace default.`), `folder` (`Scoped to Site A.`),
   `owner` (`Nok is listed as an owner.`), `usage` (`412 metered calls in the last 30 days.`),
   `rotation` (`Due for rotation on 12 Aug 2027.`). `complete: false` when the usage query fails or the key is
   the in-use fallback from a metadata-less row.
2. `POST /api/ws/{ws}/keys/{kid}/roll` `{acknowledge: bool}` → `400 tick the acknowledgement when dependents exist`,
   then 200 `{id, name, prefix, key, rolled_at}` — the new value exactly once, same id, name, scopes, metadata,
   owners, `folder_id` and disabled state.
3. A protected key → `409 This key is protected. Unprotect it before rolling.` The last key may be rolled (unlike
   revoke) because the workspace keeps a working credential throughout.
4. `[error]` a roll that cannot write → `409 The key was not rolled. The old value is still live.`

## Backend changes
- Models/schema: `ApiKey` gains `rolled_at: float | None`; append `"rolled_at": "FLOAT"` to `API_KEYS` in
  `app/schema/identity.py`.
- Routers: `routers/workspaces.py` — the two routes above; both `404` for a foreign id, `403` without
  `workspace.keys`.
- Services/jobs: `services/keys.py` — `dependents(db, ws, key) -> dict` (five queries, no N+1) and
  `roll(db, key) -> tuple[ApiKey, str]` (new secret via `security.new_api_key`, replace `hash`+`prefix`, keep
  every other field, set `rolled_at`, audit `apikey.roll` with `{dependents: n}`).
- Permissions + workspace isolation: `workspace.keys`; the probe only reads rows filtered by `c.ws.id`.
- Secrets/safefetch: the new secret is returned once and stored only as a hash — `services/secretbox.py` is not
  involved because an API key is hashed, never encrypted.
- OpenAPI: yes.

## Frontend changes
- API client: `keysApi.dependents(ws, kid)` and `keysApi.roll(ws, kid, acknowledge)` in `src/lib/api/keys.ts`.
- Feature flag: `task_key_roll`; off ⇒ neither route exists.

## Acceptance criteria
- [ ] The probe answers what this product knows, and says `complete: false` rather than guessing.
- [ ] A roll preserves id, name, scopes, metadata, owners, folder and disabled state, and returns the new value once.
- [ ] A protected key cannot be rolled; a failed write leaves the old value live and says so.
- [ ] Empty, loading and error states above all render (no dependents, incomplete probe, 409).
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no probe, no roll, today's behaviour.

## Notes for the implementer
Rolling the workspace's only key is allowed on purpose: there is no window in which the workspace has no
credential. Do not stub a dependency kind the product cannot detect — the docs' "deployments migrate" case does
not exist here, so leave it out rather than returning a permanent empty row.
