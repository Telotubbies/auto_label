## User story
As an ML engineer wiring CI, I want to import a pipeline file, run a profile, and wait for the result
from one command, so that a pull request can prove the pipeline still runs.

## UX flow (LabelDesk words)
1. **Terminal** — `labeldesk pipeline run pipelines/qa.yaml --profile ci --wait` imports-or-updates,
   starts a run and prints a step table that updates in place: `3/6 step  done  1.2s`. [empty: the file
   has no steps — "nothing to run", exit 2] [loading: one line per step, `queued → running → done`]
   [error: the failing step, its sanitised message and the run URL, exit 1].
2. **`labeldesk pipeline status <run>`** — the same table for a run started in the browser.
3. **`--json`** — one object per line (`{step, status, ms}`) so a CI log is greppable.
4. **Non-interactive default** — without `--wait` the command prints the run id and exits 0, so a
   pipeline can be fanned out.

## Backend changes
- Models/schema: none.
- Routers: none new — the CLI calls `POST /workflows/import` (T-973), `POST /workflows/{id}/run`
  (T-974) and the existing job read (`routers/devapi.py:111-120`). One addition: `GET
  /api/v1/workflows/{id}/runs/{run_id}` returning `{status, steps: [{index, status, ms}]}` so the CLI
  does not parse the job's internal `result` blob.
- Services/jobs: `packages/sdk/labeldesk/client.py` gains `import_pipeline`, `run_pipeline`,
  `pipeline_status`; `packages/sdk/labeldesk/cli.py` gains the `pipeline` sub-commands and a
  `_render_steps(table, done)` printer.
- Permissions + workspace isolation: the key's existing scopes (`read` for status, `train` for run);
  a cross-workspace run id is a 404 from the route that already enforces it.
- Secrets/safefetch: none.
- OpenAPI: yes (the run-status route).
