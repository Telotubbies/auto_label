## User story
As an admin, I want to restore several things at once without breaking a parent, and to delete for good only from
the app, so that a script can never destroy data.

## UX flow (LabelDesk words)

*Screen this contract serves:* Settings → **Trash** (the screen is T-407's card). States it must show: an empty
trash → "Nothing in the trash · Deleted projects stay here for 30 days"; loading → five row skeletons; a partial
restore → "Restored 3 · 1 needs its project first" with the skipped row still selected; a row whose project is in
the trash → `Restore the project first` instead of a checkbox.

1. `GET /api/ws/{ws}/trash` → `{items: [{type, id, name, deleted_at, deleted_by: {id, name} | null, days_left,
   parent: {type, id, name} | null, shared_images_only: bool}], counts: {project, version, run, workflow}}`,
   oldest first inside each type.
2. `POST /api/ws/{ws}/trash/restore` `{items: [{type, id}]}` → 200 `{restored: n, skipped: [{type, id, reason}]}`.
   `409` with `Restore the parent project first.` when a version or run's project is still in the trash; one bad
   item does not abort the batch.
3. `DELETE /api/ws/{ws}/trash/{type}/{id}` → permanent; `409` when the id is not in the trash; **403 for any
   API-key call** (`Permanent deletion is only available in the app.`) so the SDK and CLI cannot reach it.
4. `POST /api/ws/{ws}/trash/empty` `{types?: [...]}` → purges every matching row oldest-first, returns
   `{purged: n, failed: [{type, id, reason}]}`.
5. Retention: the 30-day window is enforced by the same worker tick that runs retention; a row past 30 days is
   purged automatically and audited as `trash.expire`. Storage stays charged until the purge (existing
   `metering.adjust` refund on purge), never at delete time.
6. `[error]` a purge whose files cannot be removed keeps the row and reports `Some files could not be deleted;
   retry.` — the DB row is not dropped on a partial file delete.

## Backend changes
- Models/schema: none (T-405).
- Routers: `routers/workspaces.py` — a `trash` router block gains `GET /trash` (rewritten payload),
  `POST /trash/restore`, `POST /trash/empty`, `DELETE /trash/{type}/{id}`; the existing
  `POST /trash/{pid}/restore` and `DELETE /trash/{pid}` stay as project-only aliases for one release.
- Services/jobs: `services/trash.py` gains `list_items(db, ws)`, `restore(db, ws, items) -> dict`,
  `purge(db, ws, type, id) -> None`, `empty(db, ws, types) -> dict`, `expire(db, now) -> int`. `purge` reuses
  `services/erasure.delete_project_data` for a project, `delete_version_data` for a version,
  `delete_model_files` for a run, and cancels work: an in-flight training job for a purged run is cancelled and
  `stop_streams` runs for a purged project (the existing purge already does this).
- Permissions + workspace isolation: `workspace.trash` for reads and restore; permanent delete additionally
  requires a user session (`c.user is not None`); `type`/`id` resolve inside `c.ws.id` only, so a foreign id is a 404.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Acceptance criteria
- [ ] A version or run cannot be restored before its project; the refusal names the parent.
- [ ] Batch restore and empty report per-item outcomes instead of failing the whole call.
- [ ] Permanent deletion is impossible with an API key; the app path works and audits `trash.purge`.
- [ ] Storage stays charged until purge, then is refunded by the existing metered amount.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Empty, loading and error states above all render.
- [ ] Flag off ⇒ today's project-only trash routes, unchanged.

## Notes for the implementer
The "web app only" rule is enforced by refusing key auth, not by a hidden button — that is what stops the SDK and
CLI. Reuse the existing erase helpers; do not write a second file walker.
