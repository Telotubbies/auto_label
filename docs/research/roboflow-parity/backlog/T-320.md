## User story
As a workflow author, I want each block to declare the ports it reads and writes, so that the editor can wire a non-linear pipeline and the server can refuse a graph that cannot run.

## UX flow (LabelDesk words)
1. **Save a workflow** — `PUT /workflows/{id}` accepts a definition carrying `nodes` and `edges` (see the schema below) and answers with the canonical form: every node gets `id`, `type`, `disabled: false` and its declared `ports.in` / `ports.out`.
2. **A refused graph** — `[error]` the 400 names the block: "block 3 (Crop): input `detections` is not produced by any earlier block", or "block 4: two blocks write `detections`". The editor highlights that node (T-322).
3. **An old workflow** — a row saved before this card (linear `blocks`) still opens, lists and runs: `T-321` converts it on read. No owner action, no migration message.
4. **A block type with no ports yet** — `[empty]` the block catalogue shows the type with "Not wired" and saving it is refused with the same 400 shape.

## Backend changes
- Models/schema: `workflows` gains `manifest_version INTEGER NOT NULL DEFAULT 1` and `graph JSON` (nullable) — the `ADD COLUMN` block goes at the end of `app/schema/dataset.py`, registered by the existing `schema.apply`. `blocks` stays the source of truth for a v1 row; a v2 save writes both `graph` and the linear `blocks` it implies, so the runner and every old reader keep working.
- Routers: `apps/backend/app/routers/workflows.py` — `PUT /{workflow_id}` accepts `{name?, blocks?, graph?}`; when `graph` is present it wins and `blocks` is derived; `GET` returns `manifest_version` and `graph`.
- Services/jobs: `apps/backend/app/services/workflow_graph.py` (new) — `PORTS: dict[str, {"in": tuple[str, ...], "out": tuple[str, ...]}]` for the eleven block types (model, filter, crop, ocr, rule, sink, replace, inner, branch, cache, outputs), `normalise(graph) -> dict` adding ids and default `disabled`, `toposort(graph) -> list[str]` refusing a cycle, `validate(graph) -> None` raising `ValueError("block N …")`, `to_blocks(graph, order) -> list[dict]` and `from_blocks(blocks) -> dict` for the v1 bridge. `services/workflows.py` routes `validate` instead of `validate_blocks` when `manifest_version == 2`.
- Permissions + workspace isolation: unchanged (`project.models` for writes, `project_ctx`).
- Secrets/safefetch: none.
- OpenAPI: yes — the request/response schema grows `graph` and `manifest_version`.

## Acceptance criteria
- [ ] Every accepted block type declares `in` and `out` ports, and a type without a declaration cannot be saved.
- [ ] A cycle, a missing producer and a duplicated producer are each refused with a block-numbered 400.
- [ ] A v1 row (linear `blocks`, no `graph`) still lists, opens and runs, and saving it without a graph keeps it at `manifest_version: 1`.
- [ ] A v2 save writes `graph` and the derived `blocks`, so `workflow_runner` needs no change.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ `task_31` off still hides every workflow route.

## Notes for the implementer
The v2 shape is `{"nodes": [{"id", "type", "disabled", "config", "ports": {"in", "out"}}], "edges": [{"from": "<node>:<port>", "to": "<node>:<port>"}]}`. `to_blocks` must emit blocks in topological order with the sink last, because `workflow_runner.run` still validates that order — do not teach the runner about edges in this card.
