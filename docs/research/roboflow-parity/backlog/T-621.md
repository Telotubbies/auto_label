## User story
As a reviewer, I want a rejection to land back on the stage that should rework it and every move to be recorded, so that work does not bounce between two people who both think the other one has it.

## UX flow (LabelDesk words)
The canvas is T-622; this card owns moving, rejecting and rerouting.
1. **`POST /stages/move {ids, to_key}`** — one row per image with the actor, the from-key and the to-key; a labeler may only move their own image along its declared `next_key`. [error: "That stage is not the next step for these images." (422)]
2. **Reject** — `POST /stages/move {ids, to_key: <reject target>}` from a review stage writes the stage's `reject_key`, clears `review`, and returns the images to `annotating` on that stage. [error: "This stage has no rejection target — set one in Label path." (409)]
3. **Reroute after publish** — `POST /stages/reroute {apply_to_open: true}` moves every open image whose stage is absent from the new graph to the entry stage; `[loading: rerouting]` and a counted result `{moved, unchanged}`.
4. **History** — every move appends one `StageMove` row, which is what T-633's time-in-stage reads.
5. **A move nobody can perform** — a stage with no `assignee_role` is refused at save time by T-620, so a move target always has a role that can act.

## Backend changes
- Models/schema: `app/models/stages.py` gains `StageMove` (`id`, `workspace_id`, `project_id`, `image_id` FK CASCADE, `user_id` FK SET NULL, `from_key`, `to_key`, `reason` String(120) default `''`, `created`), `Index("ix_stage_moves_project_image_created", "project_id", "image_id", "created")`; table creation via `create_all`, no `ADD COLUMN` block.
- Routers: `routers/stages.py` — `POST "/move"` `{ids, to_key, reason?}` → `{moved, skipped}`; `POST "/reroute"` `{apply_to_open: bool}` → `{moved, unchanged}`. 404 for an image outside this project, 422 for a `to_key` absent from the graph or a labeler stepping off the declared next stage, 409 for a rejection with no target or a reroute over 2000 open images.
- Services/jobs: `app/services/stages.py` — `move(db, c, images, to_key, reason)` (validates against `read(project)`; writes `Image.stage`, `Image.status` and one `StageMove` row per image; keeps `review` consistent), `reject_target(graph, from_key)`, `reroute(db, c, graph)`. No job kind: the reroute is one bounded update.
- Permissions + workspace isolation: `c.need("reviewer")` for any move that is not a labeler's own forward step; a labeler moving an image that is not theirs is 403, and every id is re-checked against `c.project.id` (404 otherwise) before the first write, so a mixed batch writes nothing.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Acceptance criteria
- [ ] A rejection lands on the stage's configured target, clears the review verdict and returns the image to annotating.
- [ ] Every move writes exactly one `StageMove` row with actor, from and to, which the time report can read.
- [ ] A batch containing a foreign or unknown id changes nothing at all.
- [ ] Empty, loading and error states above all render where the surface exists: 422 for the wrong next step, 409 for a missing reject target, 404 for a foreign id.
- [ ] Workspace A cannot move workspace B's images (404, not 403).
- [ ] Flag off ⇒ no move routes and status changes keep working through `PATCH /api/images/{id}`.

## Notes for the implementer
Validate the whole batch before the first write, exactly as `merge_job` does with class ids — a partial move is how an image ends up in a stage that no longer exists. Keep `status` and `stage` consistent: a stage of kind `review` implies `status == "review"`, and leaving it implies `status == "annotating"`.
