## User story
As a workspace admin, I want the members page to show how many seats are spent, who is in, who is still
waiting and what I can do to each person, so that one screen answers "can I invite another person".

## UX flow (LabelDesk words)
1. **Settings → Members** (`/:ws/settings/members`) — the roster card header reads
   `Seats · 3 of 5 used · 1 invitation pending`. [loading: five skeleton rows matching the table geometry]
   [error: `Could not load the roster.` + `Try again`; the invite block stays usable]
2. **Each row** — circular avatar with the person's initials (no image upload in this card), name, email,
   role chip, `Joined 4 Mar 2026`, and a `⋯` button.
3. **The `⋯` menu** — `Change role`, `Remove from workspace`; on the caller's own row it reads `Leave workspace`
   and no role item. Items the role cannot use are dimmed with a lock and `Request access` (v3 rule), not hidden.
4. **`[empty]`** — one member only: `Only you so far.` with `Invite teammates` as the single filled control.
5. **Seat cap** — when `used + pending >= limit` the header line turns to the warning tone and reads
   `5 of 5 seats used — remove a member or change the plan before inviting.`

## Backend changes
- Models/schema: none — `Member`, `Invite`, `Workspace` and `PLANS[...]["seats"]` exist.
- Routers: `GET /api/ws/{ws}/members` (in `routers/workspaces.py`) gains
  `"seats": {"used": int, "pending": int, "limit": int, "remaining": int}` computed from `Member` count,
  pending `Invite` count and `plan(ws)["seats"]`; each member row gains `"initials": str` (2 chars, derived
  from `User.name`, falling back to `User.email[0]`). Status 200; 404 when the slug is not a workspace the
  caller belongs to (already raised by `ws_ctx`).
- Services/jobs: `seat_state(db, ws) -> dict` in `routers/workspaces.py` beside the existing `usage()`, so the
  invite route reuses one seat calculation instead of a second query.
- Permissions + workspace isolation: roster readable with `workspace.read`; `invites` stay admin-only
  (`workspace.members`) as today; every query filters `Member.workspace_id == c.ws.id`.
- Secrets/safefetch: none.
- OpenAPI: yes — the response schema changes.

## Frontend changes

  existing table renders unchanged.

## Tests to write first
pytest — `apps/backend/tests/test_member_seats.py`:
- `test_seats_count_members_and_pending_invites` — 2 members + 1 invite on a 3-seat plan → `used=2, pending=1, remaining=0`.
- `test_invites_are_hidden_from_a_member` — a `member`-role caller gets an empty `invites` list and still sees `seats`.
- `test_seats_are_per_workspace` — two workspaces with different member counts report their own numbers.
- `test_foreign_workspace_slug_is_404` — workspace B's slug with A's token → 404.
- `test_flag_off_leaves_the_payload_usable` — flag off → the route still answers and the extra fields are additive only.

node — `apps/frontend/tests/member-roster.test.mjs`:
- `test_seat_line_wording_and_tone` — `3 of 5 used`, `1 invitation pending`, plural handling, and the cap tone at 0 remaining.
- `test_avatar_initials_fall_back_to_email` — name with two words → `PS`; single-word name → first letter of the email.

## Acceptance criteria
- [ ] The roster header states seats used, seats allowed and pending invitations from one API call.
- [ ] Every row offers `⋯` with the actions the caller's role allows; the own row offers `Leave workspace` instead.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ the old roster table renders and no menu, avatar or seat line appears.
- [ ] The seat sentence and the invite route agree on the same number (one helper, one query).
