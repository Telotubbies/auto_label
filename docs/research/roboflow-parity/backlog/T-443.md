## User story
As an owner, I want to close a client workspace and know exactly what is destroyed, so that leaving the product does not
needs a support ticket.

## UX flow (LabelDesk words)

*Screen this contract serves:* Settings → **Workspace → Delete workspace** (the dialog is T-444's card). States it
must show: the typed-slug confirm with the destructive button disabled until it matches; a non-owner → the action
absent, with the reason in the section text; a workspace mid-deletion → a banner "This workspace is being deleted"
and every action disabled; a completed purge → the signed-out page with "This workspace no longer exists".

1. `DELETE /api/ws/{ws}` `{confirm_slug}` → `202 {job_id}`; the purge runs as a job and the workspace becomes
   `status="deleting"`, answering `423 This workspace is being deleted.` to every other route.
2. `409` when: the caller's default workspace (`Your default workspace cannot be deleted.`), the caller is not the owner,
   or members still hold data (`Transfer or remove the other members first.` — owners and admins may stay).
3. `403` by policy: a workspace on the enterprise plan (`Enterprise workspaces are deleted by support.`).
4. The job purges projects, versions, models, streams, keys, webhooks, alerts, connectors and the files they own, then
   removes the workspace row; every step is audited and the last audit row carries the outcome.
5. `[error]` a file that cannot be erased stops the job with `Some files could not be deleted; retry.` and keeps the
   workspace in `deleting`, so a second call resumes instead of losing track.

## Backend changes
- Models/schema: `Workspace.status VARCHAR(16) DEFAULT 'active'` (`active|deleting`); `ADD COLUMN` addition to
  `WORKSPACES` in `app/schema/identity.py`.
- Routers: `routers/workspaces.py` — `DELETE /api/ws/{ws}` with the guards; every other workspace route (via `ws_ctx`)
  answers 423 while `status == "deleting"`.
- Services/jobs: `app/services/workspace_delete.py` (new) — `start(db, ws, actor) -> Job` (queues `kind="ws_delete"`),
  `run(job)` (iterates the workspace's projects through `erasure.delete_project_data`, deletes models/streams/versions by
  cascade, deletes connectors/webhooks/alerts/keys, then the workspace row; returns `{projects, files, freed}`),
  `resume(db, ws)`; `deps._workspace_ctx` gains one `status` check.
- Permissions + workspace isolation: `workspace.delete` (owner only) and `workspace.delete` is in `CUSTOM_DENIED`, so no
  custom role can carry it.
- Secrets/safefetch: none — hashed keys and encrypted secrets die with their rows.
- OpenAPI: yes.

## Acceptance criteria
- [ ] An owner can delete a non-default workspace with an exact-slug confirm, and it becomes unusable immediately.
- [ ] The default workspace, a non-owner and an enterprise workspace are each refused with their own sentence.
- [ ] The purge removes rows and files and resumes after a partial file failure.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no route and no danger-zone card.

## Notes for the implementer
Reuse `erasure.delete_project_data` per project — do not write a second deletion order. `status="deleting"` is what stops
a half-deleted tenant from serving requests while the job runs.
