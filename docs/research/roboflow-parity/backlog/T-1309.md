# T-1309 — Rate limits for every route class

| Field | Value |
| --- | --- |
| Wave | O (security, monitoring, performance) |
| Area | Security |
| Size | 2 agent-hours |
| Role | R3 backend |
| Skills | ponytail, test-driven-development, verification-before-completion |
| R7 security review | yes — a wrong limit is an outage or a free-for-all |
| Depends on | T-1300 (429 lines carry a request id), T-1308 (headers, so the 429 body is consistent) |
| Feature flag | `LD_RATE_LIMIT=0` remains the global off switch |

## Problem
18 `limit()` calls exist, all on auth, comments and one VLM route (`routers/auth.py:162-411`,
`images.py:634,672`, `apikeys.py:81`). Uploads, `/predict`, exports, version creation, bulk moves,
search and MCP tool calls have no per-caller ceiling, and there is no global per-IP or per-user
ceiling. One authenticated client can fill the data volume, occupy the GPU or burn credits.

## Design
- `app/ratelimit.py` gains `ROUTE_LIMITS`, an ordered tuple of `(prefix, limit, window_s, who)` where
  `who ∈ {"ip", "user", "key"}`, and `classify(request)` returning the matching rule or `None`.
- One middleware in `app/main.py` applies it **after** identity resolution is available:
  - `who="ip"` for anonymous requests,
  - `who="user"` when a session cookie/`Authorization` resolved a user (the deps layer stamps
    `request.state.user_id`),
  - `who="key"` for `/api/v1/*` (the existing 600/60 key limit stays authoritative there; the
    middleware skips `/api/v1` to avoid double counting).
- Limits (the monitoring plan's table, one source of truth in this file):

  | Class | Rule |
  | --- | --- |
  | anonymous, any `/api/*` | `ip` 120 / 60 s |
  | authenticated, any `/api/*` | `user` 600 / 60 s |
  | `POST …/upload` | `user` 30 / 60 s |
  | `POST …/predict`, `/api/v1/models/*/predict` | `user`/`key` 120 / 60 s |
  | `POST …/versions`, `…/export`, `…/train`, `…/autolabel` | `user` 10 / 60 s |
  | `POST …/board/move`, `…/images/bulk` | `user` 60 / 60 s |
  | `GET …/search`, `…/event-search` | `user` 120 / 60 s |
  | `POST /mcp` | `key` 120 / 60 s |
- 429 body is the existing message with `Retry-After`; the log line is `rate_limit.exceeded` with the
  class name (not the raw path) so the dashboard can show which class trips.
- `LD_RATE_LIMIT=0` still disables everything, including the middleware.

## Tests to write first
`apps/backend/tests/test_sec_ratelimit.py`:
- `test_anonymous_limit_is_per_ip` — 120 pass, 121st is 429 with `Retry-After`.
- `test_authenticated_limit_is_per_user` — two users do not consume each other's budget.
- `test_upload_limit_is_30_per_minute` — 31st upload is 429 and no file lands on disk.
- `test_export_and_version_limit_is_10` — a loop of 11 enqueues leaves exactly 10 jobs.
- `test_predict_limit_applies_to_the_devapi_key_path`.
- `test_mcp_tool_calls_are_limited_per_key` — 121st `tools/call` is 429 as a JSON-RPC error.
- `test_ld_rate_limit_zero_disables_every_class` — the same loops all pass.
- `test_429_line_names_the_class_not_the_path` — captured log has `upload`, not `img-123`.
- `test_window_slides` — with a shrunk window, the budget refills.

## Acceptance criteria
- [ ] Every class in the table has a test and a 429.
- [ ] Limits key on ip / user / key as documented; no class counts twice.
- [ ] `/api/v1` keeps its single 600/60 key limit (no double counting with the new middleware).
- [ ] A 429 carries `Retry-After` and a request id, and writes no partial side effect (no file, no job).
- [ ] `LD_RATE_LIMIT=0` disables all classes and is covered by a test.
- [ ] The in-memory store still bounds itself (`_hits` pruning path exercised).

## Notes for the implementer
Reuse `limit()`; do not add `slowapi`. Read the class from the prefix list top-down so the specific
upload rule wins over the generic authenticated rule. Announcing this to the owner matters: a script
that uploads 40 images a minute will now see 429s, which is the point but must be in the report.
