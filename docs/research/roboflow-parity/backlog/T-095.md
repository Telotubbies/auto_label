## User story
As a workspace admin, I want a restricted folder whose projects disappear for everyone not on its list, so
that a client's data is not merely unlisted but unreachable.

## UX flow (LabelDesk words)
1. **Home** — a restricted folder shows a lock; a member without access does not see it at all (no row, no
   count, no search hit). [empty: a workspace where every folder is restricted and the person has none →
   "No projects yet" plus "Request access" pointing at an admin] [loading: the tree resolves from
   `/folders`; no project card renders before it does]
2. **Home** — a member with access only to a deep subfolder sees that subfolder as a top-level row; the
   ancestor names are not shown in the list, breadcrumbs or search. [error: opening an ancestor's URL
   directly → the normal "Project not found" page, not a permission page]
3. **Project** — a project inside a restricted folder behaves exactly as its project role allows; the
   folder role cannot upgrade a project role (it only grants visibility).
4. **Move** — moving a project into or out of a restricted folder needs write on both folders; the refusal
   reads "You need access to both folders to move this project". [error: an admin removing their own last
   access → "Keep at least one manager on this folder"]

## Backend changes
- Models/schema: `FolderAccess(folder_id FK, user_id FK, role String(16), created)` in
  `models/project.py` (composite PK) and `Folder.restricted: bool` default `False`; two `FOLDERS` entries
  in `schema/dataset.py` (`restricted`, plus the new table via `create_all`).
- Routers: `apps/backend/app/routers/workspaces.py`
  - `GET /folders` filters to visible folders and hides ancestors of a deep grant.
  - `PUT /folders/{fid}/access` `{members: [{userId, role}]}` replaces the list (admin only);
    `400` when it would leave a restricted folder with no manager among its own rows and the actor is the
    only one.
  - `POST /folders/{fid}/projects` checks write on both source folder and target.
  - `GET /projects` (in `routers/projects.py`) filters out projects whose folder the caller cannot see.
- Services/jobs: `apps/backend/app/services/folder_access.py` (new) —
  `visible_folder_ids(db, ws, user) -> set[str]` (owner/admin: all; else explicit rows plus their
  descendants; a descendant grant hides ancestors), `can_read(db, ws, project, user) -> bool`,
  `can_write(db, ws, folder, user) -> bool`, `roots_for(db, ws, user) -> list[Folder]` (what the tree shows
  a deep-grant member), `guard_last_manager(db, folder, members) -> None`.
- Permissions + workspace isolation: enforcement lives in `deps.project_ctx` (after the project lookup:
  `if not folder_access.can_read(...): raise HTTPException(404, "project not found")`) and in
  `apikeys.KeyCtx.project` (visibility of the key's `created_by`), so every existing route inherits it. A
  cross-workspace id stays a 404.
- Secrets/safefetch: none.
- OpenAPI: yes — one route, two fields.

## Acceptance criteria
- [ ] A project in a restricted folder is 404 for anyone without a folder grant, on every route that takes a
      project — not only in lists.
- [ ] An ancestor grant reaches descendants; a descendant grant hides its ancestors from the tree, list and
      search.
- [ ] API keys inherit the creating member's visibility.
- [ ] A move needs write on both folders; the last manager cannot be removed.
- [ ] Empty/loading/error states above render (the tree's "no projects" and the direct-URL not-found page).
- [ ] Flag off ⇒ no visibility filtering and today's behaviour is unchanged.
- [ ] Workspace A cannot see or change workspace B's data (404 everywhere, including search and the dev API).

## Notes for the implementer
The guard belongs in `project_ctx` and the API-key context — not in each router — so a new endpoint cannot
forget it. Folder grants never change a project role; they only decide whether the project exists for that
person.
