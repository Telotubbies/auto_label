## User story
As a QA lead, I want to promote a fixed share of each approved batch into the answer key and keep every score a labeler ever made, so that per-labeler accuracy is a trend instead of a week-one snapshot.

## UX flow (LabelDesk words)
The screen is T-613; this card owns the two calls behind it.
1. **`GET /labeling/honeypots/pool?batch_id=`** — returns the stored rate and seed, how many candidates the batch holds and how many would be promoted. [empty: a batch with no approved images returns `candidates: 0` and the screen says "No approved images in this batch yet."]
2. **`POST /labeling/honeypots/pool`** — promotes the deterministic share and returns `{seeded, skipped, ids}`; the same seed and rate over the same batch returns the same ids on a rerun.
3. **A labeler saves a pooled image** — the save is scored, the key is not overwritten, and a new attempt row is appended while the per-labeler "latest score" stays the one row the dashboard reads.
4. **`GET /labeling/honeypots`** — each item now carries `attempts` and a bounded `history` (last five scores, newest first) and each labeler row carries `attempts`. [error: "This batch already has an answer-key pool." when the same batch is seeded twice without change]

## Backend changes
- Models/schema: new `app/models/workforce.py` with `HoneypotAttemptLog` (`id`, `workspace_id`, `project_id`, `honeypot_id` FK CASCADE, `user_id` FK CASCADE, `score` Float, `attempt_no` Integer, `created` Float) and `Index("ix_honeypot_attempt_log_lookup", "project_id", "honeypot_id", "user_id")`; registered in `app/models/__init__.py` (`from . import workforce`, one re-export line, one `DOMAIN_MODULES` entry). `HoneypotAttempt` keeps its unique row and stays the "latest score" read. Table creation comes from `Base.metadata.create_all`; no `ADD COLUMN` block.
- Routers: `routers/labeling.py` — `GET /honeypots/pool` (`batch_id` optional) and `POST /honeypots/pool` `{pct: int, seed: str, batch_id?: str}`; 422 for `pct` outside 1–50 or a seed over 64 chars, 404 for a batch outside this project.
- Services/jobs: `app/services/honeypot_pool.py` (new) — `candidates(db, project_id, batch_id)` (status `done` or `review == approved`, not already a honeypot, at least one annotation), `pick(candidates, pct, seed)` (`hashlib.sha256(seed + image_id)`, sort, take `max(1, round(n * pct / 100))`), `apply(db, c, ...)` reusing `labeling_ops.create_honeypot` so assignment and audit stay in one place; `labeling_ops.log_attempt(db, ws_id, honeypot, user_id, score)` is the one write used by both `record_save` and T-614's score route (it appends the `HoneypotAttemptLog` row with the next `attempt_no` and upserts the latest `HoneypotAttempt`); `labeling_ops.honeypots_out` gains `attempts`/`history` per item and `attempts` per labeler.
- Permissions + workspace isolation: `c.need("reviewer")` on both pool routes; candidates are filtered by `c.project.id`, so a batch id from another project or workspace is a 404 and contributes nothing.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Acceptance criteria
- [ ] A reviewer promotes a chosen percentage of an approved batch and rerunning the same seed yields the identical set.
- [ ] A labeler's second look at the same answer-key image adds an attempt row instead of replacing the first score.
- [ ] The honeypot list and the labeler table expose attempt counts and the last five scores.
- [ ] Empty, loading and error states above all render where they exist: `candidates: 0` for a batch with nothing approved, and 404/422 for a foreign batch or a bad rate.
- [ ] Workspace A cannot read or seed workspace B's pool (404, not 403).
- [ ] Flag off ⇒ no pool routes, no new attempt rows, and the existing single-image honeypot flow is unchanged.

## Notes for the implementer
Only images a reviewer already approved (`status == "done"` or `review == "approved"`) may become an answer key: promoting a labeler's own draft would grade them against their own work. Keep `HoneypotAttempt` as the latest-score row — the workforce dashboard reads it in three places — and treat the new table as history only, never as the source of the average.
