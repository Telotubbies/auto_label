## User story
As an admin, I want a rotation date per key with one reminder and a visible ladder, so that old credentials get
replaced on a rhythm instead of after an incident.

## UX flow (LabelDesk words)
1. **Create / edit key → `Rotation due`** — a date field, `Suggest one year` (fills today + 12 months) and
   `Clear` (stops reminders). The hint reads `Advisory only — nothing stops working on this date.`
2. **Table badges** — `Rotate by 12 Aug 2027` always; from 30 days out the row shows `Due in 22 days`, on the day
   `Due today`, after it `Overdue`. A key with no date shows `No rotation date` and is excluded by the due filter.
3. **One email per recipient per date** — sent on one day inside the window 15 days before the due date through
   the due day, only while the key is enabled and not protected-blocked; body names the key, the workspace and the
   due date with a link to Settings → API keys. `Roll` moves the date forward by the same interval, capped at 12 months.
4. `[empty]` every key has a date → the filter line reads `Every key has a rotation date.`
5. `[error]` a date in the past is accepted (it renders `Overdue`) but `Suggest one year` never proposes one.

## Backend changes
- Models/schema: `ApiKey.rotation_due` ships in T-388. One new table is avoided: reminders are deduplicated by a
  `Audit` row (`apikey.rotation_reminded`) instead of a new column.
- Routers: `PATCH /api/ws/{ws}/keys/{kid}` accepts `rotation_due` (epoch seconds or null);
  `GET /api/ws/{ws}/keys?due=1` filters to rows due within 30 days.
- Services/jobs: `services/key_rotation.py` (new) — `next_reminder(key, now) -> float | None`,
  `queue_reminders(db, now) -> int` (called from the existing worker tick beside `retention.enqueue_if_due`),
  `advance_after_roll(key)`; mails go through `mailer.send(...)` to `owner_ids` or, when empty, every member
  holding `workspace.keys`.
- Permissions + workspace isolation: `workspace.keys`; the job iterates workspaces and never mixes their mail.
- Secrets/safefetch: none — the mail contains the key name and prefix only.
- OpenAPI: yes.

## Frontend changes
- Route: `/:ws/settings/api` (existing).
- Components: `features/settings/keys/RotationField.tsx` (new) — date, `Suggest one year`, `Clear`; badges land in
  `keyBadges.ts` (T-389) so the ladder is one pure function.
- API client: `keysApi.list(ws, {due})` and `keysApi.patch` field.
- Feature flag: `task_key_rotation`; off ⇒ no date field, no badges, no job, no mail.

## Acceptance criteria
- [ ] A key can carry a due date, and rolling advances it by the same interval capped at one year.
- [ ] Exactly one reminder per recipient per due date, only inside the 15-day window and only for enabled keys.
- [ ] The table's due ladder and the due filter agree on the 30-day boundary.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no date, no badges, no mail.

## Notes for the implementer
Deduplicate with an audit row keyed by key id and date (`meta={"date": "2027-08-12"}`) — no new table, and the
reminder is visible in the audit log for free. Mail is one per recipient, not one per owner list.
