## User story
As a workspace admin, I want one screen that says where each of a member's permissions comes from, so
that "why can Dana export?" is a lookup instead of reading the resolver source.

## UX flow (LabelDesk words)
1. **Settings → Members → row → "Access"** — a drawer lists every permission for the project scope
   with its source: workspace role, project role, custom bundle, or `not granted`. [empty: a member
   with no project row — the drawer says "inherits `member` → labeler in every project"] [loading: one
   fetch, skeleton rows] [error: the resolver disagrees with the roster — "this changed while you were
   looking, reload" rather than a stale answer].
2. **Change with a preview** — picking a different project role shows the permission set as
   `removed` / `added` before Apply; Apply sends one PATCH and re-reads. [error: 403 → the drawer stays
   read-only and says "you cannot change roles in this project"].
3. **Copy** — "copy as text" yields a plain-English paragraph for a support ticket.

## Backend changes
- Models/schema: none — the answer is computed, never stored.
- Routers: `routers/rbac.py` gains `GET /projects/{project}/members/{uid}/access` returning
  `{workspace_role, project_role, inherited: bool, custom_roles: [{name, level, permissions}],
  permissions: [{name, granted: bool, source: "workspace"|"project"|"custom:workspace"|
  "custom:project"|null}]}`. One shared helper with the existing `_project_permissions`
  (`routers/rbac.py:144-153`) so the drawer and the roster cannot disagree.
- Services/jobs: `app/rbac.py` gains `explain(ws_role, project_role, ws_custom, project_custom) ->
  dict[str, str | None]` (permission → source) built from the same tables `permissions_for` uses
  (`rbac.py:132-145`); `permissions_for` becomes a thin wrapper over it so there is one code path.
- Permissions + workspace isolation: `project.roles`; the target member must belong to `c.ws.id`
  (`Member` is keyed by `(workspace_id, user_id)`) so a foreign uid is a 404.
- Secrets/safefetch: none.
- OpenAPI: yes.
