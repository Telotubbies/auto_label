## User story
As a team lead whose next labelling week should target what the model cannot do yet, I want each pick to carry a reason, a guaranteed share per class and a stated call budget, so that I can defend the spend and tune the queue instead of accepting a black box.

## UX flow (LabelDesk words)
1. **Active learning** (`/:ws/:project/annotate`, the card T-653 draws; API in `routers/ops.py`) — a run request now carries `k`, a per-class floor, an exploration share and an explain switch. [empty: no unlabelled image ⇒ `selected: 0` with `candidates: 0`] [loading: the summary reports `score_calls_estimate` before the run so the cost is known] [error: "no ready model" with the train link, and 409 "active-learning daily cap reached"]
2. **The batch** — picks land in the existing "Active learning <date>" batch with the tag `active-learning`, and each pick carries `{reason, score, margin, top1, top2}`.
3. **After training** — the same summary reports how many of a past pick batch the new model now gets right, so a queue can be judged.
4. **The cap** — `{used_today, cap, remaining}` unchanged; a cap of zero still means "off".

## Backend changes
- Models/schema: none — `project.settings["active_learning"]` gains `class_floor` (default 3), `explore_pct` (default 10), `explain` (default true); picks are stored in `Job.result["picks"]`, which the row already keeps.
- Routers: `routers/ops.py` — `ActiveRunIn` gains `k`, `class_floor` (0–50), `explore_pct` (0–50), `explain`; `GET /active-learning` returns `picks` from the latest run, `score_calls_estimate`, `cap`, `used_today` and a `history` line per past batch with `corrected` (0 when the model has not been retrained).
- Services/jobs: `services/active_learning.py` — `margin(preds)` (top-1 vs top-2 class confidence, 1.0 with fewer than two classes), `uncertainty` unchanged, `combined = max(band, margin)`, `select(candidates, k, floor, explore_pct, seed)` enforcing the floor per class and the exploration share, `explain(candidate)` returning the reason string, and `_run` reserving `min(CANDIDATE_LIMIT, unlabelled)` `ai_calls` through `metering.check` before scoring.
- Permissions + workspace isolation: `reviewer` to run and to read the summary (existing); the project row is the only scope, so another project's batch id never appears in a response.
- Secrets/safefetch: none.
- OpenAPI: yes — regenerate (`python tools/export_openapi.py`, `npm run gen:api-types`).

## Acceptance criteria
- [ ] Every pick carries a reason, its score and the margin that produced it, and the same inputs produce the same batch.
- [ ] A per-class floor is honoured when a class is rare, and exploration is a stated share rather than a surprise.
- [ ] The call budget is reserved before scoring and reported before the run, so a cap is a number not a truncation.
- [ ] Empty, loading and error states above all render: no ready model, cap reached with its used/limit, and zero candidates.
- [ ] Workspace A cannot see workspace B's picks (the batch and the job are project-scoped).
- [ ] Flag off ⇒ no reasons in the summary and selection behaves exactly as today.

## Notes for the implementer
`margin = 1 - (p1 - p2)` over per-class maximum confidences, and the pick score is `max(band_uncertainty, margin)` — keep both numbers in the reason so the two ideas stay distinguishable. Seed the exploration draw with the job id so a rerun is reproducible. The floor is a minimum per class per run, not a daily quota; `cap` remains the only daily limit.
