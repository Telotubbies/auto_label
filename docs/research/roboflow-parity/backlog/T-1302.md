# T-1302 — `/api/metrics`: request rate, errors and latency percentiles

| Field | Value |
| --- | --- |
| Wave | O (security, monitoring, performance) |
| Area | Monitoring |
| Size | 3 agent-hours |
| Role | R3 backend |
| Skills | ponytail, test-driven-development, verification-before-completion |
| R7 security review | yes — a new scrapeable surface |
| Depends on | T-1300 (route template + middleware seam), T-1301 (`/api/readyz` feeds `labeldesk_db_up`) |
| Feature flag | none; closed unless `LD_METRICS_TOKEN` matches |

## Problem
There is no metrics endpoint: request rate, error rate and latency exist only as log lines (and, before
T-1300, not even those). Without a histogram per route there is no p50/p95/p99 and the monitoring
plan's error-rate alert has no source.

## Design
- Add `prometheus_client` to `apps/backend/requirements.txt` (pure Python, ~1 MB, no C extension).
- `app/metrics.py` (new, ~150 lines):
  - `REGISTRY` + the four HTTP series from the monitoring plan §4.2: `labeldesk_http_requests_total`
    `{method, route, status_class}`, `labeldesk_http_request_duration_seconds{method, route}` with
    buckets `(.005,.01,.025,.05,.1,.15,.25,.5,1,2.5,5,10)`, `labeldesk_http_exceptions_total{route,type}`,
    `labeldesk_http_inflight`, plus `labeldesk_build_info{version}`.
  - `route` is always `request.scope["route"].path` when a route matched, else `"<unmatched>"`, so a
    scanner cannot create unbounded series.
  - `status_class` is `"2xx"…"5xx"`; 401/403 keep their class (that is the signal).
- One middleware records the observation in a `finally`, including the exception path (`500`).
- `GET /api/metrics`: when `LD_METRICS_TOKEN` is empty the route answers **404** (not 403: an unset
  token means "no metrics in this deployment"); when set, requires `Authorization: Bearer <token>`
  and answers the Prometheus text format via `prometheus_client.generate_latest`.
- Caddy never routes `/metrics` (already true: only `/api` is proxied); Prometheus scrapes
  `api:8000` on the Compose network. The in-product alert checker (T-1317) uses the same token.
- `config.py`: `METRICS_TOKEN`, `APP_VERSION` (read from the app module, not a new file).

## Tests to write first
`apps/backend/tests/test_metrics.py`:
- `test_route_label_is_the_template_not_the_path` — hit `/api/ws/abc/projects/img-1/images/xyz`; the
  series carries `/api/ws/{ws}/projects/{slug}/images/{image_id}`.
- `test_unknown_path_becomes_unmatched` — a 404 under `/api/nope/9` creates exactly one
  `<unmatched>` series, and ten different unknown paths do not create ten.
- `test_counts_and_status_classes` — three 200s, one 404, one 401; assert `2xx`, `4xx` counts.
- `test_duration_histogram_has_all_buckets` — `_bucket` samples with `le` labels present.
- `test_exception_increments_the_exception_counter_and_a_5xx` — a route that raises.
- `test_metrics_route_is_404_without_a_token` and `test_metrics_route_is_200_with_the_token`.
- `test_metrics_route_is_401_with_a_wrong_token`.
- `test_scrape_shape` — `generate_latest` parses line by line; no label value contains a workspace id,
  a user id, an email or a filename.
- `test_db_up_reflects_the_readyz_check` — flip the DB check result and assert the gauge.

## Acceptance criteria
- [ ] `GET /api/metrics` with the right bearer token returns a valid Prometheus exposition.
- [ ] No token configured ⇒ 404; wrong token ⇒ 401; body never explains which.
- [ ] Series count stays bounded: no raw path, no workspace/user/email label, `<unmatched>` for 404s.
- [ ] p50/p95/p99 are derivable from the histogram (buckets cover 5 ms – 10 s).
- [ ] `GET /api/metrics` itself is measured but does not recurse into its own scrape.
- [ ] `prometheus_client` is the only new dependency; the API image grows by < 2 MB.

## Notes for the implementer
Keep the registry process-local and do not expose `python_gc_*` and friends unless the process
collector is enabled deliberately — the four HTTP series plus build info are the contract. T-1311 adds
the queue/worker/disk/GPU gauges to the same module; leave a clearly marked section for it rather than
creating a second registry.
