## User story
As a customer's procurement lead, I want a dated list of everyone who can touch our data and a window to object before it changes, so that the DPA clause about prior consent is something I can point at instead of quote.

## UX flow (LabelDesk words)
1. **Public `/subprocessors`** (no login) — a table: name, purpose, data categories, region, safeguard, listed since, and the state chip "Current" or "Announced". The line under the title reads "Every processor that can touch your data, with the date we told you." [empty: "No sub-processors are listed yet." — the page still renders] [loading: four skeleton rows] [error: "Couldn't load the register." + `Try again`]
2. **`Get change notices`** — an email field and one button; after submit the page reads "Check your inbox — the confirmation link completes the subscription." A bad address answers `[error: enter a work email address]` and a repeat subscription reads "This address already gets notices."
3. **In-app banner for an admin** (`/:ws/settings/privacy`) — "1 change needs acknowledgement by 12 Dec" with `Read the change`, `Accept` and `Object`. `Object` opens a textarea for the reason and then reads "Recorded — we will reply to this address." [empty: nothing pending ⇒ the banner is absent, not empty]
4. **An admin edits the register** (`/:ws/admin` is the platform operator's; workspace admins read only) — the operator adds a sub-processor or a change with an effective date; each save writes one audit row.
5. **A workspace with nothing pending** — no banner, and the public page is unchanged for signed-out visitors.

## Backend changes
- Models/schema: `app/models/trust.py` (new) — `Subprocessor(id, name, purpose, data_categories, region, safeguard, since, current, created)`, `SubprocessorChange(id, subprocessor_id, summary, effective_at, created, notice_sent)`, `TrustSubscription(id, email, token, workspace_id nullable, confirmed_at, created)` and `SubprocessorResponse(id, workspace_id, change_id, kind('accept'|'object'), reason, user_id, created)`.
- Routers: `app/routers/trust.py` (new) — `GET /api/public/subprocessors` (no auth: rows plus announced changes), `POST /api/public/subprocessors/subscribe` (202; 422 on a malformed email), `GET /api/public/subprocessors/confirm/{token}`, `GET /api/ws/{ws}/subprocessors/pending` (auth), `POST /api/ws/{ws}/subprocessors/changes/{cid}/respond` (`accept` or `object`, 422 without a reason when objecting), operator-only `POST /api/subprocessors` and `POST /api/subprocessors/{sid}/changes` behind `require_superadmin`.
- Services/jobs: `app/services/trust.py` (new) — `public_register(db)`, `pending_for(db, workspace_id, now)`, `respond(db, c, change_id, kind, reason)`, `subscribe(db, email)` (token from `secrets.token_urlsafe`, confirmation through `mailer.send`), `announce(db, change)` (one audit row; delivery goes through the existing `mailer`).
- Permissions + workspace isolation: the public read needs no session but returns no workspace data at all; `respond` needs `workspace.update`; a change id is global but the response row is stamped with the caller's workspace, and a second workspace's response is invisible to the first (one row per `(workspace_id, change_id)`).
- Secrets/safefetch: none for the register; the subscription token is a random string, stored as given, never a password.
- OpenAPI: yes.

## Tests to write first
pytest — `apps/backend/tests/test_subprocessors.py`:
- `test_the_public_register_needs_no_session` — seed one sub-processor and one announced change → `GET /api/public/subprocessors` without a token returns 200 with the name and the effective date, and no workspace id anywhere in the body.
- `test_an_announced_change_is_not_current` — the same response marks the change `announced` and the sub-processor `current`, so the page can tell them apart.
- `test_subscribing_sends_one_confirmation` — `POST /subscribe` with a valid address → 202 and one entry in the dev mail outbox; the same address again returns 200 with `already: true` and sends nothing.
- `test_a_malformed_address_is_422` — `"nope"` and `"a@b"` → 422.
- `test_accept_and_object_are_recorded_once` — admin `POST …/respond` with `accept`, then again → the second call is idempotent; `object` without a reason → 422.
- `test_a_labeler_cannot_respond` — labeler login → 403.
- `test_a_workspace_cannot_read_anothers_response` — workspace B's response to the same change is not in workspace A's `pending` payload (both still see the change as pending).
- `test_flag_off_hides_every_route` — with the flag off → the public route, the pending route and the respond route all 404.

node — `apps/frontend/tests/subprocessors.test.mjs`:
- `test_a_change_shows_its_deadline` — `changeLine({effective_at, now})` reads "effective 12 Dec 2026 — acknowledge by 12 Dec 2026" and never a bare timestamp.
- `test_object_needs_a_reason_before_the_button_enables` — `canSubmit({kind: 'object', reason: '  '})` is false, `('  vendor abroad  ')` is true.
- `test_an_empty_register_still_renders_a_sentence` — `registerState([])` returns the "No sub-processors are listed yet." state, not `null`.

## Acceptance criteria
- [ ] A signed-out visitor reads the register with names, purposes, regions and dates.
- [ ] Subscribing confirms by email and never sends twice to the same address.
- [ ] An admin accepts or objects to an announced change once, with the response visible to that workspace only.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ the page and every route are absent, and the DPA text is unchanged.

## Notes for the implementer
Owner-gated: the real sub-processor list (names, purposes, regions, safeguards), the notice length before an effective date, and whether an objection suspends processing (INDEX §4.3). This card ships the mechanism and an empty register: it must never seed a plausible-looking vendor, because a made-up row in this table is a false statement to a customer.
