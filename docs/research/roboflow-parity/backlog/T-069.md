## User story
As a workspace owner, I want every ingested image to carry a screening verdict so that an image waiting
for approval is a countable third state, not an image that silently never appears.

## UX flow (LabelDesk words)
1. **Project settings → Uploads** — a switch "Hold uploads for approval before they enter the dataset".
   Off by default; when on, the hint reads "New images wait in **Awaiting screening**; reviewers release
   or discard them."
2. **Upload result sheet** — with the setting on, the sheet reads "Added 37 · 3 awaiting screening" and
   the three are not counted as available. [loading: the count resolves with the upload; no polling]
3. **Dataset · Images** — status filter gains **Awaiting screening**; the header line separates
   "40 uploaded · 24 approved · 3 awaiting screening". [empty: "Nothing is waiting for screening" when
   the filter matches nothing]
4. **Image detail** — a reviewer sees a verdict bar: "Awaiting screening" with **Release** and
   **Discard**. Release → the image joins the normal pipeline; Discard → confirm, then the image and its
   file are removed. [error: a second verdict on the same image → "This image was already reviewed",
   the row refreshes]

## Backend changes
- Models/schema: `apps/backend/app/models/project.py` — `Image.screening: Mapped[str]` default
  `"passed"` (`pending | passed | rejected | failed`); `schema/dataset.py` `IMAGES` block gains
  `"screening": "VARCHAR(16) DEFAULT 'passed'"` (one line, Shared). Backfill is the column default; an
  existing row reads `passed`.
- Routers: `apps/backend/app/routers/images.py`
  - `image_out` gains `screening`.
  - `GET P/images` gains `screening: str = ""` (validated against the four values).
  - `POST /api/images/{image_id}/screening` body `{verdict: "release" | "reject"}` → release:
    `screening="passed"`; reject: `screening="rejected"` and the row is soft-deleted through today's
    `delete_image` body (bytes first, meter refund); `409` when the current state is not `pending`;
    `403` for a labeler.
- Services/jobs: `apps/backend/app/services/screening.py` (new) —
  `hold_for(project) -> bool` (reads `Project.settings["hold_uploads"]`),
  `apply(img, project) -> str` (returns `pending` or `passed`), `verdict(img, value) -> str` raising
  `ValueError` for a bad transition. `ingest` calls `screening.apply` once per new image and adds
  `"awaitingScreening": n` to its response; the connector and archive paths inherit it because they call
  `ingest`.
- Permissions + workspace isolation: verdict needs `c.perm("project.review")` and goes through
  `image_ctx` (cross-workspace image id is rejected there, as today); the list filter lives under
  `project_ctx` (404 for a foreign project).
- Secrets/safefetch: none.
- OpenAPI: yes — new field, new parameter, new route.

## Acceptance criteria
- [ ] With the setting on, new images are `pending` and cannot be treated as available until released.
- [ ] The list filter and header line make the third state countable.
- [ ] Reject removes the file and refunds storage; a second verdict is 409, not a silent overwrite.
- [ ] The connector, archive and URL paths produce the same state because they call `ingest`.
- [ ] Empty, loading and error states above render (nothing-waiting copy, verdict-conflict error).
- [ ] Flag off ⇒ no column effect, no route, and today's answer shapes are unchanged.
- [ ] Workspace A cannot see or change workspace B's data (404 for a foreign project; the image route
      keeps `image_ctx`'s existing refusal).

## Notes for the implementer
There is no moderation vendor: `pending` is a human gate, `failed` is reserved for a future checker and
is never set in this card. Do not add a per-image polling loop — the count comes from the same list
response the grid already reads.
