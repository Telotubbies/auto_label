## User story
As the engineer who claims "point your notebook at LabelDesk", I want a test that runs the real client against our
server and a page that says exactly what works, so the claim is verified instead of asserted.

## UX flow (LabelDesk words)
1. **A reader of the docs page** (`docs/mlflow-client.md`) — copies three lines: install the client, set
   `MLFLOW_TRACKING_URI` to the workspace URL and `MLFLOW_TRACKING_TOKEN` to an API key with the `train` scope, then
   `start_run()` and `log_metric()`; the page lists what is supported (runs, params, metrics, tags, dataset inputs,
   metric history, search, artifacts for trained runs) and what is not (params in filters, registered models,
   logged models).
2. **CI** — with the optional extra installed, one test starts the app on an ephemeral port, drives the real client
   and asserts the round trip. [error: without the extra the test skips with a one-line reason, never fails]
3. **A reviewer** — the same test is the regression guard for T-914/T-915: a wire-shape change that breaks a real
   client fails here, not in a customer's notebook.

## Tests to write first
pytest — `apps/backend/tests/test_mlflow_client_compat.py`:
- `test_importorskip_when_the_extra_is_absent` — `pytest.importorskip("mlflow")` at module scope with the reason
  `install apps/backend/requirements-mlflow.txt to run the wire compatibility test`.
- `test_a_real_client_logs_a_run_we_can_read` — uvicorn on an ephemeral port in a thread (the same style as the
  existing `TestClient` fixtures, plus a socket) → `mlflow.set_tracking_uri(url)`, `start_run()`,
  `log_param("epochs", 3)`, `log_metric("accuracy", 0.5, step=1)`, `log_metric("accuracy", 0.7, step=2)`,
  `set_tag("team", "vision")`, `end_run()`; then `MlflowClient().get_run(run_id)` carries the param, the tag and the
  last metric, and `get_metric_history(run_id, "accuracy")` returns two points in step order.
- `test_the_same_run_is_visible_in_the_labeldesk_list` — `GET /api/ws/{ws}/projects/{p}/models` (or the search route)
  shows the run and its metric, so the two surfaces agree.
- `test_a_foreign_key_cannot_read_the_run` — workspace B's key on the run id → 404.
- `test_the_extra_is_not_imported_by_the_app` — `import app.main` with `mlflow` absent from `sys.modules` leaves it
  absent (the product never imports the library).

node — none: `none: no frontend surface`.

## Acceptance criteria
- [ ] With the optional extra installed, the real client logs a run and reads it back through our routes.
- [ ] Without the extra, the test module skips and the rest of the suite is unaffected.
- [ ] `requirements.txt` is unchanged; the extra lives in its own file and in `THIRD_PARTY_LICENSES.md`.
- [ ] Empty, loading and error states above all render.
  (A skipped test is this surface's empty state; there is no page to render.)
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ surface absent and the old behaviour unchanged.
  (With the flag off the same test asserts every wire route is 404.)

## Notes for the implementer
Overlap: none — no card adds the library; T-914/T-915 implement the wire shapes ourselves, and this card only proves
them with the client that will actually call us.
Do not import `mlflow` in application code, ever: the whole point of the wire subset is that the product stays free
of the library and its dependency tree. The doc page says "compatible client", never that LabelDesk runs MLflow —
MLflow is a source label here, not our product name.
