## User story
As a Thai accountant or auditor, I want the CSV I download and the audit export I hand over to use the same Thai headers and dates as the screen, so that the file does not need a translation step before it is filed.

## UX flow (LabelDesk words)
1. **Dataset → Export → download** — the CSV header row follows the interface language (`ชื่อไฟล์, ความกว้าง, ความสูง, สถานะ, วันที่อัปโหลด`), while the values stay machine-readable: ids, enums, ISO timestamps unless the file is a *display* export.
2. **Audit → Export** — same rule; the audit export names its language in one metadata line and keeps `action` codes in English so a SIEM rule never breaks on a translation.
3. **A report without a Thai translation** — renders the English body with one inline line: "รายงานนี้ยังไม่มีฉบับภาษาไทย — แสดงภาษาอังกฤษ" and never a half-translated table. [error: an export whose locale cannot be resolved falls back to English and says so in the file's first line]
4. **An import** — unchanged: header matching accepts both languages, and an unknown column is refused with the column name as it appeared.
5. **A Thai export opened in Excel** — the BOM is present, so Thai headers are not mojibake.

## Backend changes
- Models/schema: none.
- Routers: `GET /ws/{ws}/projects/{p}/export` and the existing audit export accept `lang=en|th` (default `en`); the response carries `Content-Language` and the file's first line names the locale for CSV.
- Services/jobs: `services/exporters.py` gains `headers_for(lang)` over one mapping table; the row writer is untouched. Audit export reuses the same helper.
- Permissions + workspace isolation: unchanged — the same project-scope check and the same 404 for a foreign project.
- Secrets/safefetch: none — no remote fetch.
- OpenAPI: yes — regenerate `openapi.json` and `api-types.gen.ts` (one query parameter).

## Tests to write first
pytest — `apps/backend/tests/test_export_headers.py`:
- `test_thai_headers_are_thai` — `headers_for('th')` returns Thai strings for every existing column and the same key set as `en`.
- `test_enum_values_stay_english` — a row exported with `lang=th` still writes `approved`, not the Thai label.
- `test_unknown_lang_falls_back_to_english` — `lang=de` returns the English file and `Content-Language: en`.
- `test_bom_is_present_for_thai` — a Thai CSV starts with `\ufeff`.
- `test_cross_workspace_export_is_404` — workspace A's token on workspace B's project returns 404 and writes no file.
- `test_flag_off_ignores_lang` — with the flag off the output is byte-identical to the pre-card fixture.

node — `apps/frontend/tests/export-lang.test.mjs`:
- `test_download_link_carries_the_locale` — `exportUrl(ws, slug, 'csv', 'th')` contains `lang=th`.

## Acceptance criteria
- [ ] A Thai CSV download has Thai headers, English enum values, a BOM and a `Content-Language` header.
- [ ] The audit export follows the same rule and states its language in one line.
- [ ] A report with no Thai translation shows the English body plus the one-line notice, never a half-translated table.
- [ ] Empty, loading and error states above all render: an export with no rows still writes the header row in the chosen language; a failed export keeps the dialog open with its retry.
- [ ] Workspace A cannot see or change workspace B's data: a foreign project's export is 404 and writes nothing.
- [ ] Flag off ⇒ the URL has no `lang` and the file is unchanged.

## Notes for the implementer
Headers are display text; values are data. Anything a machine reads back — `action`, `status`, `split`, ids, ISO dates — stays English and unformatted, which is why the mapping covers the header row and nothing else. Keep the mapping in one module: the frontend catalogue and the export headers are two views of one vocabulary, and the test asserts their key sets match.
