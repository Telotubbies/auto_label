## User story
As the person who signs off a model, I want one screen that shows the candidate and what is live side by side, so that I approve from the numbers instead of from two browser tabs.

## UX flow (LabelDesk words)
1. **Model page** (`/:ws/:project/models?model=<id>`) — `Request promotion` opens the dialog: stage, reason, and the model's own evaluation. [empty: a model with no evaluation still offers the dialog but says "This model has no evaluation yet." above the reason field]
2. **Deployments** (`/:ws/deployments`) — each alias card grows a pending block: `Waiting for approval`, the candidate's AP and latency against the live model's, the requester and the reason. [empty: "No promotion requests waiting."] [loading: two skeleton rows under the alias card] [error: the request list fails ⇒ "Requests could not be loaded" with a retry; the deploy form below it keeps working]
3. **Approve / Reject** — a dialog holds one optional note; on approve the alias card's current model changes in place and a toast confirms; on reject the row leaves the queue and the note is kept on the record.
4. **A request for a model that vanished** — the row says "That model is no longer available to promote." and offers only `Reject`. [error: approving after the model was deleted shows the API's 409 sentence, never a raw error]
5. **History** — the alias card's existing event list gains the requester, approver and request text for each promoted event.

## Acceptance criteria
- [ ] A request is raised from the model page with a target stage and a reason, and appears on the matching alias card.
- [ ] The approver sees the candidate's numbers beside the live model's before deciding, and can approve or reject with a note.
- [ ] Approving updates the alias in place and the promoted event names requester, approver and request text.
- [ ] Empty, loading and error states above all render: no pending requests says so, and a failed request list leaves Deploy usable.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ the deploy form and alias card render exactly as today.

## Notes for the implementer
Never hide the live model to make the candidate look better: both rows are always rendered, even when the candidate wins every column. `Reject` needs no reason; `Approve` takes one optional note that is stored, so an auditor can read why the stage moved.
