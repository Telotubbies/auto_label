## User story
As an integrator, I want to see whether this call loaded the weights and how long the model took, so that a slow first request is explainable instead of a mystery.

## UX flow (LabelDesk words)
1. **Hosted predict** (`POST /api/v1/models/{model_id}/predict`) — the response carries `x-model-state: cold | ready | warm`, `x-model-cold-start: 1 | 0` and `x-processing-time: 0.084`. A `[loading]` first call answers slowly and says `cold`; the next answers `ready`.
2. **Warmup** — `POST /api/v1/models/{model_id}/warmup` with the same bearer auth loads the weights and returns `{state, loaded_ms}`; it bills one `ai_calls` unit, because it is one inference. The Deploy page offers "Warm it up before the demo" beside the endpoint card.
3. **Deploy & test** — the latency line (T-314) appends "cold start" when the header is 1, so the person who is about to copy a snippet knows what production will pay once.
4. **Docs line** — one sentence in T-318's reference: "The first call after the model is unloaded pays the load; `x-model-cold-start: 1` marks it."

## Acceptance criteria
- [ ] A cold first call returns `x-model-cold-start: 1` and `x-model-state: cold`; the next call returns `0` / `ready`.
- [ ] `x-processing-time` reports the model call in seconds, not the HTTP round trip.
- [ ] `POST …/warmup` loads the weights once, bills one AI call and is refused without the `infer` scope.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] No flag: a client that ignores the headers sees exactly today's body and status codes.

## Notes for the implementer
Use the scheduler's existing lease ledger (`app/gpu/scheduler`) as the cold-start source; do not add a second residency cache. Never emit a header value derived from an exception message — the three values are a closed set.
