## User story
As an IT admin, I want to add a domain, verify it with one TXT record and see each domain's state, so that a failed
verification has a visible home.

## UX flow (LabelDesk words)

*Screen this contract serves:* Settings → **Single sign-on** (the screen is T-425's card) and the login screen's
SSO entry. States they must show: no provider → "Single sign-on is not set up" with `Add a domain`; a pending
domain → `Pending · check again` with the exact TXT record and a copy button; verifying → the button busy and the
row still pending; a failed lookup → "We could not find that record yet" plus the record again (no scary error);
an enabled provider → "Members with @acme.com can sign in with your provider" and a `Test sign-in` link.

1. `GET /api/ws/{ws}/sso` → `{enabled, domains: [{id, domain, status, record_name, record_value, last_checked}],
   config: {provider_kind, issuer, client_id, verified_at} | null}` — the secret is never returned, only
   `has_client_secret: true`.
2. `POST /api/ws/{ws}/sso/domains` `{domain}` → 201 the domain in `pending` with its record name/value;
   `409` duplicate, `400` for a public mail domain or an invalid hostname.
3. `POST /api/ws/{ws}/sso/domains/{did}/verify` → runs one DNS lookup now: found → `verified` + `audit sso.domain_verified`;
   missing or mismatched → `failed` with `{reason: "no_txt_record"|"wrong_value"|"nxdomain", record_value}` and
   `200` (a failed check is an answer, not a server error). `429` when called more than 6 times an hour for one domain.
4. `POST /api/ws/{ws}/sso/config` `{provider_kind, issuer, client_id, client_secret}` → 200; `409 verify a domain first`.
   `PATCH` accepts a masked secret (`•••`) meaning "keep the stored value".
5. `POST /api/ws/{ws}/sso/enable` `{enabled}` → 200; enabling without a verified domain and a config is `409`.
6. `DELETE /api/ws/{ws}/sso/domains/{did}` → 200; deleting the last verified domain when SSO is enabled → `409 turn SSO off first`.

## Backend changes
- Models/schema: none (T-423).
- Routers: `app/routers/sso.py` (new) — prefix `/api/ws/{ws}/sso`, the six routes above.
- Services/jobs: `app/services/sso.py` — `verify(db, row) -> tuple[str, str | None]` using
  `dns.resolver.resolve(record_name, "TXT")` guarded by a `try/except` that maps every resolver failure to a reason
  (no `dnspython` dependency: use `socket`-free record lookup only if available — otherwise the card's `TODO` is
  the resolver, see Notes), `rate_limited(db, row, now) -> bool` (counts `sso.verify_attempt` audit rows in the hour),
  `state(db, ws) -> dict`, `set_config`, `enable`.
- Permissions + workspace isolation: read `workspace.read`; every write `workspace.update`; domain/config ids resolve
  inside `c.ws.id` only.
- Secrets/safefetch: `client_secret` via `secretbox`; the DNS lookup is outbound but resolves only the workspace's own
  domain name, which the admin supplied, so it is validated as a hostname and never an IP literal.
- OpenAPI: yes.

## Acceptance criteria
- [ ] A domain is added with a published TXT record and can be verified on demand, with each failure named.
- [ ] Verification is rate-limited and a failed attempt never flips an already-verified domain.
- [ ] The IdP config requires a verified domain, and its secret can be kept by sending a mask.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no routes.

## Notes for the implementer
Use the standard library only: a TXT lookup needs `dnspython`, which is not a dependency here — implement `verify` behind
a small `resolve_txt(name)` seam that returns `None` when no resolver is available, and mark
`shortcut: stdlib has no TXT resolver; inject one when SSO ships behind a real IdP`. The seam is also what the tests
monkeypatch.
