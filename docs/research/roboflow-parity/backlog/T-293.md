## User story
As a team lead, I want a suite run to record pass/fail per image and per check, so that a regression is a number I can compare against last week instead of an argument.

## UX flow (LabelDesk words)
1. **Regression tab → *Run*** — the row shows *Queued* then *Running 34 %* with "image 34 of 100"; the job tray carries "Regression · <suite>".
2. **A finished run** — the row reads "92 % passed · 12 Nov 14:03" with the delta against the previous run ("+3 %" or "−8 %"). [empty: a suite never run shows "never run" and the Run action]
3. **A run that cannot start** — no worker, or a workflow that is disabled by its flag → the row states it ("The workflow needs its feature turned on.") and nothing is queued.
4. **Partial results** — an image whose workflow errors is recorded as `error` (neither pass nor fail) and the run's summary counts it separately: "92 passed · 5 failed · 3 errors".
5. **Cost** — the run states its cost up front ("about 0.02 credit per image · 100 images") because every image calls a model; a workspace without AI calls left is refused with the metering message before anything queues.

- **States** — [empty: a suite whose source resolves to zero images refuses to queue and names the source]. [loading: the row shows "image N of M" until the run finishes] [error: a job that dies leaves the run `failed` with T-287-style copy and keeps its partial results].

## Backend changes
- Models/schema: `EvalRun` — `id` pk, `suite_id` FK cascade, `status` `VARCHAR(16)` (`queued|running|done|failed`), `baseline_run_id` `VARCHAR(32) NULL`, `passed`/`failed`/`errors` `INTEGER`, `pass_rate` `FLOAT`, `results` JSON (per image: `{file, image_id, outputs_digest, checks:[{code, ok, expected, actual}]}`), `error` `TEXT`, `created`/`finished` `FLOAT`.
- Routers: `POST {P}/evals/{id}/run` → `202 {run_id, job_id, images, estimated_credits}`; **409** while another run of the same suite is active; `GET {P}/evals/{id}/runs` and `GET {P}/evals/runs/{run_id}`.
- Services/jobs: job kind `eval_run` (`handlers/evals.py` — new module, `eval_run` in `LOCAL_JOB_KINDS`): resolves the suite's image list (a frozen version split or the pinned ids), calls the existing workflow runner once per image with a per-image timeout, evaluates `eval_checks.run_checks`, writes results every 10 images so a crash keeps partial progress, computes the summary and links `baseline_run_id` to the suite's previous `done` run. Metering: `metering.check(db, ws, "ai_calls", images)` up front and one `charge(CREDIT_COST["infer"])` per processed image (same shape as auto-label) — a refusal happens before the job is created.
- Permissions + workspace isolation: run = `c.need("admin")` (it spends), reads = `project.review`; a foreign suite id → 404.
- Secrets/safefetch: none new — the workflow runner's own outbound guards apply per block.
- OpenAPI: yes — regenerate both files.

## Acceptance criteria
- [ ] One job runs a suite over its images, storing per-image and per-check results and a summary.
- [ ] Errors are counted apart from failures; a crash keeps partial results.
- [ ] Cost is checked before the job exists, and a per-image charge happens as the same shape auto-label uses.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ route and job kind 404.

## Notes for the implementer
Cap the run at the suite's 200 images (T-292 validates the source) and reuse the workflow runner's per-image entry point — do not add a second executor. Progress writes: every 10 images or 5 seconds, whichever comes first.
