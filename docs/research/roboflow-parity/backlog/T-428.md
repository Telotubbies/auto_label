## User story
As an external tool, I want to exchange a code for a token that spends as the person who approved it, so that usage is
attributable to a member.

## UX flow (LabelDesk words)
1. `POST /api/oauth/token` (form-encoded) `grant_type=authorization_code&code&redirect_uri&client_id&code_verifier`
   → `{access_token, token_type: "bearer", expires_in, refresh_token, scope}`. `400` for each failure code
   (`invalid_grant`, `invalid_client`, `invalid_request`).
2. `POST /api/oauth/token` `grant_type=refresh_token&refresh_token&client_id` → a new pair; the old refresh token is
   revoked in the same transaction (rotation, no reuse).
3. Every call made with an OAuth token stamps `UsageEvent.meta["user_id"]` and `meta["oauth_client_id"]`, so the
   attribution panel (T-410) shows the person, and the ledger names the app in `actor`.
4. Audit rows: `oauth.token.issued`, `oauth.token.refreshed`, `oauth.token.revoked`, `oauth.app.created`,
   `oauth.app.secret_rotated`, `oauth.app.revoked`, `oauth.consent.granted`, `oauth.consent.denied`.
5. `[error]` a revoked client → `invalid_client` and no token; a replayed refresh token → `invalid_grant` and the whole
   family is revoked (`oauth.token.reuse_detected`).
6. Denied operations: an OAuth token cannot create another OAuth client or issue keys, even with `read` — the route
   refuses with the same 404 a missing scope gives.

## Backend changes
- Models/schema: `OAuthToken(id, client_id FK, workspace_id, user_id FK, access_hash VARCHAR(64) unique,
  refresh_hash VARCHAR(64) unique, scope JSON, expires FLOAT, refresh_expires FLOAT, revoked_at FLOAT null, created)`
  in `app/models/oauth.py`; the access token is a `security`-signed JWT with `sub`, `ws`, `scope`, `client_id`, so the
  existing bearer path can authenticate it.
- Routers: `routers/oauth.py` — `POST /token`; `POST /api/ws/{ws}/oauth-clients/{id}/rotate`; `DELETE` revokes the
  client and every token of its family.
- Services/jobs: `services/oauth.py` — `exchange_code`, `refresh`, `revoke_family`, `mint(subject)`, plus one branch in
  `deps._authenticate` that recognises an OAuth JWT (`aud="oauth"`), resolves the member, and exposes `c.oauth_scope`.
  One shared line in `apikeys`-adjacent scope checking: an OAuth scope missing → the same bare 404 as a key scope.
- Permissions + workspace isolation: the token carries its workspace; `ws_ctx` still requires a `Member` row, so a
  removed member's OAuth token stops working immediately.
- Secrets/safefetch: refresh tokens stored as sha256 only; access tokens are stateless and short-lived (15 min).
- OpenAPI: yes.

## Acceptance criteria
- [ ] A valid code plus verifier yields a 15-minute access token and a rotating refresh token.
- [ ] Reuse of a refresh token revokes the family and is audited.
- [ ] Spend made with the token is attributed to the member and names the app in the ledger.
- [ ] An OAuth token cannot mint keys or clients.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no token endpoint.

## Notes for the implementer
Refresh rotation with reuse detection is the security core: one family per grant, and a reused token kills the family.
The access token is a JWT the existing bearer path already understands — do not add a second auth dependency.
