## User story
As a data engineer, I want the perceptual-hash grouping I already trust for splits exposed as a cluster
list with a slider, so that near-identical frames are something I can review instead of invisible work.

## UX flow (LabelDesk words)
1. **Dataset · Health · Duplicates** — a list of clusters: cluster thumbnail stack, "7 near-identical
   images", the splits it touches and a badge "Leaks across train and test" when it does.
   [empty: "No near-duplicates at this threshold — raise it to look harder."] [loading: 5 cluster
   skeletons and a line "Comparing 1,240 images…"]
2. **Dataset · Health · Duplicates** — a threshold slider (0 = only pixel-identical, up to 16) recomputes
   the list; the label reads "6 · 42 clusters · 3 leak across splits".
3. **Dataset · Health · Duplicates** — clicking a cluster opens its images side by side with the split
   chips. [error: an unreadable file is listed as "cannot compare" inside its own one-image cluster, never
   dropped silently]
4. **Dataset · Health · Duplicates** — "Over 3,000 images" installs show the line "Compared the newest
   3,000 images" so the count is never mistaken for the whole dataset.

## Backend changes
- Models/schema: none (the pHash is computed on demand; the existing health scan keeps its own cache).
- Routers: `apps/backend/app/routers/projects.py` — `GET /{project}/health/duplicates?max_distance=6`
  → `{clusters: [{id, size, splits: [str], leaks: bool, images: [{id, name, thumbnail, split, status}]}],
  compared, sampled, threshold}`; `400` for a threshold outside 0–16.
- Services/jobs: `apps/backend/app/services/duplicates.py` (new) —
  `clusters(db, project, max_distance=6, limit=50)` builds the union-find over `versioning.phash_groups`
  (reused, not copied) across the newest 3,000 live images, drops singletons, marks `leaks` when a cluster
  spans more than one split, and sorts by size then oldest id; `explain(cluster)` returns the pairs and the
  worst distance.
- Permissions + workspace isolation: `c.perm("project.review")` (health data is reviewer-level); rows come
  from `Image.project_id == c.project.id`.
- Secrets/safefetch: none.
- OpenAPI: yes — one route.

## Acceptance criteria
- [ ] Clusters are grouped from the same pHash comparison the version builder uses, not a second algorithm.
- [ ] The threshold changes membership and is bounded 0–16.
- [ ] A cluster spanning splits is flagged as leakage.
- [ ] Sampling over 3,000 images is disclosed; an unreadable file is never silently dropped.
- [ ] Empty/loading/error states above render.
- [ ] Flag off ⇒ no route and no section.
- [ ] Workspace A cannot see or change workspace B's data (404 for a foreign project id).

## Notes for the implementer
Reuse `versioning.phash_groups` (union-find over Hamming distance) instead of writing a second matcher; the
only new part is grouping, sorting and the leakage flag. No job: the newest 3,000 images compare in about a
second on CPU.
