## User story
As a reviewer, I want to mark a version `validation_status:approved` or `use_case:gate-entry`, so that the registry says why a model is deployable instead of leaving it to memory.

## UX flow (LabelDesk words)
1. **Save a tag** — `PUT {P}/models/{mid}/tags/{key}` with a value returns the whole tag map; the same call with an empty value deletes the key. [empty: a version with no tags returns `{}`, never `null`] [error: a key over 64 characters or a value over 256 is a 422 that names the limit]
2. **Filter** — `GET {P}/models?tag=validation_status:approved` returns only versions carrying that pair; a key with no matching version is an empty list, not a 422. [error: a filter without a colon is a 422 "tag must be key:value"]
3. **Group view** — a version's tags roll up to its registered model, so the rail can show the union of its versions' tags without a second table.
4. **No inference effect** — tags never change predict, export or deploy behaviour; they travel in the model payload.
5. **Reader** — a reader with `project.models` sees tags; a labeler gets the masked payload as today, tags included (they carry no weights).

## Acceptance criteria
- [ ] A version carries a small key-value tag map that survives reload and never returns null.
- [ ] Setting an empty value deletes exactly that key and leaves the rest.
- [ ] `?tag=key:value` narrows the list, and a key with no match is an empty list rather than an error.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
