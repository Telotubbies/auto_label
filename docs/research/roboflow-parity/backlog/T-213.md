## User story
As an engineer with many small objects, I want several images packed into one training tile, so that each object occupies more pixels and the model sees more objects per step.

## UX flow (LabelDesk words)
1. **Wizard → step 4 → Add augmentation → Mosaic** — one bounded field *Images per tile* (3–9). [empty: n/a] [loading: n/a] [error: "Mosaic needs at least 3 images." when the train pool is too small]
2. **Pool note** — "Mosaic borrows other **train** images; valid and test are never mixed in."
3. **Doubling warning** — same card text as cutout: "Many models already apply this while training… add it only after a clean baseline."
4. **Count line** — "≈ 1 tile per image · 4 images inside".

## Backend changes
- Models/schema: none.
- Routers: none.
- Services/jobs: `app/services/imaging.py` — `mosaic(im, anns, pool, params, rng)`: choose the grid from `images` (3→2×2 with one cell skipped, 4→2×2, 5–6→2×3, 7–9→3×3), resize the source and the drawn partners into cells, project their annotations into the composite with `_map_points`, and return the composite plus the concatenated annotations. `versioning.generate` passes at most `images-1` partners from the **train** rows (loaded lazily, at most `MAX_MOSAIC_PARTNERS = 8` per image, capped so a 4 000-image pool does not thrash the disk), and skips mosaic when the train pool has fewer than 3 images with `stats.mosaic_skipped`.
- Permissions + workspace isolation: unchanged; partners come from the same project's pool only.
- Secrets/safefetch: none.
- OpenAPI: no.
- Flag: `task_190` off ⇒ `mosaic` rejected (`aug_unknown_op`); premium plan → `aug_tier_unavailable`.

## Notes for the implementer
Load partners with `imaging.load(row.path)` inside a bounded LRU of 16 images per build — a mosaic of every train image re-reading 4 000 JPEGs is the one way this card can turn a 3-minute build into an hour. Cap the composite at the source image's size; never upscale.
