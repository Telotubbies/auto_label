## User story
As an admin, I want to see which credential the workspace treats as its default, so that "which key do I disable"
has an answer before an outage.

## UX flow (LabelDesk words)
1. **`⋯ → Set as default`** (and `Clear default` when set) — confirm `Make “in-app” the workspace default? Hosted
   inference started from the app is attributed to this key.` A folder key never offers it.
2. **Badges** — `Default` on the chosen row; with no default, exactly one row shows `In use` (the fallback); when
   no key qualifies, a warning card above the table reads
   `No key can act as the workspace default. Generate a key with read, upload, infer and train.` with
   `Generate new key`.
3. **Explain the fallback** — the `In use` badge tooltip: `No default is set, so the oldest enabled full-access key
   is used.`
4. `[loading]` the badges resolve with the table's own skeleton; `[error]` the fallback warning is a card, not a toast.
5. **Scope rule** — the default must hold all four scopes; the API refuses a narrower key with
   `The default key needs read, upload, infer and train.`

## Backend changes
- Models/schema: `ApiKey.is_default` ships in T-388; no new column. A partial invariant (one default per workspace)
  is enforced in the service, not by a unique index (SQLite partial indexes are avoided elsewhere in this repo).
- Routers: `POST /api/ws/{ws}/keys/{kid}/default` `{default: bool}` → 200 row; `409` for a folder key, a
  publishable key, a disabled key or a key missing a scope; `409` clears the previous default in the same commit.
- Services/jobs: `services/keys.py` — `set_default(db, ws, key)`, `resolve_default(db, ws) -> ApiKey | None`
  (default → oldest enabled all-scope key), `in_use_id(db, ws) -> str | None`.
  One shared line: the hosted-inference path stamps `meta={"api_key_id": in_use_id(db, ws)}` on the usage event so
  T-410 can attribute it.
- Permissions + workspace isolation: `workspace.keys`; the resolution filters `workspace_id` and `disabled_at IS NULL`.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Acceptance criteria
- [ ] Exactly one key is `Default` when one is set; otherwise exactly one enabled full key is `In use`.
- [ ] A key missing a scope, a folder key, a publishable key or a disabled key cannot become default.
- [ ] When no key qualifies the table says so and offers the create action.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no default concept, no badge, no attribution stamp.

## Notes for the implementer
The default is a resolution rule, not a permission: it never widens what the key may do. Stamp `api_key_id` only
where the app itself acts (hosted inference from the playground) — API calls already carry their own key.
