## User story
As a privacy officer answering an access request, I want one search that shows every place this person appears across the workspace and one archive I can hand over, so that the honest answer to a data subject is a file rather than "ask engineering".

## UX flow (LabelDesk words)
No screen in this card (T-752 owns the workbench):
1. **Find** — `POST /api/ws/{ws}/compliance/requests/{id}/find` answers `{hits: [{store, project, project_name, ref, thumbnail, match, note}], truncated: false, stores: {images: 12, comments: 1, audit: 40, alerts: 3}}`. Hits group by project in the workbench, each with a thumbnail and the field that matched (`note: "name matched"`).
2. **Nothing found** — `{hits: [], stores: {...all zero}}` and the workbench prints `"No appearance found for these identifiers."` / `"ไม่พบข้อมูลของบุคคลนี้จากตัวระบุที่ให้มา"` — the case can still be answered with that finding.
3. **Export** — `POST …/export` queues a job and answers `{job_id}`; when it finishes the case status is `exported` and `GET …/bundle` returns `dsar-<case>-<date>.zip` with `manifest.csv`, `redaction-log.txt` and `frames/`. [loading: "Building the archive — 12 frames" in the workbench] [error: 404 on the bundle before the job finished, 409 when the case was already erased]
4. **A frame whose faces cannot be blurred** — the redaction log records `frames/8812.jpg, blurred: false, reason: "face detector unavailable on this host"`, and the manifest marks it, so the officer decides before sending. The archive is never presented as redacted when it is not.
5. **A large result** — over 500 hits the response sets `truncated: true` and the workbench says `"Showing the first 500 of 1,842 — narrow the identifiers or export the full set."` The export always uses the full set.
6. **A foreign case** — 404 on find, export and bundle, and no archive path is revealed.

## Backend changes
- Models/schema: none — the hits are recomputed on demand and never stored on the case, so there is no second copy of the subject's data to erase later.
- Routers: in `app/routers/compliance.py` (created by T-750) — `POST /compliance/requests/{id}/find` → the hit set; `POST /compliance/requests/{id}/export` → `{job_id}` (409 when the case is `erased`); `GET /compliance/requests/{id}/bundle` → `FileResponse` of the built archive (404 before it exists).
- Services/jobs: `app/services/subject_index.py` (new) — `LIMIT = 500`, `search(db, ws, identifiers) -> dict` over the stores the schema actually has: `Image.name`/`Image.tags`/`Image.id`, `Comment.text`, `Audit.target` and `Audit.meta`, `AlertDelivery.event`; each hit carries the store, the project, the ref, the matched field and a signed thumbnail URL (`security.sign_path`). `app/handlers/ops.py` gains `run_dsar_export(job)` — re-runs `search()` for the case, writes `DATA_DIR/exports/dsar/<case>.zip` with `manifest.csv` (BOM, Excel-safe like the audit export), `redaction-log.txt` and blurred frame copies through `services/faceblur.blur_faces`, then sets the case status to `exported` with an audit row. `dsar_export` joins `LOCAL_JOB_KINDS` in `app/config.py`.
- Permissions + workspace isolation: `workspace.update` on all three; the case, every hit and every archive path are resolved inside `c.ws.id`; a frame path is validated with `services/erasure.inside()` before it is opened, so a tampered `Image.path` cannot read outside `DATA_DIR`.
- Secrets/safefetch: none — no URL is fetched (a remote connector's bucket is not mirrored into a DSAR bundle; the manifest names the connector as "held by the customer's bucket" instead).
- OpenAPI: yes — three routes and the hit shape.

## Tests to write first
pytest — `apps/backend/tests/test_dsar_find_export.py`:
- `test_find_matches_a_name_in_an_image_tag_and_an_audit_target` — a tag, a comment and an audit target carrying `EMP-4471` produce one hit each, with the store named.
- `test_find_returns_nothing_for_an_unknown_identifier` — `hits: []` and every store count is zero.
- `test_hits_are_capped_and_flag_truncation` — 520 matching rows return `truncated: true` and exactly 500 hits.
- `test_export_writes_a_zip_with_a_manifest_and_a_redaction_log` — run `run_dsar_export` for a case with 2 frames; the zip contains `manifest.csv`, `redaction-log.txt` and two files under `frames/`, and the case status is `exported`.
- `test_the_redaction_log_admits_a_missing_detector` — with `faceblur.available()` monkeypatched to False the log carries `blurred: false` and the reason, and the job still succeeds.
- `test_a_tampered_image_path_is_refused` — an `Image.path` of `../outside.jpg` produces a hit but the frame is skipped and named in the log; nothing outside `DATA_DIR` is read.
- `test_bundle_before_the_job_is_404_and_after_erase_is_409` — the three codes hold, and a foreign case id is 404 on all three.
- `test_flag_off_writes_no_archive` — with the flag off all three routes are 404 and no file appears under `exports/dsar`.

## Acceptance criteria
- [ ] Find returns hits grouped by store and project with the matched field, and states zero hits explicitly rather than an empty pane.
- [ ] Export produces a zip containing a manifest, a redaction log and the matched frames, and moves the case to `exported`.
- [ ] The redaction log says which frames were not blurred and why; the archive is never labelled redacted when a frame is not.
- [ ] Empty, loading and error states above all render: zero hits, `truncated` at 500, 404 before the archive exists, 409 after erasure.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no find, no export, no archive on disk.

## Notes for the implementer
Owner-gated: what counts as "the person" in this system — a name, a staff id, a face in a frame — is the controller's decision, and LabelDesk has no face index, so the workbench matches only the identifiers a person typed; a Thai lawyer must confirm what the controller may lawfully answer with (INDEX §4.3). Never claim a hit set is complete: the copy says "appearances found by these identifiers". Recompute hits per export instead of storing them, or the erasure step in T-752 would have to erase the case's own cache of the person's data — the cleanup path must not create a second copy.
