## User story
As a reviewer on a bright factory floor, I want the glass chrome to keep its 4.5:1 text contrast whether or not blur is available, so that a bar I read all day never turns into a washed-out strip.

## UX flow (LabelDesk words)
1. **Any screen, blur available** — the top bar, project rail, floating toolbar, dialogs, command palette, job tray and toasts blur at 16 px (chrome) / 20 px (overlay) with the 58% (light) / 62% (dark) tint, the 80/84% overlay tint and the 1 px inner highlight. Content surfaces stay solid.
2. **Any screen, `prefers-reduced-transparency`** — the same geometry with the 92% opaque fill, no sheen gradient, no blur; text sits on the solid fill.
3. **Settings → Appearance → Reduce transparency** — the same result in every browser, including Safari, which ignores the media query.
4. **A browser without `backdrop-filter`** — the `@supports` block never applies, so the solid fill is what renders from the start. [error: a projector profile with low contrast still passes because the contrast comes from the fill, not the blur]
5. **A glass surface added by a later card** — `.glass-sidebar` and any new chrome class inherit the same fallback, so a lane cannot ship a surface that only works with blur.

## Notes for the implementer
This card **does not move the glass values**. REDESIGN §4 proposes 24 px blur with a 62–66 % fill and a 96 % fallback; `VISUAL-OVERRIDE.md` §5 gives the running app's numbers precedence, so 16/20 px, 58/62 %, 80/84 % and 92 % stay and the test pins them. Widening the fallback selector list is the only behaviour change, and it is the one a later card would otherwise break.
