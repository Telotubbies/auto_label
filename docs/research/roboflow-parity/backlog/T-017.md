## User story
As someone creating a project, I want every task type described by what I get, so that I pick by outcome instead of guessing which model family applies.

## UX flow (LabelDesk words)
1. **New project** (workspace home → `New project`) — the type grid lists eight cards, each with an icon, an outcome sentence and two capability chips:
   `Object detection` — "Draw a box around each object." · `Boxes`, `Counts`
   `Instance segmentation` — "Outline each separate object." · `Polygons`, `Measuring`
   `Semantic segmentation` — "Colour every pixel of a class, one mask per class." · `Masks`, `Area`
   `Classification (one label)` — "Give the whole image one label." · `One label`, `Sorting`
   `Classification (many labels)` — "Give the whole image several labels." · `Tags`, `Sorting`
   `Keypoints` — "Place named points and link them into a skeleton." · `Points`, `Pose`
   `Action recognition` — "Mark when an action starts and ends in a video." · `Video`, `Segments`
   `Anomaly detection` — "Learn what good looks like and flag deviations." · `Good-only`, `Heatmap` (flag `task_29`)
2. **Ask for another type** — the last row of the grid is a quiet link `Need a different type?` opening a one-field sheet: what you would label, optional example. Submit → `Thanks — we logged it.` [empty: field blank → submit disabled] [error: `Could not send — try again`], nothing else changes.
3. **Selected state** — the chosen card gets the primary border and a `Selected` chip; the submit button keeps its label `Create project`.

## Backend changes
- Models/schema: `PROJECT_TYPES` in `models/common.py` grows to `("object-detection", "instance-segmentation", "semantic-segmentation", "classification", "multi-label-classification", "keypoint-detection", "action-recognition", "anomaly-detection")`; `ProjectPatch`/`ProjectIn` validation keeps using it. `multi-label-classification` sets `multilabel=True` on create (the column already exists). No new column.
- Routers: `POST /api/ws/{ws}/type-requests` `{wanted: str ≤300, example?: str ≤300}` → 201, writes an `Audit` row `project.type_request` (no new table); 422 empty `wanted`. `GET /api/ws/{ws}/projects/{p}` unchanged.
- Services/jobs: none.
- Permissions + workspace isolation: type requests need `workspace.read`; the audit row is written under `ws_ctx`'s workspace only.
- Secrets/safefetch: none.
- OpenAPI: yes (`type-requests`, widened enum).

## Frontend changes
