## User story
As a new user, I want the assistant conversation to persist and its proposal to create the project it describes, so that the first screen ends with something real in my workspace.

## UX flow (LabelDesk words)
1. **Assistant home** (`/:ws/assistant`) — thread loads with the brief as the first message and the proposal row. [loading: two message skeletons, composer disabled] [error: `Could not load the conversation — Retry`] [empty: no thread yet → composer with the three starter rows].
2. **Send** — type and press Enter (Shift+Enter is a newline). The user bubble appears immediately; the reply lands with one action row. [loading: a typing row, never a spinner over the thread] [error: `That message did not send — Retry` keeps the draft].
3. **Run the action** — `Create project` on the proposal → button reads `Creating…`, then the thread appends `Created “PPE Detection”. Opening it…` and the client routes to `/:ws/p/<slug>/upload`. [error: 402 project limit → `The Free plan holds 3 projects. Archive one, or ask an admin to change the plan.`; 422 → `I could not read that project name — change the details.`]
4. **Run again** — a second click on an executed action is refused server-side with `That action already ran.` and the row becomes a link to the project.

## Backend changes
- Models/schema: `models/assistant.py` (new) — `AssistantThread(id, workspace_id, user_id, created, updated)` and `AssistantMessage(id, thread_id, role: user|assistant, text, actions JSON, run JSON, created)`; register the module in `models/__init__.py` (`DOMAIN_MODULES` + re-exports). No `ADD COLUMN` needed: `create_all` makes both tables on an empty database, and `schema.apply` is unaffected.
- Routers: `routers/assistant.py` (new), prefix `/api/ws/{ws}/assistant`: `GET /thread` → `{id, messages:[{id, role, text, actions, run}]}` (creates the thread on first call, seeding from `workspaces.onboarding`); `POST /messages` `{text}` → `{messages: [user, assistant]}`; `POST /actions/{message_id}/run` → `{kind: "create_project", project: {slug, name}, message}`; 404 unknown message/thread, 409 already run.
- Services/jobs: `services/project_create.py` (new) — `create(db, ws, user, body) -> Project` extracted from `create_project` in `routers/projects.py` (slug loop, plan 402, class cleaning, audit) so the router and the assistant share one path; `routers/projects.py` becomes a thin caller.
- Permissions + workspace isolation: `ws_ctx` on every route; running a create action needs `workspace.project.create`; threads are per (workspace, user) — another member's thread id 404s; a project slug from another workspace is never accepted as input.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Acceptance criteria
- [ ] A conversation survives reload, with user and assistant bubbles in order and the action state stored on the assistant message.
- [ ] Running a proposal creates exactly one project through the same service as the New project form (same slug rules, same 402 message path).
- [ ] Empty, loading and error states above all render (including the 402 and the double-run 409).
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ surface absent and the old behaviour unchanged (routes 404, `create_project` router behaviour identical).

## Notes for the implementer
The thread is per user, not per workspace: two admins must not share one conversation. `run` stores `{project_id, slug, at}`; the UI derives "already ran" from it rather than from a new column.
