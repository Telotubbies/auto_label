## User story
As an ML engineer, I want to name pointers myself — `champion`, `field-trial`, `driver-a-cam` — and move them between versions, so that a caller can target one name that I repoint without a redeploy.

## UX flow (LabelDesk words)
1. **Model detail header → aliases** — the selected version shows its alias chips; *Add alias* opens a one-field dialog that offers the project's existing alias names as suggestions and accepts a new one. [empty: "No aliases — add one to point a caller at this version."] [loading: the dialog's confirm reads "Adding…" and the chip appears only on success] [error: a name with spaces, capitals or more than 32 characters is refused inline with the rule shown]
2. **Move an alias** — adding an alias that another version already holds asks "Move `champion` from v2 to v3?" with the consequence: "Callers using `champion` get v3 on their next request." Confirming moves it and leaves v2 with no chip. [error: a failed move leaves both versions unchanged and names the reason]
3. **Remove an alias** — the chip's × asks once ("Callers using `driver-a-cam` will get 404 until you point another version at it.") and records who removed it. [error: `production` cannot be removed from here; the dialog says to move it instead]
4. **Serving alias stays special** — `production` and `staging` keep today's Deploy page behaviour and their rollback; a free-form alias never changes what `/api/v1/models/{id}/predict` returns, because that route takes the model id.
5. **Reader** — a reader sees the chips with no Add or × (permission-dimmed, not hidden).

## Backend changes
- Models/schema: none — `DeploymentAlias(project_id, alias, model_id, previous_model_id)` already holds any name (`apps/backend/app/models/training.py:77-88`).
- Routers: `apps/backend/app/routers/training.py` gains `GET {P}/models/{mid}/aliases` → `[{alias, reserved}]`; `POST {P}/models/{mid}/aliases` body `{alias}` → **201** with the alias payload, **409** when the target is not `ready`, **422** on a bad name, **404** when the model or alias is not this project's. `DELETE {P}/models/{mid}/aliases/{alias}` → **204**, **404** when the alias points elsewhere, **409** for a reserved name. `model_out` gains `aliases: [str]` from one query.
- Services/jobs: `apps/backend/app/services/deployments.py` — `clean_alias(raw) -> str` accepts `^[a-z][a-z0-9-]{1,31}$`, refuses `latest`, keeps `DEPLOY_ALIASES` as the reserved pair; `set_alias(db, project, model, alias, user)` and `clear_alias(db, project, model, alias, user)` write one `DeploymentEvent` (`deploy` / `rollback` stays as today, a clear writes `action="deploy"` with `model_id=None`).
- Permissions + workspace isolation: alias writes need `admin` like today's `switch`/`rollback` (`apps/backend/app/routers/deployments.py:30-48`); reads follow `project.models`; another project's model id is a 404 from `_model`.
- Secrets/safefetch: none.
- OpenAPI: yes — three routes, one payload field; `python tools/export_openapi.py`, `npm run gen:api-types`.

## Acceptance criteria
- [ ] A version can carry several user-named aliases, and one alias always points at exactly one version.
- [ ] Moving an alias is one confirmed action that records an event naming the old and the new version.
- [ ] `production` and `staging` keep their serving behaviour and cannot be removed from the model page.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ surface absent and the old behaviour unchanged.

## Notes for the implementer
Overlap: 5-F5.34 → T-268, 5-F5.35 → T-005. `T-268` writes the legacy `{project}/{number}` alias row for a version; do not write free-form aliases into that table or the legacy resolution breaks. Lowercase-only is deliberate: the alias is a URL fragment, so normalise nothing and reject instead of surprising a caller with a different name than the one typed.
