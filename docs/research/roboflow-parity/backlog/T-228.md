## User story
As an engineer feeding a TensorFlow detector, I want TFRecord shards with the image bytes and boxes in the record, so that the export drops straight into the pipeline.

## UX flow (LabelDesk words)
1. **Export dialog → TFRecord** — one chip whose hint reads "TensorFlow detection records; one shard per split". [empty: as T-224] [error: as T-224]
2. **Progress** — a large TFRecord build reports per-image progress like every other format. [loading: "Exporting… n%"]

## Backend changes
- Models/schema: none.
- Routers: none.
- Services/jobs: `app/services/exporters.py` — `export_tfrecord(m, src, out, should_stop)`: write `<split>/<file>.tfrecord` using the TFRecord container format with `struct` only — length (uint64 LE) + CRC32C of the length + payload + CRC32C of the payload; each payload is a `tf.train.Example` serialised **by a tiny local proto emitter** (the `Example` message is a handful of length-delimited fields: `image/encoded` bytes, `image/width`, `image/height`, `image/object/bbox/xmin/ymin/xmax/ymax` float lists, `image/object/class/text` bytes list). CRC32C is implemented in a 12-line table-driven helper — no protobuf, no tensorflow import, no new dependency.
- Permissions + workspace isolation: unchanged.
- Secrets/safefetch: none.
- OpenAPI: no.

## Acceptance criteria
- [ ] Records are valid TFRecord frames with correct CRC32C; a minimal parser reads back every field.
- [ ] One shard per split, one record per image; the writer adds no dependency.

- [ ] Flag off ⇒ the chip is absent from the new dialog.

## Notes for the implementer
TFRecord's CRC is **CRC32C (Castagnoli)**, not zlib's CRC32 — a zlib implementation produces files TensorFlow rejects with a confusing "Data loss" error. Keep the masked-crc variant (`((c >> 15) | (c << 17)) + 0xa282ead8`) used by the format.
