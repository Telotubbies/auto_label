## User story
As an ML engineer comparing my own checkpoint against a trained one, I want the same yardstick automatically, so that the number I quote is not from a different tool.

## UX flow (LabelDesk words)
1. **A validated upload** — the row moves from *Checking* to *Evaluating* (progress from the job) and then to its metric tiles; the badge stays *External weights*.
2. **Same panels** — confusion matrix, TIDE error breakdown, worst images, per-class counts, threshold default: all present because it is the same evaluation path. [empty: a version without test or valid images ⇒ the same "evaluation skipped" note a trained model gets]
3. **Compare** — the uploaded model appears in the Compare picker with its metric and latency, and the Pareto chart treats it identically. A model on another version is dimmed with "different dataset version".
4. **An artefact** — an ONNX row never enters Compare and its evaluation entry is absent with "This file is not runnable here."
5. **A failing evaluation** — the model stays usable and the card carries T-287's failure state.

- **States** — [empty: a split with no held-out images stores the same "evaluation skipped" note a trained model gets]. [loading: the row moves from *Checking* to *Evaluating* with the job's progress] [error: a failed evaluation renders T-287's failure state, not an error toast].

## Backend changes
- Models/schema: none.
- Routers: none new.
- Services/jobs: `handlers/training.py::run_weight_check` — on success, enqueue one `eval_model` job for the model (same helper T-283 uses) so the upload response's *Checking* is followed by *Evaluating*; refuse to enqueue for `runtime_refs.runnable is False` ("this file is not runnable here"). `services/evaluate.py` needs no change: an uploaded `.pt` resolves through the same `resolve("trained:<id>")` path.
- Permissions + workspace isolation: the evaluation job runs as the workspace context it builds (existing pattern); no new grant.
- Secrets/safefetch: none.
- OpenAPI: no.

## Tests to write first
pytest — `apps/backend/tests/test_uploaded_eval.py`:
- `test_a_validated_upload_enqueues_exactly_one_evaluation` — run the check handler → one `eval_model` job for the model, `model.status == "ready"`.
- `test_an_artefact_upload_gets_no_evaluation` — an ONNX row → zero `eval_model` jobs, `runnable is False`.
- `test_the_evaluation_writes_the_same_payload_keys` — a stubbed evaluator → `metrics.eval` contains `coco`, `per_class`, `f1_best`, `latency_ms`, exactly like a trained model.
- `test_an_uploaded_model_joins_compare_on_the_same_version` — after evaluation, `insights.compare([trained, uploaded])` returns both models with a Pareto list.
- `test_a_foreign_workspace_upload_is_never_compared` — the compare call with a foreign id → 404/400, no metric leak.
- `test_a_failed_evaluation_keeps_the_model_ready` — the evaluator raises → `eval_error` set, `status == "ready"`.
node — none: no new frontend surface.

## Acceptance criteria
- [ ] A validated upload is evaluated automatically with the same job kind and the same payload keys as a trained model.
- [ ] An artefact-only file is never evaluated and never compared.
- [ ] An uploaded model with an evaluation is comparable and deployable on the same version.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no automatic evaluation, uploads stay inert.

## Notes for the implementer
