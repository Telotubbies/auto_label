## User story
As an ML engineer, I want to list requests, filter them by state, model and duration, and open one as a
waterfall, so that a slow or failing call is a two-click answer.

## UX flow, click by click.
1. **Project → Traces** — `/:ws/p/:project/traces`: newest first, columns time, model, image, state, duration,
   and a link to the run when the trace came from a job. [empty: "No traces yet — run a prediction" with the
   link to Models] [loading: five skeleton rows] [error: "Traces could not be loaded" with *Try again*]
2. **Filter** — chips: `state:error`, `model:<name>`, `duration > 2000`, `run:<job id>`, `user:me`; a free-text
   box searches the trace name. [empty vs no-match are different screens: "no traces at all" versus "no trace
   matches these filters" with *Clear filters*]
3. **Open one** — the detail is linkable at `/:ws/p/:project/traces/:id`: the span waterfall with each span's
   duration and its share of the total, the slowest span highlighted, the attributes of the root (model,
   confidence, image), and *Copy trace id*. [error: a deleted or expired trace shows "this trace was removed
   by retention" and a link back to the list]
4. **A failed trace** — the failed span is red, the error text is printed verbatim, and the row offers *Retry*
   which re-runs the same request through the existing predict path.
5. **Save the view** — the current filters and columns become a named view stored per project. [empty: no
   saved views ⇒ the select shows only *All traces*]

## Backend changes
- Models/schema: `SavedTraceView(id, workspace_id, project_id, name, filters JSON, columns JSON, created_by,
  created)` in `apps/backend/app/models/evaluation.py`.
- Routers: `GET {P}/traces?filter=&limit=&cursor=` → `{traces: [...], next_cursor}`. The `filter` grammar is a
  deliberately small subset: `state:<ok|error|in_progress>`, `model:<id|name>`, `run:<job id>`, `user:me`,
  `duration>N`, `duration<N`, combined with spaces (AND only). An unparsable filter is a 400 naming the
  offending token. `GET/POST/DELETE {P}/trace-views` for saved views; `POST {P}/traces/{id}/retry` re-runs a
  playground-shaped request and returns a 202 with the new trace id.
- Services/jobs: `apps/backend/app/services/trace_query.py` (new) — `parse(filter) -> (clauses, rejected)`
  building SQLAlchemy conditions against indexed columns only (no JSON scan, no `LIKE '%…%'` on attributes);
  `page(db, project, filter, cursor, limit)` with a keyset cursor on `(started, id)`. Retry calls the existing
  playground `_run` path and needs no new job kind.
- Permissions + workspace isolation: `project.review` on every route; a trace id or saved view from another
  project is a 404.
- Secrets/safefetch: none. Dependency: none added (no `mlflow-skinny`), so no
  `THIRD_PARTY_LICENSES.md` change.
- OpenAPI: yes — regenerate both files.

## Acceptance criteria
- [ ] Traces list newest first with working state, model, run, duration and text filters, and a keyset cursor that never repeats a row.
- [ ] A trace detail is linkable by URL and shows a waterfall whose shares sum to one.
- [ ] Empty and no-match states are distinct screens.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ surface absent and the old behaviour unchanged.
