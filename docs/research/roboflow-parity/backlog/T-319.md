## User story
As the person shipping a pipeline, I want one panel that lists where this workflow can run with the one line each destination needs, so that deploy is a choice rather than six tutorials.

## UX flow (LabelDesk words)
1. **Workflows → Deploy** (`/:ws/:project/workflows/:id/deploy`, new tab beside the run panel) — a list of destinations, each with a one-line "best for": `Endpoint` (call it from an app), `Batch` (a folder of images, results later), `Stream` (a camera, continuous), `Edge device` (on-site hardware), `Batch file export`. [empty: nothing saved yet → every row is disabled with "Save the workflow first" and one link to the editor] [loading: five skeleton rows] [error: the destinations cannot be read → "Deployment options could not load." and the run panel still works]
2. **Endpoint row** — T-316's URL and snippet, plus the version the endpoint answers with: `v3 · live` once T-328 has published, `v3 · draft` while publishing is not in use.
3. **Batch row** — opens T-355's job dialog with this workflow pre-selected; when `task_354` is off the row says "Batch running is not enabled in this workspace."
4. **Stream row** — opens the Streams list with the workflow's model pre-selected; only offered when the workflow's first block is an `ultralytics`/`tensorrt` model ref, because that is what a stream worker can run. Otherwise the row carries "Streams run a single detection model; this workflow has crops or OCR." as its disabled reason.
5. **Edge row** — always disabled until T-358 exists, with the catalogue's reason from T-310; the row keeps its label so the option is visible and honestly unavailable.

## Backend changes
- Models/schema: none.
- Routers: `apps/backend/app/routers/workflows.py` — `GET /{workflow_id}/destinations` returning one row per destination `{id, label, best_for, available, reason, payload}`, where `payload` carries the invoke path, the published version number or the stream-ready model ref. Read-only.
- Services/jobs: `apps/backend/app/services/workflow_destinations.py` (new) — `DESTINATIONS` in fixed order and `rows(db, project, wf) -> list[dict]`; the stream readiness rule lives here as `stream_ref(wf) -> str | None`.
- Permissions + workspace isolation: `project_ctx` + `project.models`; a foreign workflow id is 404 through `svc.get`.
- Secrets/safefetch: none.
- OpenAPI: yes — one GET.

## Frontend changes
- Route: `/:ws/:project/workflows/:id/deploy` — a tab of the workflow editor, not a new top-level page.
- Nav entry: none (the workflow editor is reached from the project nav's Deploy group already).

- API client: `apps/frontend/src/lib/api/workflows.ts` — `workflowDestinations(ws, project, id)`.
- Feature flag: none — `task_31` gates the router and the editor.

## Acceptance criteria
- [ ] Five destination rows render in the fixed order, each with its "best for" line.
- [ ] A workflow with nothing saved disables all five with one shared reason and one link to the editor.
- [ ] The stream row is offered only when the workflow is a single detection model, and says why otherwise.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ `task_31` off hides the editor and the route, as today.

## Notes for the implementer
The edge row exists from day one and is always disabled; do not hide it, because "we cannot run on your hardware yet" is a truthful answer and a missing row is not. `export` is the existing dataset/CSV artefact path, so it links to T-355 rather than duplicating the writer.
