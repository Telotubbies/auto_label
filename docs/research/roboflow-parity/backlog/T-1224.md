## User story
As the merge captain, I want the Q2 findings — versions, training, compare, deploy — deduped and turned
into fix cards, so that the pipeline wave closes on measured trust rather than a demo that happened to
work.

## UX flow (LabelDesk words)
1. **Collect** — three area reports, three journey results and the performance report.
2. **Dedupe and severity** — one root cause, one finding; a perf overage is attributed or marked
   "unattributed".
3. **Fix cards** — one stub per S1/S2, plus one batched card for the S3s that share a file.
4. **Regression check** — rerun J1–J5 and areas 1–3; a new failure there is a Q2 regression, not a Q1
   leftover.
5. **Release note** — `docs/qa/releases/q2.md` with the metric table, budgets, open findings and accepted
   S3s.

## Acceptance criteria
- [ ] Every Q2 finding is filed or rejected with evidence; ids continue from Q1.
- [ ] Every budget row in the Q2 note has measured, budget and margin; a miss is S2 over 20 % and S3 under.
- [ ] A new failure in J1–J5 or areas 1–3 is filed as a regression with the Q2 change that caused it, or
      "unattributed" with the commit range.
- [ ] Every S1/S2 has a dispatchable stub with exclusive files and a named failing test.
- [ ] The metric table includes J6–J8 and the P2/P4 SUS-8 scores.
- [ ] The release note does not call the wave shipped while an S1 is open or a budget is unattributed.
- [ ] Empty, loading and error states: the failed-run, failed-export and 503-predict findings are present.
- [ ] Owner questions (Thai, real GPU, prices) are separated; none is answered by an agent.
- [ ] Workspace isolation: any cross-workspace finding is S1 and escalated.

## Notes for the implementer
The performance report is evidence, not a verdict: a number without the machine and build SHA is not
accepted. Keep the perf section short — the table is the content.
