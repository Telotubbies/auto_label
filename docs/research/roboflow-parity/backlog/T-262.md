## User story
As an ML engineer, I want the run to refuse what cannot work and to warn me about what will disappoint me, so that a five-image run or a second concurrent run never silently wastes the GPU.

## UX flow (LabelDesk words)
1. **Train → health chip** (T-261) — the chip's popover lists blockers first ("This dataset has 3 approved images — a fine-tune needs at least 5.") then warnings ("The test split is empty; the model will be scored on validation instead."), each with its remedy in the same line. [empty: no blockers and no warnings ⇒ the chip is green and the popover says "Nothing to fix."] [loading: the chip shows "Checking…" and Start is disabled until the first answer] [error: "The pre-flight check failed" + Retry; Start is disabled with that reason rather than starting blind]
2. **Start pressed with a blocker** — the API answers **400** with `{code, remedy}`; the form renders the same sentence on the dataset row and scrolls to it, so a stale tab cannot start a doomed run.
3. **A run is already active** — Start is disabled with "A run is already queued for this project — wait for it or stop it." and the API answers **409** with the remedy "stop the running job first". The queue is one deep per project, not per user.
4. **Warnings never block** — the amber chip still lets Start through, once, with a confirm ("2 warnings — train anyway?").

## Backend changes
- Models/schema: none.
- Routers: `GET {P}/train/preflight?version_id=&mode=current` → `{blockers: [{code, message, remedy}], warnings: [...], counts: {images, train, valid, test, classes, largest_class, smallest_class}, active_job_id: str | null}`. `POST {P}/train` calls the same service: a blocker ⇒ **400** `"…"` naming the remedy; an active `train`/`queued|running` job in the project ⇒ **409** `"a training run is already queued for this project — wait for it or stop it first"`.
- Services/jobs: new `apps/backend/app/services/train_preflight.py` — `RULES` list of `(code, level, message, predicate)`; it **imports** `versions_ready.rules(...)` (area 4's T-223) for the version-level facts and adds the train-only rules: `too_few_images` (blocker under 5 approved), `empty_train_split` (blocker), `thin_dataset` (warning under 20), `small_valid_split` (warning under 15 — reused by T-273's search gate), `small_test_split` (warning), `class_imbalance` (warning when largest/smallest instance ratio > 5), `rare_class` (warning under 3 instances). `preflight(db, project, version, mode) -> dict` and `assert_startable(db, project, version, mode)`.
- Permissions + workspace isolation: `c.perm("project.train")` on the preflight route (it reveals class counts); a foreign `version_id` is 400 "pick a generated version", a foreign project slug is 404.
- Secrets/safefetch: none.
- OpenAPI: yes — regenerate both files.

## Acceptance criteria
- [ ] One payload lists blockers and warnings with a remedy each; the chip and the start refusal agree word for word.
- [ ] A blocker is a 400 at the API, not only a disabled button.
- [ ] One active run per project: a second start is a 409 with the remedy, and a different project is unaffected.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no route, no 409, today's single validation message.

## Notes for the implementer
Numbers are fixed: floor 5 approved images (blocker), thin under 20 train images (warning), valid under 15 (warning — T-273 makes it a blocker for search), imbalance ratio > 5 (warning), rare class under 3 instances (warning). Do not add a general "class imbalance blocks training" rule; the row says warnings never block. If area 4's `versions_ready.py` (T-223) is not merged when you pick this up, keep the four version-level rules local to `train_preflight.py` and delete them when it lands.
