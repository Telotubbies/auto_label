## User story
As an MLOps engineer, I want an export delivered into the bucket my workspace already connected, so that I stop downloading a ZIP and re-uploading it by hand.

## UX flow (LabelDesk words)
1. **Export dialog → Send to storage** — a list of the workspace's storage connectors (name + kind only). [empty: "No storage connected yet — an admin can add one under Settings → Integrations." with the entry disabled] [loading: three skeleton rows] [error: "Could not load storage destinations — retry"]
2. **Send** — the button reads "Sending… 60%" while the artefact uploads, then "Delivered to <bucket>/exports/v3/coco.zip" with the object key. [error: "The bucket refused the upload: <reason>" inline, with the local ZIP still downloadable]
3. **Not available** — an Azure connector is listed with "Delivery to Azure containers is not supported yet." so nothing fails silently after a click.
4. **Permission** — a role without `project.export` never sees the section.

## Backend changes
- Models/schema: none — the destination is a `Connector` row (kind, encrypted config) and the delivery is a field on the export job.
- Routers: `POST /versions/{vid}/export` body gains `destination_id: str | None`; a foreign or unknown id is a 404 `destination_not_found`; `GET /versions/export-destinations` → `[{"id","name","kind","supported": bool, "reason": str}]` for workspace connectors, sanitised (no config).
- Services/jobs: `app/services/bucket_sink.py` (new) — `upload(conn, key: str, path: Path) -> {"key","bytes"}` reusing `connectors._config` (decrypted credentials), `connectors._import_boto3`/`_s3_client` and `_recheck_public` so credential handling and the SSRF guard stay in one home; `s3` uses `put_object`, `gcs` goes through its S3-interoperability endpoint when configured, `azure` raises `ValueError("azure containers are not supported for delivery yet")`, a missing SDK raises the same 501 the read path raises. The `export` job handler uploads after the ZIP is built and records `result.destination = {"id","kind","key"}`; `should_stop` is honoured between uploads.
- Permissions + workspace isolation: `c.perm("project.export")` on both routes; the connector is looked up by `workspace_id == c.ws.id`, so another workspace's connector is a 404; an admin-only credential surface stays admin-only (this route never returns config).
- Secrets/safefetch: credentials via `services/secretbox` (already encrypted at rest, decrypted only inside `_config`); the endpoint URL passes `connectors._recheck_public` / `safefetch.check_url` before any request.
- OpenAPI: yes — regenerate both files.

## Tests to write first

- `test_upload_puts_the_object_under_the_key` — a fake boto3 client records `put_object(Bucket=…, Key='exports/v3/coco.zip', Body=…)`; the returned `bytes` equals the file size.
- `test_credentials_are_decrypted_once` — `secretbox.encrypt_config` in the connector, and the fake client receives the plaintext key (proves `_config` is used, not the raw row).
- `test_azure_is_refused_with_a_readable_reason` — `ValueError` containing "not supported".

- `test_private_endpoint_is_refused` — `endpoint_url="http://169.254.169.254"` → `BlockedURL` before any client is built.
- `test_flag_off_is_404` — `task_230` off → the destinations route 404s and an export with `destination_id` is a 400 `destination_unavailable`.
- `test_a_foreign_connector_is_404` — a connector of another workspace.

## Acceptance criteria
- [ ] An export can be delivered to an S3-compatible connector; the job result names the object key and the byte count.
- [ ] Credentials never leave the service; a private endpoint is refused before a request; Azure fails with a stated reason.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ both routes 404/400 and the export menu has no destination section.

## Notes for the implementer
Reuse the connector's SDK path instead of hand-rolling SigV4 — one signing bug here is a credential leak or a silent no-op. The upload runs inside the existing `export` job, so no new job kind and no long request.
