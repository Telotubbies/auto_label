## User story
As a team lead, I want to see which images regressed and be stopped from deploying under my own rule, so that the gate I wrote is enforced by the product, not by memory.

## UX flow (LabelDesk words)
1. **Regression → a run** — header: pass rate, counts (passed / failed / errors), the delta against the baseline, and the run time.
2. **Per-image strip** — a grid of dots, one per image: green passed, red failed, grey error; hovering names the file and the first failed check. Clicking opens the image with its check list. [empty: a run with zero results (queued) shows "Waiting for the first image."]
3. **Per-check table** — check sentence, passed / total, and the most common failure value ("expected ≥ 3, saw 1" ×8).
4. **Compare to baseline** — a diff list: "3 images newly failing · 1 newly passing · harness count −4 overall".
5. **Deploy gate** — promoting a model on the Deploy page while the project's gate is unmet is refused: "Two suites are below their minimum pass rate: Counting 0.72 (min 0.90). Run them or change the rule." with links to each run. A workspace admin can still change the rule in the suite — there is no override button. [error: a promote that fails the gate returns 409 and the Deploy card keeps its previous model]

- **States** — [loading: a running suite shows the image count and a determinate bar, never an indefinite spinner].

## Backend changes
- Models/schema: none (T-292/T-293 ship the tables).
- Routers: `PUT {P}/deployments/{alias}` and `POST …/rollback` gain the gate check in the existing handler: read the project's suites with `gate_min_pass is not null`, take each one's latest `done` run, and **409** with `{code: "eval_gate", suites: [{id, name, pass_rate, min}]}` when any is below. `GET {P}/evals/runs/{run_id}` returns the per-check aggregation (T-293 stores per-image results; the route adds `checks: [{sentence, passed, total, top_failure}]`).
- Services/jobs: `services/deployments.gate_failure(db, project) -> list[dict]` — the single place the rule lives; the promote and rollback handlers both call it. `services/eval_checks.aggregate(results) -> list[dict]` for the per-check table.
- Permissions + workspace isolation: promote stays `c.need("admin")`; the gate payload exposes only the project's own suite names and rates.
- Secrets/safefetch: none.
- OpenAPI: yes — the new 409 shape and the aggregated route (regenerate both files).

## Tests to write first

- `test_a_passing_suite_allows_the_promote` — gate 0.9, run 0.95 → 200 and the alias moves.

- `test_a_suite_that_never_ran_does_not_block` — gate set, no run → 200 (an unrun suite is not evidence).
- `test_rollback_is_blocked_by_the_same_rule` — 409 on rollback too.
- `test_the_latest_done_run_is_the_one_judged` — an old failing run and a newer passing run → 200.
- `test_a_suite_without_a_gate_is_ignored` — 0.1 pass rate, no gate → 200.
- `test_flag_off_removes_the_gate` — `task_292` off → promote 200 even below the rate.
- `test_aggregate_reports_the_top_failure_value` — three failures with the same actual → `top_failure` names it and the count.

- `test_dot_grid_maps_three_states` — passed/failed/error results → three colours and counts.
- `test_delta_only_against_a_baseline` — no baseline → no delta text; with one → signed delta.
- `test_newly_failing_images_are_listed` — a file failing now and passing before appears in the diff with its name.

## Acceptance criteria
- [ ] A run shows pass rate, counts, per-image states, per-check aggregation and the baseline diff.
- [ ] A promote or rollback under an unmet gate is a 409 naming every suite, its rate and its minimum; the alias does not move.
- [ ] An unrun suite never blocks a deploy.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no results block and no gate.

## Notes for the implementer
The gate reads the **latest done** run only — never an average and never a running one. No override button: changing the rule is the override, and it is auditable in the suite's own history.
