## User story
As a labeler, I want a pixel mask saved on the image like any other shape, so that hair, foliage and transparency can be labelled without a hundred polygon points.

## UX flow (LabelDesk words)
1. **No screen changes in this card** — the brush tool is T-135. The observable change is that a saved mask round-trips through `GET /api/images/{id}` and appears in the Objects list with the kind `mask`.
2. **Payload** — a mask is `{"kind":"mask","size":[h,w],"counts":[…],"box":{"x","y","w","h"}}`: COCO-style uncompressed RLE, column-major, even-length counts, plus the normalised box used for culling, list ordering and training fallback.
3. **Rejections the user meets later** — a mask whose counts do not sum to `h*w`, a size outside `1–8192` pixels per side, or a mask that pushes one image past the cap returns 400/413 with a plain message the tool surfaces as "That mask is too large to save — paint a smaller region".
4. **Flag** — with `task_mask` off the brush tool and `PUT` of a mask are 404, but a mask previously written (by a workspace with the flag on, or before it was turned off) still loads, renders as its box outline and exports.

## Backend changes
- Models/schema: none — `Image.annotations` is JSON (`models/project.py:111`) and the array is the paint order.
- Routers: `PUT /api/images/{image_id}/annotations` (`images.py:534`) accepts `kind: "mask"` when `is_enabled("task_mask", db, c.ws.id)`; the whole-request cap becomes `len(json.dumps(annotations)) <= 4 MB` → `413 "annotations too large for one image"` in addition to the existing 5,000-annotation cap.
- Services/jobs: `services/masks.py` (new) — `encode(mask_array) -> shape`, `decode(shape, height, width) -> ndarray`, `validate(shape) -> shape` (raises `ValueError`), `box_of(shape)`; `images._check_ann` gains the `mask` branch and normalises counts to `int`.
- Permissions + workspace isolation: unchanged `image_ctx` write check; `project.annotate` is required, and a foreign image id stays 404.
- Secrets/safefetch: none.
- OpenAPI: yes — the annotations request is documented with the new shape example.

## Acceptance criteria
- [ ] A mask saves and reloads byte-identically, appears in the Objects list as `mask`, and participates in stack order like every other shape.
- [ ] Malformed, oversized or off-size masks are rejected with 400/413 and never partially stored.
- [ ] With `task_mask` off, mask writes are 404 while polygons and boxes still save, and a stored mask still loads.
- [ ] One image cannot exceed 4 MB of annotation JSON; the message names the limit.
- [ ] Empty, loading and error states above all render (a stored mask without a decodable bitmap renders its box outline, never a crash).
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ the mask write is absent (404) and the brush tool is not rendered.
- [ ] Keyboard-only path: not applicable in this card; T-135 owns the brush keys.

## Notes for the implementer
Store `counts` as COCO uncompressed RLE (alternating run lengths, starting with zeros) so COCO export is a copy, not a conversion. `size` is `[height, width]` — the same order COCO uses; the box is derived and stored only to keep culling and training cheap.
