# T-1317 — Four alert rules, one checker, one runbook each

| Field | Value |
| --- | --- |
| Wave | O (security, monitoring, performance) |
| Area | Monitoring / operations |
| Size | 3 agent-hours |
| Role | R12 SRE + R3 backend |
| Skills | ponytail, test-driven-development, documentation-writer, verification-before-completion |
| R7 security review | yes — sends mail and reads platform state |
| Depends on | T-1302, T-1311 (the series), T-1301 (`readyz` shape) |
| Feature flag | `LD_ALERT_CHECK=0` disables the job; thresholds are env vars |

## Problem
Nothing watches the platform. Disk exhaustion, a wedged queue, a 5xx spike and a missing worker are
discovered by a user. `docs/runbooks/recovery-after-shutdown.md` handles "it already broke"; there is no
"it is about to break".

## Design
One job, one evaluator, four rules, four runbooks. No Alertmanager, so alerts work on the default stack
without the monitoring profile.

- `app/services/system_check.py` (new, ~95 lines):
  - `THRESHOLDS` from config: `LD_ALERT_DISK_GB=5`, `LD_ALERT_QUEUE_S=900`, `LD_ALERT_ERROR_RATE=0.02`,
    `LD_ALERT_WORKER_S=300`.
  - `evaluate(db, metrics) -> list[dict]` returns `[{rule, firing, value, threshold, since}]`, pure and
    unit-testable. Inputs: disk free bytes, oldest-queued seconds, workers online, and the 5xx/total rate
    parsed from the metrics registry (or from one HTTP scrape of `/api/metrics` when the job runs in a
    separate worker process; the URL and token come from `LD_METRICS_URL`/`LD_METRICS_TOKEN`).
  - Rules exactly as the monitoring plan §4.7: `disk_low`, `queue_stuck` (queued age AND zero workers),
    `error_rate_spike` (ratio AND ≥ 20 rps), `worker_missing` (zero workers AND queued > 0).
  - `notify(rule, state)`: one email through the existing `mailer` to `LD_OPS_ALERT_EMAIL` falling back to
    `LD_SUPERADMINS`; when neither is set, `log.critical` with the rule and value and return.
  - Dedupe: one message per rule per hour, a module dict `{rule: last_sent}`; a recovered rule sends one
    "recovered" line.
- `app/handlers/ops.py`: `run_system_check(job)` handler, `HANDLERS = {..., "system_check": …}`.
- `config.py`: `"system_check"` appended to `LOCAL_JOB_KINDS` defaults so the worker claims it.
- `app/worker.py` `_schedule_ops()`: enqueue `system_check` every `LD_ALERT_EVERY_S` (default 300 s) when
  none is queued (the existing self-throttled scheduler pattern, ~10 lines).
- Four runbooks in `docs/runbooks/alerts/`: `disk-low.md`, `queue-stuck.md`, `error-rate.md`,
  `worker-missing.md`. Each: symptom, what the alert means, first three commands, decision tree, how to
  silence, what to tell the owner, and what a false positive looks like.

## Tests to write first
`apps/backend/tests/test_system_check.py`:
- `test_disk_low_fires_at_the_boundary` — 4.9 GiB fires, 5.1 GiB does not.
- `test_queue_stuck_requires_a_stale_queued_job_and_no_worker` — stale queue with a worker online does
  **not** fire (that is a busy worker, not a stuck queue).
- `test_worker_missing_requires_queued_work`.
- `test_error_rate_spike_needs_the_rate_floor` — 50 % errors at 2 rps does not page.
- `test_recovery_sends_one_message`.
- `test_dedupe_is_one_per_hour`.
- `test_no_recipient_logs_critical_and_does_not_raise`.
- `test_the_job_is_registered_and_claimed` — `HANDLERS` has it, `LOCAL_JOB_KINDS` contains it,
  `missing_handlers()` is empty.
- `test_each_runbook_file_exists_for_each_rule` — loop over the four rule names.
- `test_notify_never_blocks_on_smtp` — a mailer that raises does not fail the job.

## Acceptance criteria
- [ ] Four rules, each with a boundary test and a runbook whose filename matches the rule.
- [ ] One email per rule per hour, one recovery message, no mail storm.
- [ ] With no recipient configured the job logs CRITICAL and exits normally.
- [ ] The check costs < 50 ms and one DB query set; it never runs inside a request.
- [ ] A broken mailer, a broken `/metrics` scrape or a missing data dir cannot fail the worker loop.
- [ ] The four thresholds are env-tunable and documented in `deploy/.env.example`.

## Notes for the implementer
Reuse `mailer` and the existing job queue; do not add Alertmanager, a webhook service or a second
scheduler thread. Read the four runbooks' "first three commands" back to yourself: each must be a
command the owner can paste into the VM (`df -h`, `docker compose ps`, `docker compose logs --tail=100
worker`, `curl -fsS localhost/api/readyz`). Typo guard: the config name is `LD_SUPERADMINS`.
