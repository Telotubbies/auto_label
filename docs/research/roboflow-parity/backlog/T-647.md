## User story
As a safety officer whose real label is compliance rather than detection, I want five standing questions answered per image and stored as filterable values, so that "vest not worn" becomes a query and a review task instead of a new shape type nobody understands.

## UX flow (LabelDesk words)
1. **Classes & Tags → Question set** (`/:ws/:project/classes`) — three to five questions with yes/no answers and one rule line ("answer no → tag `review:vest`"). This card stores them and answers them.
2. **Dataset → select → Answer questions** (`/:ws/:project/browse`) — a job answers each selected image; a failed image keeps its previous answers and is counted. [loading: "Answering 4 questions on 120 images…"] [error: "image analysis on a hosted model is off for this workspace" when the gate refuses]
3. **Grid** — answers arrive as columns and as chips that filter (`?attr=vest:no`), through the existing query-parameter surface.
4. **Rule** — an answer of `no` adds the configured tag, which then drives the existing tag filter; no new label type, no new shape.
5. **Flag off** — no question set, no answers, no columns.

## Backend changes
- Models/schema: `images.attributes` JSON, nullable (default `{}`), one `IMAGES["attributes"] = "JSON"` line in `app/schema/dataset.py`; question sets stay in `Project.settings["questions"] = [{"key", "text", "review_tag"}]` — no second table. The answer shape is `{"<key>": {"answer": "yes"|"no"|"unknown", "source": "vlm", "at": <epoch>}}`.
- Routers: new `app/routers/attributes.py` — `PUT /api/ws/{ws}/projects/{project}/questions` (3–5 questions, keys `[a-z0-9_]{1,24}`, text ≤ 200 chars, one optional `review_tag`) → 200 with the stored set; `POST .../questions/answers` (`image_ids` ≤ 500 or `batch_id`) → 202 job; `GET .../questions` → the set plus a per-key answered count. And `GET .../images` gains `attr: str = ""` (`"vest:no"`) filtering on the JSON value, SQL-portable like the existing `_tag_filter`.
- Services/jobs: `services/attributes.py` (new) — `clean_questions(raw)`, `answer_image(vlm, im, questions) -> dict` (one call per image with all questions in one prompt, strict yes/no JSON), `apply_rule(db, img, answers)` adding the tag; `handlers/insights.py`-style job kind `image_questions` with `run_job(job)` writing answers per image and returning `{"answered", "failed", "images"}`; `config.LOCAL_JOB_KINDS` gains `image_questions`.
- Permissions + workspace isolation: `project.classes` to edit the set, `reviewer` to run, `project.read` to read answers; `_visible()` still hides a labeler's unassigned images, and an image id from another project is 404 through `project_ctx`.
- Secrets/safefetch: `services/secretbox.py` holds a hosted endpoint token if one is stored; no image leaves the deployment unless `workspaces.ai_egress` is true (T-640's `ai_egress.require`).
- OpenAPI: yes — regenerate (`python tools/export_openapi.py`, `npm run gen:api-types`).

## Acceptance criteria
- [ ] Three to five questions are stored once and answered per image by one job, with `yes`, `no` and `unknown` all storable.
- [ ] Answers filter the grid through a URL parameter and a failed image is counted without losing its previous answers.
- [ ] A rule turns a `no` into a tag exactly once, so the review work appears as a query.
- [ ] Empty, loading and error states above all render: an image with no answers returns `{}`, a running job counts progress, a refused gate is a 409 sentence.
- [ ] Workspace A cannot answer or read workspace B's images (404, not 403).
- [ ] Flag off ⇒ no question set, no answer job, and `attributes` absent from image payloads.

## Notes for the implementer
One model call per image carrying all questions, not one call per question — five questions on 500 images is 500 calls, and the pass is priced accordingly. `unknown` exists so a model that cannot see the detail is countable instead of guessed. Keys are stable identifiers: renaming a question's text keeps its key, so old answers stay joinable.
