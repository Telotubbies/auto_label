## User story
As the person who trained the model, I want to write the four paragraphs only I can write and see the card as the reader will, so that the handover document takes ten minutes instead of an afternoon in a text editor.

## UX flow (LabelDesk words)
1. **Model page → Card** (`/:ws/:project/models?model=<id>&tab=card`) — the tab opens on the live revision when one exists, otherwise on the generated draft. [empty: "Fill Intended use, Not for, Known failure modes and Contact before publishing." listed as a checklist] [loading: the tab shows the form skeleton, the model header stays]
2. **Author** — four text areas with their hints; the generated facts sit above in a read-only block and cannot be edited into the text. [error: publishing with a missing field focuses it and prints the API's sentence naming it]
3. **Preview** — a toggle renders the Markdown as the reader will see it, with the revision number and publish state.
4. **Publish** — freezes the revision; the tab shows `Revision {n}` and the publish time, and the model page's subtitle names the live revision.
5. **Download bundle** — the action names the three files it will contain; a model without weights shows it disabled with the API's reason. [loading: the button shows pending while the zip is built]

## Acceptance criteria
- [ ] The Card tab pre-fills from the run and asks only for the four prose fields.
- [ ] Publish is refused while a field is empty, names it, and focuses it.
- [ ] Publishing freezes a revision; the tab and the model subtitle both name the live revision.
- [ ] Empty, loading and error states above all render: a first visit shows the checklist, a missing field is named, and the bundle action explains itself.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no Card tab and the model page is unchanged.

## Notes for the implementer
The generated facts block is read-only by construction — render it from the API payload, never from the text areas. Keep the four fields in the fixed order the API validates (intended use, not for, failure modes, contact) so the error sentence and the form agree.
