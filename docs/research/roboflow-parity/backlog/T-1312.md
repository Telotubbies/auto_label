# T-1312 — Optional OpenTelemetry traces behind `LD_OTEL=1`

| Field | Value |
| --- | --- |
| Wave | O (security, monitoring, performance) |
| Area | Monitoring |
| Size | 2.5 agent-hours |
| Role | R3 backend |
| Skills | ponytail, test-driven-development, verification-before-completion |
| R7 security review | no — but span attributes must not carry secrets (asserted) |
| Depends on | T-1300 (request id in the log line lets a span be joined to it) |
| Feature flag | `LD_OTEL=1` + `LD_OTEL_ENDPOINT`; off by default, module not imported when off |

## Problem
A slow request that spends 300 ms in SQL and 900 ms in Pillow is indistinguishable from a slow network,
and a 5-minute job has no breakdown at all. Logs alone cannot show the shape of a request.

## Design
- `app/tracing.py` (new, ~60 lines):
  - `install(app)`: returns immediately unless `LD_OTEL=1`; then builds a `TracerProvider` with a
    `BatchSpanProcessor` over an OTLP/HTTP exporter (`LD_OTEL_ENDPOINT`), a `Resource` with
    `service.name="labeldesk-api"` and `service.version=APP_VERSION`, and instruments FastAPI only.
  - `span(name, **attrs)` context manager used by the worker: one `job.run` span with `job.kind`,
    `job.id`, `job.status` (set on exit).
  - `LD_OTEL_SAMPLE=0.1` (default 1.0 when enabled) so a production host does not trace everything.
- `app/worker.py`: `with tracing.span("job.run", kind=job.kind, job_id=jid):` around `run_one`'s body —
  one line, wrapped so the no-op path costs a function call.
- The request id is attached to the server span as `http.request_id`, so a trace and a log line match.
- No SQLAlchemy instrumentation (noisy and slow; the query-count card covers N+1). No log exporter.

## Files
Exclusive:
- `apps/backend/app/tracing.py` (new)
- `apps/backend/tests/test_tracing.py` (new)
Shared (one line each):
- `apps/backend/app/main.py` — `tracing.install(app)` after middleware setup
- `apps/backend/app/worker.py` — the `span(...)` wrapper around `run_one`
- `apps/backend/app/config.py` — `OTEL`, `OTEL_ENDPOINT`, `OTEL_SAMPLE`
- `apps/backend/requirements.txt` — `opentelemetry-sdk`, `opentelemetry-exporter-otlp-proto-http`,
  `opentelemetry-instrumentation-fastapi` (versions pinned to the same minor line)
- `deploy/docker-compose.yml` + `deploy/.env.example` — the three env vars, empty by default

## Tests to write first
`apps/backend/tests/test_tracing.py`:
- `test_disabled_means_no_import` — with `LD_OTEL` unset, `sys.modules` has no `opentelemetry` entry
  after a fresh import of `app.tracing`.
- `test_enabled_installs_one_provider` — with an in-memory exporter, one server span per request, named
  `GET /api/healthz` (or the route template).
- `test_span_carries_the_request_id` — the same id as the response header.
- `test_job_span_has_kind_and_status` — run a stub job; attributes `job.kind`, `job.id`, `job.status`.
- `test_no_secret_in_span_attributes` — a login request's span carries no password, token or API key.
- `test_sampling_is_honoured` — a deterministic sampler stub at 0.0 exports nothing.

## Acceptance criteria
- [ ] Without `LD_OTEL`, the package is not imported and startup time is unchanged (report a timing).
- [ ] With it, requests and jobs produce spans that join to the log line by request id.
- [ ] Span attributes never include headers, bodies, passwords, tokens or file paths.
- [ ] The exporter failure path (endpoint down) never fails a request or a job; one log line per minute.
- [ ] Three env vars documented in `deploy/.env.example`.

## Notes for the implementer
Import inside the function (`from opentelemetry import trace` in `install`), never at module import, so
the default deployment pays nothing. Do not add `opentelemetry-instrumentation-sqlalchemy` or
`-logging`. If pinning three OTel packages is awkward, pin `opentelemetry-sdk==<x>` and let the other
two follow the same release; tests must fail loudly on a mismatch (one import assert).
