## User story
As the manager of a project inside a labour dispute, I want to freeze its footage and see exactly what a sweep would delete before it runs, so that a scheduled job cannot destroy the evidence we are about to need.

## UX flow (LabelDesk words)
1. **Settings → Privacy → per-project row → `Preview`** (`/:ws/settings/privacy`) — a dialog shows counts per data class ("412 frames, 88 event clips, 3 cached exports"), a storage figure and 20 thumbnails, over the line "Nothing is deleted by a preview." [empty: "Nothing matches these rules yet."] [loading: "Counting what would be deleted…" with the dialog open and `Delete nothing` as the only button] [error: "The preview could not finish — 3 files are locked by another process." with `Try again`]
2. **`Freeze this project (legal hold)`** — a dialog takes a reason, an owner and a review date. On save, the project header shows a red banner: "Under legal hold until 1 Dec 2026 — nothing in this project can be deleted."
3. **A sweep while the hold is on** — the run log records "skipped: legal hold" and every delete path answers `[error: this project is under legal hold until 2026-12-01]`, including the image delete and the workspace trash purge.
4. **Release the hold** — owner or admin only, with the reason re-typed; the banner disappears and one audit row records who released it.
5. **Sweep run log** — the project row lists the last five runs with time, counts and failures ("3 files were locked — retried at 03:10"). [empty: "No sweep has run for this project yet."]

## Backend changes
- Models/schema: `LegalHold(id, workspace_id, project_id, reason, owner_id, review_at, created, released_at, released_by)` in `app/models/policy.py`; `projects` gains `legal_hold_until FLOAT NULL` and `legal_hold_reason VARCHAR(255) DEFAULT ''` in `app/schema/dataset.py` (`PROJECTS`); no backfill.
- Routers: `app/routers/policies.py` — `GET /api/ws/{ws}/projects/{project}/retention/preview` (counts, `bytes`, 20 signed thumbnails, `nothing_deleted: true`), `POST …/retention/hold` and `DELETE …/retention/hold` (422 on a missing reason or a review date in the past), `GET …/retention/runs` (last five `retention.run` audit rows reshaped).
- Services/jobs: `app/services/retention_preview.py` (new) — `preview(db, project, rules) -> dict` reusing `retention.count_events`, `Image` counts and `_stale_versions`; `app/services/legal_hold.py` (new) — `active(project) -> bool`, `guard(project) -> None` raising `HTTPException(409, "this project is under legal hold until …")`. `services/retention._clean_project` and `services/erasure.delete_project_data` call `legal_hold.guard` first and return `skipped: "legal_hold"` in the stats.
- Permissions + workspace isolation: `workspace.update` to place or release a hold, `project.privacy` to preview; the project is resolved through `project_ctx`, so a foreign slug is 404. Only the workspace owner may release a hold the workspace owner did not set.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Tests to write first
pytest — `apps/backend/tests/test_retention_preview.py`:
- `test_preview_counts_and_deletes_nothing` — a project with two images older than its 30-day window → `GET …/retention/preview` reports `images: 2` and `nothing_deleted: true`, and both image rows still exist afterwards.
- `test_preview_returns_twenty_signed_thumbnails_at_most` — 30 expired images → the sample list has exactly 20 entries, each a signed path.
- `test_hold_blocks_the_sweep` — place a hold with a future `review_at` → `retention.run_retention` for that project returns `skipped: "legal_hold"` and the image rows survive.
- `test_hold_blocks_image_delete_and_trash_purge` — with the hold on, `DELETE /images/{id}` and the trash purge both answer 409 carrying the hold date.
- `test_hold_needs_a_reason_and_a_future_review_date` — `POST …/retention/hold` with `reason=""` and with `review_at` yesterday → both 422.
- `test_only_an_owner_releases_a_hold` — an admin who did not place the hold answers 403; the owner releases it and one `retention.hold.release` audit row exists.
- `test_hold_from_another_workspace_is_404` — a project slug from workspace B under workspace A's path → 404.
- `test_flag_off_keeps_todays_behaviour` — with the flag off, the hold route 404s and a sweep deletes exactly as before.

node — `apps/frontend/tests/legal-hold.test.mjs`:
- `test_hold_banner_names_the_date` — `holdBanner({legal_hold_until: 1798761600})` contains the formatted day and the word "hold".
- `test_preview_totals_sum_the_classes` — `previewTotals({images: 2, events: 3, exports: 1})` is `6` items and the storage string uses the shipped byte formatter.
- `test_a_locked_file_is_named_as_a_retry` — `runLine({failed: 3})` reads "3 files were locked — retried on the next sweep".

## Acceptance criteria
- [ ] Preview returns counts, a storage figure and at most twenty samples, and changes nothing.
- [ ] A legal hold blocks the scheduled sweep, single-image delete and workspace trash purge, each naming the hold date.
- [ ] Only the owner (or the admin who placed it) can release a hold, and the release is audited.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no preview, no hold banner, routes 404, and the sweep is byte-for-byte today's behaviour.

## Notes for the implementer
Owner-gated: whether legal hold is available to every workspace or only on a contract, who may release one, and how long a released hold's record is kept (INDEX §4.3). The guard belongs in `_clean_project` and `delete_project_data`, not in the route: a hold that only covers the button someone remembered is worse than no hold. A hold never expires by itself — the review date is a reminder, not an automatic release.
