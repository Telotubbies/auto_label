## User story
As the owner of a client workspace at an agency, I want to hand it to another admin before I leave, so that the workspace is neither abandoned nor stuck with an account nobody can sign into.

## UX flow (LabelDesk words)
1. **Settings → Members → the owner row → `Transfer ownership`** (`/:ws/settings/members`) — the row's menu gains the action, visible to the owner only. [loading: the row's shipped table skeleton] [error: the table's shipped "Could not load members" with **Try again**]
2. **The dialog** — one `Select` of members who are admins ("They must already be an admin. Make them one first."), the sentence `"You keep full access as an admin, but only Somchai can hand the workspace on."` / `"คุณยังเข้าถึงได้เต็มที่ในฐานะผู้ดูแล แต่คุณสมชายเท่านั้นที่โอนเวิร์กสเปซต่อได้"`, and a `Transfer` button that opens the step-up sheet.
3. **The recipient's side** — an email with one link and, signed in, a banner on Members: `"Chaiyaporn wants to give you this workspace. Accept or decline."` with both buttons. Accepting asks for the recipient's own step-up (the same sheet).
4. **Accepted** — the page reloads as the new owner, an audit row `ownership.transfer` names both accounts, and the previous owner's member row reads `Admin`.
5. **Declined or expired after 7 days** — the owner's row reads `"The offer to Chaiyaporn expired. Send it again."` and nothing changed. [empty: no pending transfer ⇒ no banner]
6. **A second transfer while one is pending** — refused: `"Send the current offer again or cancel it first."`

## Backend changes
- Models/schema: `app/models/compliance.py` (new) — `OwnershipTransfer(id, workspace_id FK CASCADE, from_user FK users, to_user FK users, token VARCHAR(64) PK default token_urlsafe(24), created FLOAT, expires FLOAT, accepted FLOAT null, declined FLOAT null)`. One row per workspace at a time (checked in the service, not a constraint — a retry after a decline is the same shape). No `ADD COLUMN`; the table is created from metadata.
- Routers: in `app/routers/workspaces.py` — `GET /api/ws/{ws}/owner/transfer` → the pending offer `{token, to, to_name, expires}` or `null`; `POST /api/ws/{ws}/owner/transfer {user_id}` (owner only, `Depends(step_up)`) → 201 with the offer and sends the mail; `POST /api/ws/{ws}/owner/transfer/{token}/confirm` (the named recipient, `Depends(step_up)`) → `{owner_id}`; `POST …/{token}/decline` → `{ok}`; `DELETE …/{token}` (owner cancels). 404 for a foreign token, 403 for a caller who is not the recipient, 409 for a second pending offer.
- Services/jobs: `app/services/ownership.py` (new) — `offer(db, ws, actor, to_user) -> OwnershipTransfer` (validates: actor is the owner, recipient is a member, recipient's `Member.role == "admin"`, no live offer), `pending(db, ws)`, `apply(db, transfer) -> None` (sets `ws.owner_id`, ensures the recipient's `Member.role = "admin"`, demotes the previous owner's `Member.role` to `"admin"`, writes `ownership.transfer` with `from`/`to` names and one `member.role` row), `cancel`, `decline`, `EXPIRES = 7 * 86400`. The email goes through the shipped `mailer.send(..., kind="ownership")`.
- Permissions + workspace isolation: the offer route checks `c.ws.owner_id == c.user.id` (not the admin role — an admin cannot take the workspace); confirm resolves the token inside `c.ws.id`, so a token from another workspace is 404; the recipient must be a `Member` of this workspace.
- Secrets/safefetch: none — the token is a random string stored in its own row (like `Invite.token`), the email contains a `PUBLIC_URL` deep link, and no URL is fetched.
- OpenAPI: yes — five routes and the offer payload.

## Acceptance criteria
- [ ] The owner offers the workspace to an admin member, the recipient accepts by email link, and `ws.owner_id` changes with one audit row naming both accounts.
- [ ] The previous owner stays an admin member; nobody loses access by being transferred away.
- [ ] A non-owner cannot start or confirm a transfer, and a token from another workspace is 404.
- [ ] Empty, loading and error states above all render: no pending offer shows no banner, the dialog's loading state is the submit spinner, and the expired offer shows its sentence.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ the action is absent and the API keeps today's explicit `"ownership transfers are not supported"` refusal.

## Notes for the implementer
Two confirmations, both with a step-up: the outgoing owner proves it is them, the incoming owner proves it is them. Keep the 7-day expiry in the service, not in the mail text. Do not relax the `role="owner"` refusals in `invite()` and `set_role()` — those close a privilege-escalation path, and this flow is the only door to the owner role.
