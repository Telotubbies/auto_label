## User story
As a project manager, I want to see old-versus-new before a rename lands, and to freeze the class list, so that "car" and "vehicle" merge in one reviewed step and nobody mints a class mid-batch.

## UX flow (LabelDesk words)
1. **Classes & tags → a row's name → edit** — names become editable in place; a **Review changes** button appears once anything differs. [empty: no edits → the button is absent]
2. **Diff sheet** — each change as a row: old name, an arrow, new name, and what it means — "renames 41 annotations", or "merges into "vehicle": 128 annotations move, "car" disappears". A rename whose new name matches another class is labelled **Merge** and cannot be undone by renaming back (the source row is gone). [error: a name that is not alphanumeric plus `-` → the row is marked and Confirm is disabled with the rule shown]
3. **Confirm changes** — applies every change in one transaction, shows "3 classes updated · 169 annotations relabelled", refreshes the class list and the editor's class picker. [loading: the confirm spins; the sheet cannot be dismissed while it runs]
4. **Lock classes** — a switch at the top of the class card: "Lock classes · nobody can add or rename a class". With it on, the New class field, the row edit affordances, the editor's "New class…" field and the free-text object search disappear; the per-class segmentation tool (Smart Polygon) stays, because it labels an existing class.
5. **Who may do it** — both actions need `project.classes`; a labeler who may mint classes while unlocked loses that ability when locked, and the editor says "Classes are locked by a project manager".
6. **Reversible** — unlocking is immediate and needs no confirm; it never re-creates a merged class.

## Backend changes
- Models/schema: none — names live on `LabelClass`, the lock in `Project.settings`.
- Routers: `POST /classes/rename-preview` `{changes: [{id, name}]}` → `[{id, old, new, action: "rename"|"merge", affected}]` (no writes); `POST /classes/rename` applies the same body after re-validating (409 if a row changed since the preview), reusing the existing merge path (`projects.py:312`) for collisions; `POST /classes/lock` `{locked: bool}` writes `settings.classes_locked` and audits `classes.lock`; `POST /classes` returns 400 `"classes are locked"` while locked.
- Services/jobs: `services/class_admin.py` (new) — `preview_changes(db, project, changes)`, `apply_changes(...)` (rename non-colliding first, then merge into the target), `is_locked(project)`, `set_locked(...)`; the annotation relabel happens through the existing class merge, which already rewrites every image.
- Permissions + workspace isolation: `project.classes` on all four routes; every class id is validated against `c.project.id`, so a foreign id is 400/404.
- Secrets/safefetch: none.
- OpenAPI: yes — three routes.

## Frontend changes

## Acceptance criteria
- [ ] A rename set shows old, new, action and affected count before anything is applied; a collision is labelled Merge.
- [ ] Confirm applies all changes in one transaction, relabels every affected annotation and leaves no orphan class index rows.
- [ ] Locking the class list removes every add/rename affordance in Classes and in the editor, while Smart Polygon still labels existing classes.
- [ ] Only `project.classes` holders can rename or lock; unlocking is immediate.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no lock switch and no lock behaviour; the rename diff still works.
- [ ] Keyboard-only path: Classes → Tab to a name → edit → Tab to Review changes → Enter → Tab Confirm → Enter.

## Notes for the implementer
Apply order matters: rename the non-colliding rows first, then merge colliders into their target, or a swap pair (`car`→`vehicle`, `vehicle`→`car`) deadlocks on the unique constraint. Merge keeps the target's colour, as the existing merge does.
