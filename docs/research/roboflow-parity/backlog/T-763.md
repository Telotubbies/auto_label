## User story
As the reviewer who signs off a pilot, I want a sandbox key to be visibly fake and a promotion to show me exactly what changes before two of us approve it, so that "we tested it" cannot quietly become "it is running the line".

## UX flow (LabelDesk words)
1. **Settings → API Keys inside a sandbox** (`/:ws/settings/api`) — a new key reads "Created — copy it now, it is shown once." and starts `ld_test_`; the list row carries the chip "Test key". [empty: "No keys yet — a sandbox key starts with ld_test_ and is refused by production inference."]
2. **A sandbox key against production inference** — `[error: this is a test key; production inference refuses keys minted in a sandbox]` with 403, and the attempt is in the audit log.
3. **Attaching a sandbox model to a production camera** (`/:ws/:project/streams`) — `[error: sandbox models cannot be attached to a production camera]` with 409 and the camera row unchanged.
4. **`Promote to production`** — opens a diff: dataset versions, class list additions/removals, and metric deltas per model, each marked added/changed/removed. `Request approval` needs a second manager; the request shows "Waiting for a second approver" and the same person cannot approve their own request. [empty: "Nothing in this sandbox is ready to promote yet."] [loading: the diff renders skeleton rows] [error: "This sandbox is not linked to a production workspace, so there is nothing to promote into."]
5. **Approved** — one audit row names both people and the applied diff; the production project gains the copied versions and classes.

## Backend changes
- Models/schema: `Promotion(id, sandbox_workspace_id, target_workspace_id, project_id, plan JSON, requested_by, requested_at, approved_by, approved_at, state, applied_at)` in `app/models/identity.py`; no new column elsewhere.
- Routers: `app/routers/environments.py` — `GET /api/ws/{ws}/projects/{project}/promotion` (the diff or `null`), `POST …/promotion` (201, `state="pending"`), `POST …/promotion/{pid}/approve` (409 when the caller requested it, 200 with `state="applied"`), `DELETE …/promotion/{pid}` (withdraw, requester only); `POST /api/ws/{ws}/keys` passes `test=is_sandbox(ws)`; the stream create/update path calls `environments.guard_model_ref`.
- Services/jobs: `app/services/promotion.py` (new) — `diff(db, source, project) -> dict` (versions added, classes added/removed, metric deltas), `apply(db, promotion) -> dict` (copies version rows and classes by value, never image bytes), `can_approve(promotion, uid) -> bool`; `app/security.new_api_key(publishable=False, test=False)` returns `ld_test_` / `ld_test_pub_` prefixes; `app/apikeys.resolve_key` refuses a `ld_test_` token with 403 and one audit row.
- Permissions + workspace isolation: promotion needs `workspace.update` in both workspaces and a manager role on the project; a project from another workspace is 404; the target workspace must be the one named by `sandbox_of`, never one supplied by the client.
- Secrets/safefetch: none — key material is generated by `security.new_api_key`; nothing new is stored in the clear.
- OpenAPI: yes.

## Tests to write first
pytest — `apps/backend/tests/test_promotion.py`:
- `test_a_sandbox_key_starts_with_ld_test` — sandbox admin → `POST /keys` → the returned key starts `ld_test_` and the row carries `prefix` beginning `ld_test_`.
- `test_a_production_workspace_mints_a_normal_key` — production admin → the key starts `ld_` and never `ld_test_`.
- `test_a_test_key_is_refused_by_production_inference` — `ld_test_` bearer against an inference route → 403 with "test key" in the detail and one `apikey.use` audit row.
- `test_a_sandbox_model_cannot_attach_to_a_production_camera` — production project, `model_ref` naming a sandbox model → `POST /streams` and `PATCH /streams/{sid}` both 409 and the row keeps its old `model_ref`.
- `test_the_requester_cannot_approve` — request a promotion, approve it as the same user → 409; a second manager approves and `state` becomes `applied`.
- `test_an_unlinked_sandbox_has_nothing_to_promote` — a sandbox whose `sandbox_of` is empty → `GET …/promotion` returns `null` with `reason="unlinked"`.
- `test_flag_off_keeps_keys_and_streams_unchanged` — with the flag off → keys still `ld_`, a test-shaped key is not minted, and the promote routes 404.

- `test_the_approver_button_is_disabled_for_the_requester` — `canApprove({requested_by:'u1'}, 'u1')` is false, `('u2')` is true.
- `test_a_test_key_chip_says_what_it_means` — `keyChip('ld_test_abc')` reads "Test key" and `keyChip('ld_abc')` is `null`.

## Acceptance criteria
- [ ] A sandbox key starts `ld_test_`, is chipped "Test key", and is refused by production inference with 403.
- [ ] A sandbox model cannot be attached to a production camera from either the create or the update path.
- [ ] A promotion shows a real diff, needs a second approver, and records both people in one audit row.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ today's key prefixes, no chip, no promote entry, routes 404.

## Notes for the implementer
The gate is the prefix, not a permission: `apikeys.resolve_key` is the one place every key passes, so refuse `ld_test_` there rather than in each inference route. Approval is two managers by default and the second may be an admin; a requester can withdraw but never approve — that rule lives in `promotion.can_approve`, so the router and the button cannot disagree.
