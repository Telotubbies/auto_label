## User story
As a CI engineer, I want to prepare an upload, PUT the file to the returned address and poll one task id
so that a dropped connection on a 3 GB archive costs a retry, not a restart.

## UX flow (LabelDesk words)
1. **Developer API** — `POST …/uploads/sessions` with `{kind:"archive", filename, bytes}` returns
   `{taskId, uploadUrl, headers, expiresAt}`; the client PUTs the file **without** its API key, because
   the address is the grant. [empty: `bytes` omitted → the server estimates from the plan and proceeds]
   [loading: prepare is a single request; the PUT carries the progress] [error: `bytes` over the plan's
   remaining storage → 402 with the plan line]
2. **Developer API** — `PUT <uploadUrl>` with `Content-Type: application/zip` → `200 {status:"uploaded"}`
   and the server starts the archive job. A second PUT to the same address → `409 {"detail": "this
   upload already started"}`. [error: expired grant → 401 "this upload link expired — prepare a new one"]
3. **Developer API / job tray** — `GET …/uploads/sessions/{taskId}` reports
   `pending | uploaded | running | done | failed` with `progress` and, when done, the same counts the UI
   shows ("Added 37 · duplicates 3 · failed 0").
4. **Developer API** — `kind:"video"` returns the same three steps; the finished video is a row on
   **Video** with its `extract_frames` job id, so frames land in a batch exactly as a browser upload does.

## Backend changes
- Models/schema: none — the token is stateless (signed payload) and the replay/state check reads the
  `Job` row created at PUT time (`params.session`).
- Routers: `apps/backend/app/routers/uploads.py`
  - `POST /uploads/sessions` → `201 {taskId, uploadUrl, headers: {"Content-Type": ...}, expiresAt}`;
    `kind` in `archive|video`; `filename` extension validated as today; the body also carries
    `annotation_overwrite` (passed to `ingest`, T-063) and `batch_name`/`split`/`tags`.
  - `PUT /uploads/sessions/{token}` — body read up to `MAX_UPLOAD_MB`; verifies the HMAC, expiry and
    `project_id`; creates the job (`archive_ingest` or `extract_frames`) and stores the bytes under
    `DATA_DIR/uploads/{taskId}`.
  - `GET /uploads/sessions/{token}` → state derived from the job row (`pending` before PUT).
- Services/jobs: `apps/backend/app/services/upload_sessions.py` (new) —
  `issue(kind, ws_id, project_id, filename, ttl=3600) -> {token, expiresAt}` (HMAC-SHA256 over
  `kind|ws|project|exp|nonce` using `config.SECRET`, URL-safe base64), `verify(token) -> payload` raising
  `Expired`/`BadToken`, `used(db, nonce) -> bool`.
- Permissions + workspace isolation: issuing needs `project.upload` and the PUT re-checks that the token's
  project still exists in the token's workspace; a token minted for project A and replayed under project B
  is 404. No API key is accepted on the PUT (a leaked URL cannot be replayed after one use).
- Secrets/safefetch: no outbound fetch; the grant is signed with the existing `SECRET` (no new secret
  store).
- OpenAPI: yes — three routes.

## Acceptance criteria
- [ ] Prepare → PUT → poll works for both kinds, with one task id the caller can bookmark/poll.
- [ ] The PUT accepts no API key and cannot be replayed; an expired or foreign token is refused.
- [ ] Archive PUT lands in the existing `ingest` path (the one refusal rule set) and video PUT reuses the
      existing extraction job.
- [ ] Status reports the same counts the Upload result sheet shows.
- [ ] Empty/loading/error states above render (JSON states; the tray row covers the human view).
- [ ] Flag off ⇒ all three routes 404 and nothing else changes.
- [ ] Workspace A cannot see or change workspace B's data (a token scoped to A is 404 under B).

## Notes for the implementer
Do not add object storage: the "signed URL" is this API's own PUT path with a signed token. TTL is one
hour (the video path's documented expiry); a `bytes` estimate over the storage allowance is refused at
prepare time so a wasted 3 GB PUT cannot happen.
