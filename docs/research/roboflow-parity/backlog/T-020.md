## User story
As a team labelling the same objects across product lines, I want projects in one annotation group to share one class list, so that a second project over the same imagery does not force me to retype the vocabulary.

## UX flow (LabelDesk words)
1. **Create a project with a group** — the group string already posts (`Home.tsx:35`). The new project copies the group's class list at creation, so its Classes page is never empty while its sibling has eight classes. [empty: a brand-new group name → the project starts with the classes typed in the form, exactly as today]
2. **Add a class in one project** — it appears in every other project of the same group within the same request, with the same name and a colour picked by group order. A toast states `Added “vest” to 3 projects in PPE.` [error: the sibling write fails → nothing is written anywhere and the toast reads `Could not share the class — nothing changed.`]
3. **Rename a class** — all siblings rename together. If a sibling already holds the new name, 409 with the project names: `“helmet” already exists in Line A. Merge them instead.`
4. **Merge classes** — merges in every sibling; annotation counts per project update.
5. **Delete a class** — allowed only when no sibling project holds that class; otherwise 409 listing the projects that still use it. [error: this exact 409]
6. **Leave a group** — Project settings shows `Shared vocabulary with PPE (3 projects)`; choosing `Use its own vocabulary` unlinks the project and copies the current classes (no deletion anywhere).

## Backend changes
- Models/schema: `models/project.py` gains `AnnotationGroup(id, workspace_id, name, created)` with `UniqueConstraint(workspace_id, name)`, and `Project.group_id` (nullable FK `annotation_groups.id`, `ondelete="SET NULL"`). `ADD COLUMN` `{"group_id": "VARCHAR(32)"}` appended to `PROJECTS` in `app/schema/dataset.py`; register the model in `models/__init__.py` (`DOMAIN_MODULES`).
- Routers: `GET /api/ws/{ws}/annotation-groups` → `[{id, name, projects, classes}]`; `POST` create; `PATCH /api/ws/{ws}/projects/{p}` accepts `group_id` (link/unlink, unlink copies classes); class add/rename/merge/delete routes call the vocabulary service. `project_out` gains `annotationGroupShared: bool` and `groupSize`.
- Services/jobs: `services/vocabulary.py` (new) — `resolve_group(db, ws, name)`, `copy_into(db, project, group)`, `add_class(db, group, name)`, `rename_class(db, group, old, new)`, `merge_classes(db, group, sources, target)`, `delete_class(db, group, name)`, each returning `(changed_projects, conflicts)`. One transaction: the router commits once.
- Permissions + workspace isolation: class edits keep `project.classes`; group resolve is workspace-scoped (`unique(workspace_id, name)`); a group id from another workspace 404s; unlink needs `project.settings`.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Acceptance criteria
- [ ] A project created in an existing group starts with that group's classes, not an empty list.
- [ ] Add, rename, merge and delete follow the four rules above; a conflict writes nothing and names the project.
- [ ] Empty, loading and error states above all render (new group, conflict 409 copy).
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag none: existing projects without a group behave exactly as today; the backfill only links equal `annotation_group` strings in the same workspace.

## Notes for the implementer
One transaction per edit: collect the sibling writes, then commit once, so a failure leaves no half-shared vocabulary. Colour is `PALETTE[index]` by group order, so siblings look alike.
