## User story
As an engineer deploying to a Jetson, a mini-PC or a cloud CPU, I want one action that exports the model to each format and measures it, so that the format decision is answered with numbers instead of a guess.

## UX flow (LabelDesk words)
1. **Model page → Benchmark** (`/:ws/:project/models?model=<id>`) — pick formats, image size and an accuracy floor, then `Run benchmark`. Formats the worker cannot build are disabled with their reason. [empty: "No engine build available on this worker — the table explains why per format."] [loading: one row appears per format as it finishes, each with a working spinner]
2. **Results table** — one row per format: build time, ms per image, FPS at batch 1, file size, precision and the model's accuracy at the same settings. Rows sort by FPS and the cheapest row that clears the floor is marked. [error: one format fails ⇒ its row keeps the failure sentence and the other rows continue]
3. **Attach to model** — keeps the table on the model page and inside the model card from T-789. [loading: the button shows pending while the rows are stored]
4. **A model that is not ready, or an HF directory model** — the action is disabled with the reason ("Benchmarking needs a single-file model.").
5. **Re-running** — replaces the attached table after confirmation, so a stale number never sits beside a newer one.

## Backend changes
- Models/schema: none new — rows are stored at `TrainedModel.metrics['benchmark']` = `{run_at, imgsz, floor, rows:[{format, precision, built_s, latency_ms, fps, bytes, ap, error}]}`.
- Routers: `POST …/models/{mid}/benchmark` `{formats:[…], imgsz, floor}` queues one job and returns it; `GET …/models/{mid}/benchmark` returns the stored table; `POST …/models/{mid}/benchmark/attach` keeps it. Both live in `routers/runs.py`, `admin` required.
- Services/jobs: new `app/handlers/benchmark.py` with `run_benchmark(job)` building each requested preset through `services/edge.export_plan()` and the adapter's `export()`, timed with `time.perf_counter`, then measuring `latency_ms` over up to 20 test images; one format's exception is captured into its own row. Add `benchmark` to `LD_LOCAL_JOBS` in `config.py`.
- Permissions + workspace isolation: `admin` to queue and attach, `project.models` to read; another workspace's model answers 404.
- Secrets/safefetch: none — artifacts stay under `DATA_DIR/bench/` and are deleted after measuring.
- OpenAPI: yes — regenerate both generated files.

## Acceptance criteria
- [ ] One action measures every requested format and returns build time, ms per image, FPS, file size and accuracy per row.
- [ ] A format the worker cannot build is refused with its reason before any job is queued.
- [ ] One failing format leaves its row's error and lets the other rows finish.
- [ ] Empty, loading and error states above all render: no buildable format explains itself, rows stream in, failures stay in their row.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no Benchmark section, no job kind and the model page is unchanged.

## Notes for the implementer
Measure latency on the test split of the model's own version, at the image size in the request, and state the batch size (1) in the header — a number without its settings is the thing this card replaces. Never time the first inference after a cold load as the row's latency: warm up once, then average up to 20.
