## User story
As the person who started a search, I want each candidate to appear as it finishes, with its own score, so that a ten-hour run is useful at hour two instead of opaque until the end.

## UX flow (LabelDesk words)
1. **During the search** — the run view reads "Candidate 3 of 7 · YOLO11 Medium · epoch 18 of 20" and lists finished candidates with their score and latency; the current one is highlighted. [empty: before the first candidate starts ⇒ "Preparing candidate 1 of 7."] [loading: the candidate list shows seven grey rows from the plan, so the shape is known up front] [error: one candidate failing does not end the search — its row reads "Candidate failed — <remedy>" and the next one starts]
2. **A candidate that hits its own cap** — its row reads "Stopped at the candidate cap · weights kept" and counts as finished with whatever score it reached.
3. **The search ends** — the run registers **one** model: the best candidate, named `<run name> (best: <variant>)`; the losers are kept as candidates, not as deployable models, so the model list stays readable.
4. **Every candidate dies** — the job fails with the remedy of the last candidate and no model row is registered.
5. **The tray** — the job tray shows "Search · candidate 3 of 7 · 42 %", not a bar that resets per candidate.

## Backend changes
- Models/schema: new table `search_candidates` — `id` pk, `job_id` `VARCHAR(32)` (indexed, no FK so a deleted job leaves the record for the 30-day audit), `project_id` FK cascade, `variant` `VARCHAR(64)`, `family` `VARCHAR(32)`, `status` `VARCHAR(16)` (`queued|training|done|failed|stopped`), `metrics` JSON, `weights` `VARCHAR(1024)`, `credits_used` `FLOAT`, `error` `TEXT`, `created`/`updated` `FLOAT`. Register in `models/__init__.py`.
- Routers: `POST {P}/train` with `engine="search"` creates the plan's `search_candidates` rows (`status="queued"`) inside the same transaction as the model and job, and sets `job.params.options.candidates = [variant, …]`. The payload of `GET {P}/models/{mid}` gains `search: {candidates: [...]}` (empty for a single-model run).
- Services/jobs: `handlers/training.py::run_train` branches on `opts["engine"] == "search"`: for each candidate in order, write its `status="training"`, run the adapter under the existing `scheduler.exclusive` lease, update `search_candidates.metrics`/`weights`/`status="done"`, and `job.progress = (i + candidate_progress) / n × 100`. A candidate failure records `error` and continues; a cap stop records `status="stopped"` and continues. After the loop the best candidate (highest `map5095`, ties → higher `map50`, then earlier in the plan) is materialised as the `TrainedModel`'s weights and evaluated once (the existing `evaluate` stage runs on the winner only).
- Permissions + workspace isolation: unchanged (`c.need("admin")`); candidates are read through the model payload, which is already project-scoped.
- Secrets/safefetch: none.
- OpenAPI: yes — regenerate both files.

## Acceptance criteria
- [ ] One search run creates one job, N candidate rows and exactly one deployable model.
- [ ] A failed or cap-stopped candidate is visible and does not abort the search.
- [ ] The winner is chosen deterministically (score, then plan order) and is the only model registered.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no candidate rows, no `search` payload key, today's single run.

## Notes for the implementer
Candidates share the parent job's GPU lease — acquire once, reuse; do not re-enter `scheduler.exclusive` per candidate or a search would fight its own lock. Winner selection is one function in `architecture_search.best()`, tested there.
