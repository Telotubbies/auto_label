## User story
As a reviewer disputing a label change, I want the timeline of one image with the field that changed, so that "who turned this person into a worker" is answered from the record instead of an argument.

## UX flow (LabelDesk words)
No screen in this card (T-749 owns the rail):
1. **An image's history** — `GET /api/ws/{ws}/history/image/{id}?limit=50` answers newest-first `[{kind: "revision", id, at, user, status, deltas: [{change: "class", label: "box 3", from: "person", to: "worker"}], annotations: 12}]`, plus `{kind: "audit", action, target, meta}` rows that name this image.
2. **A save that changed nothing** — no revision row is written, so the timeline never fills with identical entries. [empty: "No changes since upload." / "ไม่มีการเปลี่ยนแปลงตั้งแต่การอัปโหลด"]
3. **A version's history** — the same route with `kind=version` returns the audit rows that name it (`version.create`, `export`, `train`) with their counts. [loading: the rail's five skeleton rows]
4. **Restoring** — `POST /history/image/{id}/restore {revision_id}` writes a *new* revision whose labels equal the old one, and the timeline shows the restore as the newest entry, never a rewritten past.
5. **A revision that names a deleted class** — 409 `"This label set uses a class that no longer exists (person). Recreate the class, then restore."`
6. **A foreign object** — an image, version or model from another workspace is 404, and so is an image id in a project the caller cannot read.

## Backend changes
- Models/schema: `ImageRevision` in `app/models/project.py` — `id (PK)`, `workspace_id (index)`, `project_id (index)`, `image_id (FK images CASCADE, index)`, `user_id (null)`, `annotations JSON`, `status VARCHAR(16)`, `review VARCHAR(16) null`, `created FLOAT`, with `Index("ix_image_revisions_image_created", "image_id", "created")`. Re-exported from `models/__init__.py`. New table, so no `ADD COLUMN`; it appears on an existing database through `metadata.create_all`.
- Routers: `app/routers/history.py` (new), prefix `/api/ws/{ws}`, `dependencies=[Depends(require_flag("task_object_history"))]` — `GET /history/{kind}/{object_id}` (`kind` in `image|version|model`, `limit` 1–200), `POST /history/image/{object_id}/restore {revision_id}`.
- Services/jobs: `app/services/history.py` (new) — `CAP = 50`, `record(db, ws_id, img, user_id, before, after)` (skips identical label sets, inserts, prunes beyond `CAP` oldest-first), `diff(before, after) -> list[dict]` (boxes matched by annotation id: `add`, `remove`, `class`, `attr`, `geometry`; each with a human label `"box 3"`), `timeline(db, c, kind, object_id, limit)` and `restore(db, c, img, revision_id)`. `app/services/labeling_ops.py::record_save` gains one call to `history.record` so the one full-set write path is the only place revisions are born.
- Permissions + workspace isolation: reading needs `project.read`, restoring needs `project.review` (`c.perm`); the object is resolved through `project_ctx`/`image_ctx` so a foreign id is 404 — including an image whose project belongs to another workspace.
- Secrets/safefetch: none — annotations are JSON already stored on the image row, and pruning deletes rows, not bytes.
- OpenAPI: yes — two routes and the timeline shape.

## Acceptance criteria
- [ ] Every full-set label save writes one revision, an identical save writes none, and at most fifty are kept per image.
- [ ] The timeline for an image, version or model is newest-first, names the actor and carries the field deltas.
- [ ] Restore writes a new revision; history is never rewritten and the restore is visible as the newest entry.
- [ ] Empty, loading and error states above all render: an unchanged image reads "No changes since upload.", the rest is T-749's rail.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no revision is written, both routes are 404, and saving labels behaves exactly as today.

## Notes for the implementer
`record_save` in `services/labeling_ops.py` is the single full-set write path (canvas, workflow sink, consensus merge) — hooking it once is why this is three hours and not three days. Store the *after* payload on the revision so a restore needs no replay; storing diffs would make a restore impossible after a cap prune. Do not extend `Audit` for this: audit rows answer "who did what to the workspace", revisions answer "what did this label set look like", and mixing them is how the audit log becomes too big to export.
