## User story
As a team lead, I want a saved draft and a live version to be different things, so that a half-finished pipeline cannot answer production traffic.

## UX flow (LabelDesk words)
1. **Save** (`Ctrl/⌘+S`, the Save button) — writes the draft exactly as today, creating a new version row. The header badge reads `Draft v7` when the draft is newer than what is live, and `Live v7` when they match.
2. **Publish** — a separate button, enabled only when the gate is `publishable`. Pressing it asks one confirmation: "Serve v7 to the endpoint and to every batch job?" Then the badge becomes `Live v7`.
3. **Blocked** — `[error]` the Publish button is disabled with the first blocking reason beside it: "3 blocks reference a model that is no longer ready." A "Check again" link re-runs the checks; the panel lists every check with pass / fail and one line each.
4. **Approval** — when the workspace requires approval, the gate's last step reads "Waiting for a manager to approve v7" with Approve / Reject for managers and a note for everyone else: "Ask a project manager to approve this version."
5. **Auto-publish** — a small switch: "Publish the next saved draft automatically once its checks pass." It never skips the approval step; it only saves the second click.
6. **The endpoint** — a published workflow's invoke URL serves the **published** blocks, so editing a draft cannot change what a customer's client receives.

## Backend changes
- Models/schema: `workflows` gains `published_version INTEGER NOT NULL DEFAULT 0`, `published_at FLOAT`, `publish_state JSON` (nullable). `ADD COLUMN` lines appended to the `WORKFLOWS` block in `app/schema/dataset.py` that T-320 created. Existing rows read as `published_version: 0` = nothing published, and the invoke endpoint falls back to the current version only while `task_328` is off.
- Routers: `apps/backend/app/routers/workflows.py` — `GET /{workflow_id}/publish` returns `{status, checks: [{id, label, ok, detail}], approvals: {required, approved_by, at}, published_version, draft_version}`; `POST /{workflow_id}/publish` (200 / 400 not publishable / 409 already publishing / 403 needs a manager); `POST /{workflow_id}/publish/approve` and `/reject` (`project.settings` permission); `PUT /{workflow_id}` accepts `auto_publish: bool`.
- Services/jobs: `apps/backend/app/services/workflow_publish.py` (new) — `CHECKS` in fixed order (compiles, every model ref resolves now, exactly one image input, every node reachable, sink present, no disabled sink), `check(db, project, wf) -> list[dict]`, `publishable(checks, approval)`, `publish(db, wf, user_id)` setting `published_version = wf.version` and appending a `WorkflowVersion` note, `approve/reject(db, wf, user_id)`, `published_blocks(db, wf) -> list[dict]` used by T-316.
- Permissions + workspace isolation: publish and approve need `project.models`; approve additionally requires the `manager` project role, because a reviewer approving their own pipeline is not a gate. Foreign ids stay 404 through `svc.get`.
- Secrets/safefetch: none.
- OpenAPI: yes — four routes and three columns.

## Acceptance criteria
- [ ] Saving never changes what the endpoint serves; publishing does, in one confirmed action.
- [ ] Every check appears with pass/fail and a readable detail; the button is disabled until all pass and approval is satisfied.
- [ ] Editing after publish reports a draft ahead of the live version and leaves the live version untouched.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no publish routes, no badge change, and the endpoint serves the current version.
