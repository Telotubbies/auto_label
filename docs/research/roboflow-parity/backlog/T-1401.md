# T-1401 — Evaluation matching as one native call per image

| Field | Value |
| --- | --- |
| Wave | R (Rust hot paths) |
| Area | Performance / evaluation |
| Size | 4.0 agent-hours |
| Role | R14 Rust systems engineer + R6 review (Staff applied-ML reviewer for the metric parity) |
| Skills | ponytail, test-driven-development, systematic-debugging, verification-before-completion |
| R7 security review | no — pure arithmetic, no I/O, no new input surface |
| Depends on | **T-1320 baseline** (a recorded `evaluate` job duration and the `_sweep` share), **T-1400** (crate, seam, benchmark, CI job) |

## Problem
The `evaluate` job spends its Python time in a greedy matcher that runs 19 times per image, once per
confidence threshold. Measured on 2026-11-17 (`docs/research/rust-hybrid/PLAN.md` M1–M5): 1.45 ms/image at
10 gt / 50 pred, 5.90 ms at 10 / 200 and **19.73 ms at 25 / 300**, i.e. 3–40 s for a 2 000-image val
split, plus ~10 % for the confusion matrix and the worst-image list. Every IoU there is a dict lookup,
a slice and a function call; the same records in one numpy call take 22 ms instead of 106 ms, which shows
the arithmetic is not the cost.

Training and retraining both run this (`services/finalize.py:19`, `handlers/training.py:166`), so it is on
the critical path of the feature customers wait for.

## Design
**One Python→Rust call per image for all 19 thresholds**, not one per threshold: per-call overhead is what
killed the numpy option.

Kernel in `packages/labeldesk-core/src/sweep.rs`:

```rust
// gt_boxes: [n,4] xywh, gt_cls: [n] class index
// pr_boxes: [m,4] xywh, pr_cls: [m], pr_conf: [m]
// thresholds: [k] ascending confidence floors, iou_min: 0.5
// -> [k,3] i64  (tp, above, ground_truth_count)
fn sweep_counts(gt_boxes, gt_cls, pr_boxes, pr_cls, pr_conf, thresholds, iou_min) -> PyArray2<i64>;

// the pair form, for the confusion matrix and the worst-image list
// -> [2,p] i64  (gt index, pred index)
fn match_pairs(gt_boxes, gt_cls, pr_boxes, pr_cls, pr_conf, conf, iou_min, same_class) -> PyArray2<i64>;
```

Exact semantics to preserve (this is where the parity tests earn their keep):

- predictions are visited in **descending confidence**, ties keeping input order (`sorted(..., key=-conf)`
  is stable);
- a match needs `iou >= iou_min` **and** the same class when `same_class`;
- among equal IoUs the **later gt index wins** (`_match` uses `iou >= best_iou` while scanning gt in order);
- a gt index is consumed once; predictions below `conf` are skipped but still counted in `above` for the
  thresholds they clear;
- `box_iou` stays the unclamped xywh formula of `services/boxes.py` (not `labeling.bbox_iou`, which clamps).

Python side:

- `apps/backend/app/kernels.py` gains `sweep_counts(...)` and `match_pairs(...)`, converting the record's
  lists once per image (class names → an index map built per evaluation, not per image).
- `apps/backend/app/kernels_py.py` holds today's loops, moved verbatim.
- `services/evaluate.py` changes three call sites: `_sweep`, `_confusion`, `_worst`; `_match` becomes a thin
  wrapper over `match_pairs` so its tests keep working. The curve, the best-F1 pick and all rounding stay
  in Python — the kernel never returns a metric.

## Acceptance criteria
- [ ] The report records the **before** number from the baseline: `_sweep` ms/image at the fixture's real
      gt/pred counts, the `evaluate` job duration from `docs/ops/perf/baseline.json`, and the kernel's
      measured share. If the share cannot give 2x on the job, the card closes instead of merging.
- [ ] `tools/perf/bench_kernels.py --kernel evaluate_sweep --min-speedup 5` passes, with the median of 10
      warm runs on the T-1319 fixture and on the 25 gt / 300 pred shape.
- [ ] `_sweep`, `_confusion` and `_worst` produce byte-identical output on both paths for a recorded
      500-image evaluation, and the 27 existing `test_evaluate.py` cases pass unchanged.
- [ ] The `evaluate` job duration drops by at least the pre-registered amount in a re-run of the harness;
      both numbers are in the report.
- [ ] No metric, rounding or threshold constant changes in `evaluate.py`; a diff that changes a number is
      a defect, not a port.
- [ ] The kernel does no I/O, allocates per image only, and holds no state between calls.
- [ ] With `LD_FORCE_PY_KERNELS=1` the API suite is green and the job runs at the old speed.

## Notes for the implementer
Port the loop, do not improve it. TIDE buckets (`_tide_*`) are **out of scope**: they run six extra AP50
runs and are a different card if they ever prove hot. `insights_eval.py` has its own copy of the sweep
grid; leave it alone here, and open a follow-up card only if the profile shows it costs real time.

Do not pass Python callables or dicts into the kernel. If a signature starts needing objects, the design is
wrong: build flat arrays in Python and keep the kernel numeric.
