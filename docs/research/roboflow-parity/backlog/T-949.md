## User story
As an ML engineer, I want the deploy dialog to tell me which release rule a model fails, so that shipping
below the bar is a deliberate, recorded act instead of an oversight.

## UX flow (LabelDesk words)
1. **Models → Deploy** — `/:ws/p/:project/deploy`; each candidate row in the alias picker gains a rule
   summary: "3 of 3 rules pass" or "fails 1 of 3: recall(helmet)". A model with no evaluation reads "not
   evaluated". [empty: a project with no rules shows no summary line at all, not "0 of 0"]
2. **Pick a failing model → Deploy** — the confirmation dialog refuses first: "This model fails 1 of 3
   release rules — recall(helmet) 0.71 < 0.90", with *Run evaluation* (links to the model panel), *Cancel*,
   and *Deploy anyway* shown only to owner/admin, styled as a secondary with the sentence "This override is
   recorded in the audit log." [loading: the dialog shows the rule list as it resolves, the primary
   disabled until it has] [error: "Release rules could not be checked" blocks the deploy, never allows it]
3. **Override** — *Deploy anyway* requires a reason (a text field, minimum 10 characters) and then performs
   the switch; the audit entry reads `deploy.override` with the model, the alias and the reason.
4. **A model with no evaluation** — under an active gate the dialog offers only *Run evaluation*; there is
   no override path.
5. **After the switch** — a dismissible banner on the Deploy page: "Production points at a model below the
   release gate." [empty: a passing deploy shows no banner]

## Backend changes
- Models/schema: no new column. `DeploymentEvent` (`apps/backend/app/models/training.py`) already records
  events; this card writes `override=True` and the reason into its existing payload JSON.
- Routers: `PUT {P}/deployments/{alias}` (`apps/backend/app/routers/deployments.py:30`) body gains
  `override: bool = False` and `reason: str = ""`.
  `GET {P}/deployments` rows gain `gate: {status, failing: [{metric, actual, value, class_name}]}` from
  T-948's verdict. 409 with the failing rules when `override` is false and the verdict is `fail`; 403 when
  `override` is true and the caller is not owner/admin; 400 when `override` is true and `reason` is shorter
  than 10 characters; 409 "not evaluated" when `status == "no_evaluation"`.
- Services/jobs: `apps/backend/app/services/deployments.py` — `switch()` calls
  `release_rules.verdict(...)` before `_deployable`'s work is committed, and raises a typed
  `GateRefused(rules)`; the router maps it to 409. No new job.
- Permissions + workspace isolation: the aliases POST already needs `admin`; the override additionally
  checks `c.ws_role in ("owner", "admin")` and writes `audit(c.db, ...)` with the reason. Cross-workspace
  alias or model → 404 unchanged.
- Secrets/safefetch: none. Dependency: none added (no `mlflow-skinny`), so no
  `THIRD_PARTY_LICENSES.md` change.
- OpenAPI: yes — regenerate both files.

## Frontend changes

## Acceptance criteria
- [ ] A model failing a rule cannot become an alias target without an owner/admin override carrying a reason.
- [ ] The override writes one audit row naming the model, the alias and the reason.
- [ ] An unevaluated model cannot be force-deployed while rules exist.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ surface absent and the old behaviour unchanged.
