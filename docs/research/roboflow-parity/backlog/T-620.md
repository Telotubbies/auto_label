## User story
As an ops lead, I want to name the stages an image passes through and say where a rejection goes, so that a second review tier is one more stage instead of a second project.

## UX flow (LabelDesk words)
The canvas is T-622; this card owns the graph and its rules.
1. **`GET /stages`** — the project's stages, or the default `Annotate → Review → Done` when nothing is configured, plus `source: "default"|"custom"`. [empty: a project with no graph returns the default three]
2. **`PUT /stages`** — replaces the graph in one transaction; keys are slug-safe and unique, position 0 is the entry stage, `next_key` and `reject_key` name an existing key or `null`. [error: "Stage 3 has no assignee role, so it cannot accept files." (422 with the index)]
3. **A review stage** — carries `reject_key` ("Rejections return to"), so a rejection has a destination that is not "whatever was before".
4. **Stages in use** — a key referenced by an image cannot be removed: 409 "3 images still sit in stage `rework` — move them first." and nothing is written.
5. **Publish** — the API stores the graph and bumps `Project.settings["stages"]["version"]`; the reroute itself is T-621.

## Backend changes
- Models/schema: new `app/models/stages.py` with `LabelStage` (`id`, `workspace_id`, `project_id` FK CASCADE, `key` String(40), `name` String(80), `kind` in `annotate|model|consensus|review|rework`, `position` Integer, `assignee_role` String(16), `instructions` Text default `''`, `cap` Integer nullable, `allow_edits` Boolean default True, `next_key` String(40) nullable, `reject_key` String(40) nullable, `created`, `updated`, `UniqueConstraint("project_id", "key")`), registered in `app/models/__init__.py`. `Image.stage` already exists from T-618; no new column here.
- Routers: `routers/stages.py` (new), prefix `/api/ws/{ws}/projects/{project}/stages` — `GET ""` → `{source, version, stages: [...]}`; `PUT ""` `{stages: [...]}` → the same payload. 422 with the offending index for a duplicate or non-slug key, an unknown `kind`, a `next_key`/`reject_key` that names nothing, a cycle, an `assignee_role` outside `PROJECT_ROLES`, or a `cap` outside 0–1000; 409 for removing a key that open images still use.
- Services/jobs: `app/services/stages.py` (new) — `DEFAULT_GRAPH`, `read(db, project)` (falls back to the default), `validate(project, stages)`, `keys(project)`, `entry_key(project)`, `version(project)`. No job kind.
- Permissions + workspace isolation: `GET` needs `reviewer`, `PUT` needs `manager`; `project_ctx` makes a foreign project a 404 and the "in use" count is scoped to `c.project.id`.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Acceptance criteria
- [ ] A project without a graph reads the default `Annotate → Review → Done` and says it is the default.
- [ ] A saved graph is rejected as a whole when any key, kind, role, target or cycle is wrong, naming the offending index.
- [ ] A stage still used by an image cannot be removed, and the count is in the 409.
- [ ] Empty, loading and error states above all render where the surface exists: the default graph, the 422/409 sentences, and 404 for a foreign project.
- [ ] Workspace A cannot read or write workspace B's stages (404, not 403).
- [ ] Flag off ⇒ no stage routes, and the queue and board behave exactly as today.

## Notes for the implementer
One chain with an explicit reject edge is enough — do not build a free-form DAG editor's data model. `reject_key` on a review stage is the whole "two review tiers" story, and `Image.stage == ''` must keep meaning "the status is the stage" so existing rows need no migration.
