## User story
As the operator of a self-hosted LabelDesk, I want to turn the MCP endpoint on with one flag, point my
agent at it with one config snippet, and read exactly what it can do, so that "connect an agent" is a
five-minute job with no surprises for my security reviewer.

## UX flow (LabelDesk words)
1. **`deploy/.env`** — set `LD_DOMAIN` as today; nothing new is required to keep MCP off.
2. **`docker compose --profile mcp up -d`** — the `mcp` service starts beside `api` and is reachable at
   `https://<LD_DOMAIN>/mcp` through the existing Caddy certificate. [error: without the profile the
   container does not exist and `/mcp` answers the SPA's 404].
3. **`docker compose ps`** — one line for `mcp`; its log carries the bind address and no key.
4. **Agent setup** — `docs/MCP.md` gives the two snippets (Claude Desktop / any host with a `command`, and
   a hosted runner with a URL), the three environment variables, and the four things the server will not do.
5. **First call** — `whoami` returns the workspace and the key's scopes; a workspace with `task_992` off
   answers 404 until an admin enables it in Settings → Features.

## Backend changes
- Models/schema: none.
- Routers: none.
- Services/jobs: deployment only.
  - `apps/mcp/Dockerfile` (new): `python:3.11-slim`, install `packages/sdk` and `apps/mcp` from the build
    context, run as a non-root user, `CMD ["labeldesk-mcp", "--http", "--host", "0.0.0.0", "--port", "8020"]`.
    No volumes, no database, no `LD_SECRET` — it holds no secret of its own.
  - `.dockerignore` at the repo root (new): `data/`, `*.pt`, `apps/frontend/node_modules`, `design*/`,
    `research/`, `docs/`, `.git/` — the MCP image builds from the repo root because it needs both
    `packages/sdk` and `apps/mcp`, and the ignored set keeps the build context small.
  - `deploy/docker-compose.yml`: one service, `mcp`, under `profiles: ["mcp"]`, `build: {context: ..,
    dockerfile: apps/mcp/Dockerfile}`, env `LABELDESK_URL=http://api:8000`,
    `LD_MCP_ALLOWED_HOSTS=${LD_DOMAIN}`, `LD_MCP_ALLOWED_ORIGINS=https://${LD_DOMAIN}`,
    `depends_on: [api]`. No key in the environment: keys arrive per request.
  - `deploy/Caddyfile`: inside the `{$LD_DOMAIN}` block, before `reverse_proxy web:80`,
    `route /mcp* { reverse_proxy mcp:8020 }`. `route` keeps the written order; a `handle` block would
    require re-wrapping the existing `reverse_proxy`.
- Permissions + workspace isolation: unchanged (the key still decides); the endpoint adds no new identity.
- Secrets/safefetch: no secret is stored in the image, the compose file or the Caddyfile.
- OpenAPI: no.

## Acceptance criteria
- [ ] `docker compose --profile mcp up -d` serves `/mcp` on the API's origin; without the profile nothing
      listens and `/mcp` is the SPA's 404.
- [ ] The image holds no secret and runs as a non-root user.
- [ ] `docs/MCP.md` is enough on its own to connect a Claude Desktop host and a hosted runner.
- [ ] The R7 sign-off section lists every tool's scope, the confirm rule, the audit row and the four
      non-goals, with the test name that proves each.
- [ ] Empty, loading and error states: the docs name the 401, 403, 404 (flag off), 413 and 429 a client can
      meet, with the sentence each one prints.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids) — restated
      in the docs as a property, proved by T-998.
- [ ] Flag off ⇒ the compose profile is not started and `task_992` is off per workspace; both are documented
      as the two independent switches.
- [ ] `ruff check apps/backend` clean; the full serial API suite passes.

## Notes for the implementer
The R7 sign-off is a table in `docs/MCP.md`: tool → scope → route → the test that proves it. A reviewer
should be able to read it without opening a card.
Keep the two switches distinct in the docs: the profile decides whether this deployment runs the endpoint at
all; `task_992` decides whether one workspace may use it. Neither replaces the other.
