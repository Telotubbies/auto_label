## User story
As a team running one production line, I want a key that only reaches my folder, so that a leak affects one site
and my team can rotate it without an admin round-trip.

## UX flow (LabelDesk words)
1. **Folder card `⋯` → `API keys`** — the key table from T-389 with a folder header
   `Keys for “Site A”. Calls made with these keys only reach this folder's projects.` and `Generate key here`.
2. **Settings → API keys → `Folder keys`** — the same table, with a folder picker above it; a key row shows a
   `Site A` chip next to its name.
3. **Create** — the dialog is the workspace dialog plus a locked `Folder: Site A`; the key cannot be made default
   (checkbox absent).
4. **`[empty]`** `No keys for this folder yet.` + `Generate key here`; **`[error]`** without `workspace.keys`
   the entry is dimmed with a lock and `Request access`, and a direct URL answers the settings 403 screen.
5. **Behaviour** — a folder key that calls a project outside its folder gets the same bare 404 as a missing project.

## Backend changes
- Models/schema: `ApiKey.folder_id` already exists from T-388 — no new column.
- Routers: `POST /api/ws/{ws}/keys` accepts `folder_id` (validated to a folder of this workspace, `400` otherwise,
  `409` when combined with `publishable` or `is_default`); `GET /api/ws/{ws}/keys?folder_id=` filters the list.
  Scope enforcement: `KeyCtx.project(slug)` treats a project outside `key.folder_id` as missing.
- Services/jobs: `services/keys.py` — `folder_filter(db, key)` used by `apikeys.KeyCtx.project`; one shared line in
  `apikeys.py`.
- Permissions + workspace isolation: creating a folder key needs `workspace.keys` **and** folder access — the
  route is 403 when `folder_access.can_see_folder` is false, 404 when the folder is another workspace's.
- Secrets/safefetch: hashed as today; no new secret path.
- OpenAPI: yes.

## Frontend changes
- Route: `/:ws/settings/api?folder=<id>` (existing tab, one new query parameter).
- Components: `features/settings/keys/FolderKeys.tsx` (new) — folder header, table reuse, folder picker;
  one menu item added to the folder card's `⋯` (the file owner is T-387's `FolderPermissionsDialog.tsx` sibling —
  mount in `FolderTree.tsx` when area 1's card is present, otherwise in `Home.tsx`'s folder card).
- API client: `keysApi.list(ws, {folderId})` and `keysApi.create(ws, body)` gain the field in `src/lib/api/keys.ts`.
- Feature flag: `task_folder_keys`; off ⇒ no folder entry, no `folder_id` accepted in the create route.

## Acceptance criteria
- [ ] A folder key reaches only its folder's projects and answers 404 everywhere else.
- [ ] Folder keys cannot be the workspace default or publishable, and the UI never offers it.
- [ ] The folder card and the Settings tab show the same table and the same actions.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no folder entry point and `folder_id` is refused.

## Notes for the implementer
One row, one folder: no multi-folder keys. The 404 for an out-of-folder project comes from `KeyCtx.project`, so
the same rule covers every devapi route without touching each one.
