## User story
As the person building the ten screens, I want the surface, glass and colour roles the app already ships written down once and pinned by a test, so that no screen has to invent a colour and no lane can slip in a second palette.

## UX flow (LabelDesk words)
1. **Any screen** — nothing new is visible. Every role the v3 frames name resolves to a variable that already exists in `apps/frontend/src/index.css`: surface → `--card`, raised surface → `--popover`, subtle surface → `--muted`, outline → `--border`, text → `--foreground`, muted text → `--muted-foreground`, primary → `--primary`, glass fill → `--glass-tint`, glass solid → `--glass-solid`, glass edge → `--glass-edge`, glass highlight → `--glass-hi`. [empty: n/a — no screen owns this card] [loading: n/a] [error: n/a]
2. **Settings → Appearance** — the existing seed (`#3b6cf6`), mode, contrast, scheme and "Reduce transparency" controls behave exactly as today; the HCT runtime in `lib/theme.ts` stays the only place a colour is derived. [error: an invalid seed still falls back to `DEFAULT_SEED`]
3. **Any screen, dark mode or high contrast** — the same variable names resolve to the dark or high-contrast roles; a component written once reads correctly in both.
4. **A reviewer reading the mapping** — the comment block in `index.css` says, per frame role, which shipped variable stands for it and why a new variable was refused.

## Notes for the implementer
The v3 frames' `--surface-container`, `--outline`, `--text-muted`, `--glass-fill`, `--glass-blur`, their hex table and the `#5B4BE0` seed are **vocabulary, not variables**: `VISUAL-OVERRIDE.md` §1 and §5 make the running app's `index.css` and `components/glass.tsx` the visual standard, so each frame name is mapped onto the shipped role instead of creating a second name for the same colour. Two names for one role is how a dark-mode bug becomes unfixable. Do not add a spacing scale either: Tailwind's 4-px step already is 4/8/12/16/20/24/32/40/48/64.
