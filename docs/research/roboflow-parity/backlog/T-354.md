## User story
As an ML engineer, I want to run one workflow across a batch, a video's frames or a bucket prefix and keep the results as a file, so that a pipeline can be applied to last month's footage without a script.

## UX flow (LabelDesk words)
1. **Deployments → Batch → "New batch job"** — four fields: workflow, source (`Batch`, `Video frames`, `Bucket prefix`), output (`Results JSONL`, `CSV`, `COCO`, `Write to dataset`), name. A workflow whose contract is not exactly one image input plus optional scalars is refused **before** the job exists: "This workflow needs two images, so it cannot run over a folder." `[empty: no published workflow → "Publish a workflow first." with a link to the workflow list]` `[loading: the job row appears with 0 % and advances per image]` `[error: every image unreadable → the job fails with the count and the first reason, never a silent empty result]`
2. **Progress** — the job row shows `n of m` and the tray carries it; cancelling stops before the next billable call, exactly as the model batch does.
3. **The artefact** — `Results JSONL` is one line per image: `{"image": "<name>", "outputs": {...}, "time": 0.084, "skipped": [...]}`. `CSV` writes one row per detection through the existing writer. `Write to dataset` runs the workflow's `annotations` sink, so an image gains annotations and the job records how many.
4. **Where it lands** — under `DATA_DIR/batch_inference/<project>/<job>` beside the model outputs, downloadable from the job row and deleted with the project's erasure.

## Backend changes
- Models/schema: none — `Job.kind = "batch_infer"` with `params.source.kind = "workflow"` and `params.output` extended.
- Routers: `apps/backend/app/routers/batch_inference.py` — remove the `501` for `kind == "workflow"`; validate the workflow exists in this project, is published (when `task_328` is on), and its contract has one image input; `output` gains `"results"`; the `dataset` write additionally requires `project.annotate`.
- Services/jobs: `apps/backend/app/services/batch_inference.py` — `source_images` unchanged for batch/video; a new `_workflow_run(db, project, wf, img, c, write_back)` calling `workflow_compile.compile` + `workflow_runner.run`; `_write_results(path, rows)` writing JSONL with `json.dumps(..., ensure_ascii=False)`; `run()` branches on `source.kind == "workflow"` and reuses the existing clamp, cancel and metering loop.
- Permissions + workspace isolation: `project.infer`, plus `project.annotate` when the output is `dataset`; the workflow is looked up with `services.workflows.get(db, project, id)`, so a foreign id is 404.
- Secrets/safefetch: bucket sources keep going through `connectors.fetch_bytes`; a workflow sink that writes to a webhook is not added here.
- OpenAPI: yes — one enum value and one output format.

## Acceptance criteria
- [ ] A workflow batch runs over a batch, a video's frames or a bucket prefix and writes one artefact with one entry per processed image.
- [ ] A workflow with a different input shape is refused before the job exists, naming the mismatch.
- [ ] The dataset output requires `project.annotate`, and the quota clamp and cancel stop before the next billable call while keeping what was produced.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] No flag: extends the existing `task_36` surface; with that flag off nothing changes.

## Notes for the implementer
`results` is the new format; `csv`/`coco` stay model-shaped and are skipped for a workflow whose sink is `annotations`, because a workflow's outputs are not always boxes. Reuse the loop's cancel, clamp and metering lines rather than writing a second runner.
