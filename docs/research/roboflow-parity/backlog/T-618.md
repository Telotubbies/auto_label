## User story
As a labeler, I want a queue of the tasks I can act on, ordered by what matters most, and as a lead I want a cap so nobody is handed three days of work by accident.

## UX flow (LabelDesk words)
The screen is T-619; this card owns the list and every action on it.
1. **`GET /queue`** — stage counts plus rows ordered `priority desc, created asc`, with `priority`, `stage`, `status`, `assignee`, `due_at` and the cap. [empty: `items: []`, `total: 0`]
2. **`POST /queue {action: "claim", ids}`** — assigns the rows to the caller until the cap; the surplus comes back in `capped` with 409 "Your queue is at its cap — release work before claiming more." [error: "Already claimed by another person." for a row someone else holds]
3. **`{action: "release"}`** — clears the assignee and the claim timestamp, leaving the status alone.
4. **`{action: "priority", value: 2}`** — −5 to 5, higher first; `{action: "stage", value: "review"}` moves along `STATUSES` and is reviewer-only.
5. **`{action: "assign", value: "<user_id>"}`** — reviewer-only; assigning an `unassigned` row moves it to `annotating` exactly as `/board/move` does today.

## Backend changes
- Models/schema: `Image` gains `priority` Integer default 0, `due_at` Float nullable, `stage` String(20) default `''` (empty means "the status is the stage"), `claimed_at` Float nullable — columns in `app/models/project.py`, ADD COLUMN lines in the `IMAGES` block of `app/schema/dataset.py`. `ProjectMember.task_cap` Integer nullable (NULL = uncapped) in `app/models/identity.py` plus the `PROJECT_MEMBERS` block of `app/schema/identity.py`. Existing rows read as priority 0, no stage, uncapped; no backfill.
- Routers: `routers/queue.py` (new), prefix `/api/ws/{ws}/projects/{project}/queue` — `GET ""` (`stage`, `assignee`, `status`, `limit` 1–200) → `{stages: [{key, label, count}], items: [...], total, caps}`; `PUT "/caps"` `{caps: {"<user_id>": cap}}` (reviewer only, each cap `null` or 0–500) → the same `caps` map; `POST ""` `{action, ids, value}` with `action` in `claim|release|priority|stage|assign`. 404 for an image outside this project, 409 for a claim over the cap or a row already claimed, 422 for an unknown action, a priority outside −5..5, a stage outside `STATUSES`, a cap outside 0–500, or an assignee who is not a project member.
- Services/jobs: `app/services/queue.py` (new) — `list_tasks(db, c, filters)`, `bulk_action(db, c, action, ids, value)`, `cap_for(db, project_id, user_id)`, `open_count(db, project_id, user_id)`, `stage_counts(db, c)`. No job kind.
- Permissions + workspace isolation: `GET` needs `annotator` and a labeler sees only rows assigned to them; `claim`/`release` act only on the caller's rows; `priority`, `stage` and `assign` need `reviewer`. Every row is filtered by `c.project.id`, so a foreign image id is a 404 and never a success count.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Acceptance criteria
- [ ] `GET /queue` returns stage counts and rows ordered by priority then age, with the cap for each member.
- [ ] Claiming past the cap writes the rows up to the cap, names the surplus in `capped` and returns 409.
- [ ] Release, priority, stage and assign each write only the named rows and return `{updated, skipped}`.
- [ ] Empty, loading and error states above all render where the surface exists: `items: []`, the 409/422 sentences, and 404 for a foreign id.
- [ ] Workspace A cannot read or change workspace B's queue (404, not 403).
- [ ] Flag off ⇒ no queue routes and the annotate board is unchanged.

## Notes for the implementer
`Image.stage` starts empty and means "use the status": do not backfill 4,000 rows to say `annotate`. The cap counts rows with a status of `unassigned` or `annotating` — review work is not the labeler's queue and must not block a claim.
