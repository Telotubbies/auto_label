## User story
As a customer's ML engineer who needs one house rule enforced, I want to install a small declarative module that adds a metric or a check beside ours, so that the rule ships in days without us maintaining a fork.

## UX flow (LabelDesk words)
1. **Settings → Extensions** (`/:ws/settings/extensions`) — `Add extension` takes an uploaded `.json` manifest; the dialog lists the capabilities it asks for before anything is stored. [empty: "No extensions installed." with the upload action] [loading: the install button shows pending while the manifest is validated]
2. **Install** — the API validates the manifest's magic bytes and signature envelope, the API version range, the capabilities and the expression, then stores it disabled until an admin enables it. [error: an incompatible API version ⇒ "Needs API {wanted}; this build supports {supported}" and nothing is stored]
3. **Run** — a `metric` extension is computed for one model on demand and returned with its value and the inputs it read; a `check` extension returns pass/fail and one sentence.
4. **Refusal** — a capability outside the allow-list (`write:labels`, `network`, `exec`) is refused by name, never warned about. [error: a malformed expression is 422 with the offending token]
5. **Audit** — installation, enable/disable and every run write an audit row naming the extension and its version.

## Backend changes
- Models/schema: `Extension` (`id, workspace_id, name, version, api_version, author, capabilities(JSON), kind, expression, message, enabled, installed_by, created, last_error`) in a new `app/models/extensions.py`; a new table needs no `ADD COLUMN`.
- Routers: new `app/routers/extensions.py` — `GET …/extensions`, `POST …/extensions` (multipart manifest, 201), `PATCH …/extensions/{id}` `{enabled}`, `POST …/extensions/{id}/run` `{model_id}`; 422 for a bad manifest, 409 for a duplicate name+version.
- Services/jobs: `app/services/extensions.py` (new) — `MANIFEST_MAX_BYTES = 32 * 1024`, `CAPABILITIES = {'read:labels','read:metrics','read:card'}`, `API_RANGE = (1, 0)`, `validate(manifest)` (magic bytes `{"labeldesk":` preamble, no unknown keys, version range, capability subset, expression parsed), `evaluate(extension, facts)` using `ast.parse` with a whitelist of `BinOp/Num/Name/Compare` over named facts and no attribute access, `run(db, project, extension, model)` returning `{value, verdict, message, inputs}`.
- Permissions + workspace isolation: `admin` to install, enable or disable; `project.models` to run against a model; an extension or model from another workspace answers 404.
- Secrets/safefetch: no network capability exists; the manifest is read from the upload with a size cap and never executed as code. Nothing is fetched.
- OpenAPI: yes — regenerate both generated files.

## Acceptance criteria
- [ ] A manifest-only extension can be installed, listed, enabled and disabled, and never stores executable code.
- [ ] The capability allow-list, the API version range and the expression whitelist each refuse with a named reason.
- [ ] Running a metric or a check returns a value or verdict with the inputs it read, for one model.
- [ ] Empty, loading and error states above all render as API states: an empty registry lists nothing, an incompatible manifest states its range.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no extension routes and no evaluation path exists.

## Notes for the implementer
Owner-hold: BEYOND §4 names this as a non-goal; do not schedule until the owner overrules it. A marketplace is the thing §4 refuses; this is a manifest-only metric/check slot with four allowed capability strings, and there is no code path that imports customer Python. Keep `ast` evaluation to arithmetic and comparisons over named facts — the moment an attribute or a call is allowed, the guard is gone.
