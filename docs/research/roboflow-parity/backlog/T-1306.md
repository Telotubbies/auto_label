## Problem
Threat reasoning exists only in two wave notes (`docs/research/inference-hub/PLAN.md` §5,
`docs/research/mcp/MCP-PLAN.md` §7/§11) and in reviewers' heads. There is no single document that a new
reviewer, an auditor or the owner can read to know what LabelDesk assumes about its attackers. New
surfaces (inference hub, MCP, monitoring) get assessed ad hoc or not at all.

## Design
`docs/ops/THREAT-MODEL.md` (new, ~220 lines), six sections:

1. **Assets and actors** — one table: tenant data (images, labels, versions, weights), workspace
   credentials, API keys, connector/PLC credentials, GPU time, the operator's host, availability.
   Actors: anonymous internet, an authenticated member of another workspace, a malicious member of the
   same workspace, a compromised API key, a hostile image/URL, a supply-chain attacker, an operator
   error.
2. **Data flow (text)** — browser → API → DB/data dir → worker → remote GPU worker → outbound
   (safefetch, SMTP, webhooks, connectors, PLC) → MCP client → future inference hub.
3. **STRIDE table per boundary** — eleven boundaries, five columns (threat, impact, existing control
   with `file:line`, residual risk, owning card or "accepted"). Boundaries exactly as the security
   plan §4.2 lists them.
4. **Trust assumptions** — this deployment is one API process; the GPU host is operator-controlled;
   `LD_SECRET` is not in the repository; the browser is not trusted; a tenant may be hostile to
   another tenant but not to the operator.
5. **Out of scope** — with a reason each: root compromise of the host, malicious weights exploiting a
   runtime, side-channel attacks on a shared CPU, physical access, a compromised PyPI mirror.
6. **Review triggers** — a new route family, a new outbound client, a new credential store, a new
   process, or a new third-party binary ⇒ update this file in the same branch.

Every row cites either a `path:line` control or a card id. The inference-hub §5 table is referenced,
not copied; where it fits, the row says "see inference hub §5 #N".

## Tests to write first
This is a document card; the "tests" are mechanical guards in `tools/tests/test_docs_ops.py` (new, ~40
lines):
- `test_every_boundary_has_a_stride_table` — the eleven boundary names from the security plan appear as
  headings, in order.
- `test_every_row_cites_a_control_or_a_card` — every table row has a non-empty last column matching
  either `accepted` or `T-\d{3,4}`.
- `test_no_card_is_cited_that_does_not_exist` — every `T-…` in the file has a card file.
- `test_out_of_scope_rows_have_a_reason`.

## Acceptance criteria
- [ ] Eleven boundaries, each with a STRIDE table; every row has an impact and a disposition.
- [ ] Every disposition is a real card id or the word `accepted` with a reason.
- [ ] The "review triggers" list names the four events, and `OPENCODE_TEAM_FLOW.md` §1 R7's remit
      matches it on the words (auth, RBAC, secrets, uploads, outbound URLs, webhooks, connectors,
      PLC/OT) — add `MCP`, `workers`, `installers` and `monitoring` as R7 triggers in the same edit.
- [ ] The document fits in one screen-height table per boundary: no paragraph longer than four lines.
- [ ] The four mechanical guards pass.

## Notes for the implementer
Plain words, no threat-model theatre: a row that says "SQL injection — impact: tenant data read —
control: SQLAlchemy Core with bound parameters everywhere, `routers/images.py:241-250` — residual: raw
`text()` nowhere in app code (grep) — card: T-1305" is worth ten paragraphs of methodology. Do not
invent mitigations: if the control does not exist, the residual-risk column says so and the card column
names the card that will build it. R7 must sign off on every "accepted".
