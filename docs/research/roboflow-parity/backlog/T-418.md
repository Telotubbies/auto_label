## User story
As an owner, I want to pre-authorise a capped overage, so that a busy week does not stop training mid-run.

## UX flow (LabelDesk words)
1. **Plan & billing → `On-demand spending`** — a toggle with `Off` / `On`; turning it on shows
   `Enabled. Spending stops at your monthly cap.` and a warning that in-flight training and deployments stop when
   the cap is reached.
2. **Monthly spending cap** — a checkbox plus an amount field; the cap saves on blur, on `Enter` and on
   `Save cap` — three ways to commit one edit. `Remove cap` asks `Spend will be unlimited. Continue?` and states
   `Unlimited` on the row afterwards.
3. **Turning off** — confirm `Turn off on-demand spending? Training and deployments stop when the included and
   prepaid credits run out.` A cap of `0` also turns it off, after the same confirm.
4. **`[empty]`** Free plan: the card is a single line `On-demand spending is not available on Free.` with no toggle.
5. **`[error]`** an amount that is not positive → inline `Enter an amount greater than zero, or remove the cap.`;
   a server refusal snaps the field back and shows the sentence.
6. **`[loading]`** the field shows a tick while saving; the toggle is disabled mid-save.

## Backend changes
- Models/schema: `BillingAccount.flex_enabled` and `spend_cap_usd` exist from T-412; no new column. The cap default
  when flex is first enabled is `None` → the API answers `409 cap_required` until a cap is set, so no default amount
  is invented.
- Routers: `GET/PATCH /api/ws/{ws}/billing/flex` `{enabled?, cap_usd?}` → `{enabled, cap_usd}`; `409 cap_required`
  when enabling without a cap; `400` for a negative amount.
- Services/jobs: `services/billing.py` — `flex_state(db, ws)`, `set_flex(db, ws, enabled, cap_usd, actor)`;
  `deps.charge` and `metering.check` consult `flex_headroom(db, ws)` (returns `None` when off, else
  `cap_usd - month_spend`), so the 402 becomes "cap reached" rather than "allowance reached".
- Permissions + workspace isolation: `workspace.billing`; the headroom is read from `c.ws`.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Frontend changes
- Route: `/:ws/settings/billing` (T-414's tab, new card).
- Components: `features/settings/billing/FlexCard.tsx` (new) — toggle, cap field with three commit paths, confirm

## Acceptance criteria
- [ ] Flex can be enabled only with an explicit cap, and the cap saves by blur, Enter or button.
- [ ] At the cap, credit-requiring actions stop with a message that names the cap.
- [ ] Disabling flex states that running jobs will stop, and a zero cap means off.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no card, no headroom, today's plan-only stop.

## Notes for the implementer
No default cap is configured, so the first enable must ask for one — that is the honest version of "a default applies".
Owner decisions (provider, ladder/prices, self-host licence) remain open; this card stores a cap, it does not price it.
