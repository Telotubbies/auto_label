## User story
As an enterprise admin, I want a sign-in to add or remove me from the workspace according to my directory groups, so
that a leaver loses access on their next attempt.

## UX flow (LabelDesk words)
1. On an SSO sign-in (T-426) with the flag on, the sync runs before the session is issued:
   - neither required groups nor auto-join → manual invite only, unchanged;
   - auto-join only → the user is added to the workspace at the default role (T-382);
   - required groups only → a non-matching existing member is removed and audited; a matching user still needs an
     invite;
   - both → matching users are added, non-matching members are removed.
2. Custom roles mapped to groups are reconciled on every sign-in: a matching group's role is assigned, a role whose
   group no longer matches is cleared, and a role assigned by hand (no mapping) is left alone. Losing every mapped role
   falls back to the default role.
3. `[empty]` a user with no groups and no mapping is untouched (no removal) unless required groups exist.
4. `[error]` a removal writes `member.sync_remove` with the reason `not_in_required_group`; the user sees
   `You no longer have access to this workspace.` on the sign-in screen, not a 500.

## Backend changes
- Models/schema: `Member.synced_role_id: str | None` — the custom role the sync last assigned, so a manual assignment
  can be told apart from a synced one. `ADD COLUMN` addition to `MEMBERS` in `app/schema/identity.py`.
- Routers: the sync is invoked from the SSO callback (T-426); no route of its own.
- Services/jobs: `services/dir_sync.py` — `sync(db, ws, user, claims) -> dict` returning
  `{added, removed, role_assigned, role_cleared, reason}`; `reconcile_roles(db, ws, member, groups)` honouring
  `synced_role_id`; every change audited (`member.sync_add`, `member.sync_remove`, `member.sync_role`).
- Permissions + workspace isolation: the sync only ever writes rows for the workspace the SSO config belongs to.
- Secrets/safefetch: none.
- OpenAPI: no.

## Frontend changes
- API client: none. One line in the SSO error branch (T-426) for the `not_in_required_group` message.
- Feature flag: `task_dir_sync`; off ⇒ the callback issues a session exactly as T-426 does.

## Notes for the implementer
`synced_role_id` is the whole trick: without it a manual grant looks identical to a synced one and the next sign-in
would clear it. Removal is audited with the reason, never silently.
