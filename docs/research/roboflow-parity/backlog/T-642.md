## User story
As an ops lead who cannot review 20,000 images but will not ship unreviewed labels either, I want to state where a box is accepted, where it is escalated for review and when the batch splits, so that "how much will I have to review" is answered before the job spends anything.

## UX flow (LabelDesk words)
1. **Auto label → Review policy** (`/:ws/:project/annotate`, drawn by T-643) — two floors: accept at or above, review down to. This card stores and enforces them.
2. **Preview** — the same sample returns accept / review / discard per class and for the batch, computed with the same function the run uses. [empty: a sample with no box in any band reports zeroes, never a blank table] [loading: the panel keeps the previous counts dimmed rather than flipping to zero] [error: a review floor at or above the accept floor is a 422 naming both fields]
3. **Run** — accept-band boxes write to a `done` image, review-band boxes write to `review` and add the tag `bucket=review`, discard-band boxes are counted and dropped. A VLM box carries a fixed 0.50 score, so it always lands in the review band whatever the floors say.
4. **Job report** — `{"accept": n, "review": n, "discard": n}` beside `annotations`, so the board can show two queues without recomputing.

## Backend changes
- Models/schema: none — the policy lives in `Project.settings["autolabel"] = {"accept": 0.6, "review": 0.3}` (JSON already on the row), written through the existing project PATCH; no column, no backfill.
- Routers: `AutoLabelIn` gains `bands: {"accept": float, "review": float} | None` (each 0–1); 422 when `review >= accept`; the preview response gains `bands: {"accept": int, "review": int, "discard": int, "per_class": {name: {…}}}`; 400 "confidence bands are not enabled for this workspace" when the flag is off and the payload carries bands.
- Services/jobs: `services/autolabel_policy.py` (new) — `bands(params) -> tuple[float, float]` (defaults 0.60 / 0.30), `bucket(anns) -> dict[str, list[dict]]` (a box without a numeric confidence counts as review, never accept), `outcome(anns) -> "done" | "review" | "mixed"`, `tag_review(anns)`; `handlers/training.py` routes each image's boxes, sets the status once per image, and returns the three totals; `routers/training.py`'s preview calls the same `bucket`.
- Permissions + workspace isolation: `reviewer` to preview or run (already `c.need("reviewer")`); every query is scoped by `project_ctx`, so another workspace's batch id is 404 through the existing `_autolabel_query`.
- Secrets/safefetch: none — no new endpoint and no new payload.
- OpenAPI: yes — regenerate (`python tools/export_openapi.py`, `npm run gen:api-types`).

## Acceptance criteria
- [ ] Two floors decide three bands, the preview reports the same three counts the run produces, and the review band's boxes are tagged so a queue can be filtered.
- [ ] A VLM run reports every box in the review band instead of implying a calibrated score.
- [ ] Empty, loading and error states above all render: zeroes for a sample with no hits, a 422 for an inverted policy, the existing 503 for an unreachable model.
- [ ] Workspace A cannot run against workspace B's batch or images (404 for a foreign batch id).
- [ ] Flag off ⇒ bands are refused and status, tags and report are exactly today's.
- [ ] No image is discarded silently: every dropped box is counted in the job report.

## Notes for the implementer
Defaults are 0.60 accept and 0.30 review; the tag is the literal `bucket=review` because the existing tag filter matches a whole string. An image with any review-band box stays in `review` — never promote half an image — and a box with no numeric confidence is review, never accept. The score of a VLM box is 0.50 by contract (`adapters/refine.py`), so do not invent a per-box score for it.
