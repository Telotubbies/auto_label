## User story
As an ML engineer, I want the train form to offer only the families and sizes this worker can actually build, each with the resolution it will start at, so that an impossible choice is never clickable and I know what a size means before I spend credits.

## UX flow (LabelDesk words)
1. **Train → Recipe → Advanced** — the family grid lists only families valid for this project's task; a family card names its licence and, when unavailable, the sentence that says why. [empty: a task with no installed adapter shows "No model family is installed on this worker — see Settings → Compute" instead of an empty grid] [loading: six skeleton cards at the grid's final size] [error: `GET /train/options` failing shows "The model catalogue could not be read" with a Retry, and Start stays disabled]
2. **Size axis inside a family card** — picking *RF-DETR* shows Nano / Small / Medium / Large, each with its own starting resolution ("512 px"); picking *YOLO* shows the n–x axis at "640 px"; classification shows "224 px". The resolution line states "Starting resolution — the version's resize step can change it."
3. **A size the worker cannot build** — the card is dimmed with a lock and the reason ("needs the `rfdetr` package on this worker"); the select never lands on it.
4. **A task mismatch** — a detection-only family under a segmentation project renders dimmed with "detection projects only"; no request reaches the API.

## Backend changes
- Models/schema: none.
- Routers: keep `GET {P}/train/options` (`apps/backend/app/routers/training.py:194`) but build its body from the new service. Response per family: `{family, label, adapter, license, available, reason, request_access: bool, sizes: [{id, label, weights, default_imgsz, vram_mb}], default_size}` plus the existing `{supported, task}`. `POST {P}/train` gains one validation hop: the `(task, family, variant)` triple must resolve in the catalogue, else **400** with a message that names the valid ids: `"variant 'yolo26-h' is not available for object-detection; choose one of: yolo26n, yolo26s, …"`.
- Services/jobs: new `apps/backend/app/services/train_catalog.py` — move `FAMILIES`, `_SIZES`, `_yolo`, `_hf`, `_BASE_VARIANTS`, `_family_of`, `_base_variant`, `_SUFFIX` out of the router (behaviour identical) and add `DEFAULT_IMGSZ = {"nano": 384, "small": 512, "medium": 576, "large": 704}` for `rf-detr`, `640` for the ultralytics families, `224` for classification suffixes, `1008` for `sam3`; expose `families(db, task, project_type) -> list[dict]`, `resolve_variant(task, variant) -> (family_row, size_row)`, `valid_variants(task) -> list[str]`. Adapter probes stay behind `adapters/catalog._probe`'s 15 s cache.
- Permissions + workspace isolation: `GET /train/options` stays on `project_ctx` with no extra grant (it is licence metadata, same as today); a foreign project slug is 404 from `project_ctx`. `POST /train` keeps `c.need("admin")`.
- Secrets/safefetch: none.
- OpenAPI: yes — regenerate both files.

## Acceptance criteria
- [ ] `GET /train/options` returns a size axis with a starting resolution per size, and a `request_access` flag per family.
- [ ] `POST /train` rejects an unknown `(task, family, variant)` with a 400 naming the valid variants; no model row and no job are created.
- [ ] Detecting-only families are unavailable (with a reason) outside detection projects.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off (`task_250`) ⇒ today's flat family grid and today's 400 text still render; the response keeps every key it has today.

## Notes for the implementer
Extend `adapters/catalog.py`; do not invent a second zoo — `_zoo()` stays the source of refs, `train_catalog` only adds size/resolution/licence rows. Per-size VRAM: RF-DETR reuses `adapters/rfdetr_ad.VRAM_MB`, ultralytics `1400`; anything else reports `0` and the UI prints no VRAM line.
