## User story
As a person at the company domain, I want to ask to join a workspace and have an admin accept me, so that a colleague can be added without an admin knowing their address in advance.

## UX flow (LabelDesk words)
1. **Workspace settings → Workspace** — a new switch `Domain join` with a domain field (`acme.co.th`), hint `People with this email domain can ask to join. An admin still approves each one.` Turning it on without a domain → `Add the email domain first.`
2. **Visitor with a matching domain** — on the workspace picker (`/`) a listed entry `Acme — ask to join` (only for workspaces whose domain matches the caller's verified email). Click → `Request sent. An admin at Acme will approve you.` [error: already a member → `You are already in Acme.`; domain off → the entry does not exist; rate-limited → `You have already asked — an admin has not answered yet.`]
3. **Admin → Settings → Members** — a `Join requests` block above join links: requester name/email, `asked 2 h ago`, `Accept as` role select (default `labeler`), `Accept`, `Decline`. [empty: `No pending requests.`] [error: seat limit → `3 of 3 seats used.` and the accept is disabled]
4. **Joinable list** — `GET /api/joinable` returns only workspaces whose `domain_join_enabled` is on, the caller's email domain matches exactly, and the caller is not already a member. No other workspace is named.

## Backend changes
- Models/schema: `workspaces.join_domain VARCHAR(255) DEFAULT ''` and `workspaces.domain_join_enabled BOOLEAN DEFAULT FALSE` — `ADD COLUMN` appended to `WORKSPACES` in `app/schema/identity.py`; `JoinRequest(id, workspace_id, user_id, role_hint, status pending|accepted|declined, created, decided_by, decided)` new model in `models/identity.py`, `UniqueConstraint(workspace_id, user_id)`.
- Routers: `GET /api/joinable` (auth) → `[{slug, name}]`; `POST /api/ws/{ws}/join-requests` (auth) → 201, 409 already member, 409 pending exists, 403 domain mismatch/disabled; `GET /api/ws/{ws}/join-requests` (admin) → pending rows; `POST /api/ws/{ws}/join-requests/{id}/accept {role}` (admin) → creates the Member (seat check 402), sets status; `POST …/decline`; `PATCH /api/ws/{ws}` accepts `join_domain` (validated as a bare domain) and `domain_join_enabled`.
- Services/jobs: `services/domains.py` (new) — `normalise_domain`, `matches(email, domain)` (exact suffix after `@`, no subdomain wildcard), `request`, `decide`, `joinable(db, user)`; one mail to the admins on a new request reusing `mailer.send`.
- Permissions + workspace isolation: request needs `workspace.read` of nothing — it only needs an authenticated user whose email domain matches; listing/deciding needs `workspace.members`; the request row is created only in the workspace named by the path, and `GET /joinable` never reveals a non-matching workspace.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Acceptance criteria
- [ ] A same-domain user can ask to join; an admin accepts with a role and the person appears in the roster.
- [ ] `GET /joinable` lists only exact-domain matches the caller is not already in.
- [ ] Empty, loading and error states above all render (no requests, duplicate, seat cap).
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ surface absent and the old behaviour unchanged (invite-only).
- [ ] Matching is exact after `@`; `sub.acme.co.th` does not match `acme.co.th`.

## Notes for the implementer
No wildcard domains. A declined request stays as a row so the same person cannot re-ask in a loop; an admin can clear it manually later.
