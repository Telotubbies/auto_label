## User story
As a reviewer, I want to walk the events my team marked wrong one at a time and route each into training, so that the queue is worked once instead of twice by two people.

## UX flow (LabelDesk words)
1. **Start a review session** — `POST …/review-sessions` with `{model_id?, verdicts: ["wrong","unclear"], size?}` returns the session with its first item and a lock. A second person starting one on the same stream gets `409` and the tab shows "Mai is reviewing these 34 events since 14:20" with "Check again". `[loading: "Starting…" until the first item is resolved]` `[empty: nothing to review → "Nothing marked wrong or unclear yet." with a link to the event list]`
2. **Each item** — the event's snapshot, its verdict and the model's boxes, plus four actions: `Add to dataset`, `Send to annotation`, `Reject`, `Snooze`. Each action advances to the next item and is written immediately.
3. **Save and exit** — the session records how many were routed where and releases the lock; returning later resumes at the first unreviewed item.
4. **The lock** — it expires after 10 minutes without a decision; the holder's browser renews it on each decision. `[error: a decision after expiry → 409 "This session expired. Restart to continue." and the tab offers "Start again"]`
5. **Snooze** — a snoozed event leaves this session and reappears after 24 hours, so a genuinely ambiguous frame does not block the queue.

## Backend changes
- Models/schema: new module `apps/backend/app/models/review.py` — `ReviewSession` (`id`, `workspace_id`, `project_id`, `stream_id`, `created_by`, `holder_id`, `holder_since`, `status` ∈ `open|done|expired`, `filters` JSON, `counts` JSON, `created`, `updated`) and `ReviewDecision` (`id`, `session_id`, `event_id`, `action` ∈ `dataset|annotate|reject|snooze`, `user_id`, `created`), both registered in `models/__init__.py`.
- Routers: `apps/backend/app/routers/review.py` (new) — `POST /api/ws/{ws}/projects/{project}/review-sessions`, `GET /review-sessions/{id}` (returns `{status, holder, items, progress}`), `POST /review-sessions/{id}/decisions` (`{event_id, action}`), `POST /review-sessions/{id}/release`, `GET /review-sessions/{id}/blocked` (who holds it).
- Services/jobs: `apps/backend/app/services/review_session.py` (new) — `LOCK_TTL_S = 600`, `open(db, project, user, filters) -> ReviewSession | Blocked`, `take(db, session, user)`, `next_item(db, session)`, `decide(db, c, session, event_id, action)`, `release(db, session)`, `expire(db)` called by the existing job sweep so an abandoned lock dies without a request.
- Permissions + workspace isolation: `project.review` to open and decide; the session owns one stream of one project, so a foreign id is 404 and a foreign event inside the session is refused.
- Secrets/safefetch: none — `dataset` reuses `routers/streams.py:556`'s ingest path.
- OpenAPI: yes — five routes.

## Acceptance criteria
- [ ] One reviewer holds a session; a second is told who holds it and when it started, and can check again.
- [ ] Four actions each advance the session and are persisted immediately; resuming starts at the first unreviewed item.
- [ ] The lock expires after 10 minutes of no decision, and a late decision is refused with a restart path.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no session routes and no behaviour change.

## Notes for the implementer
The lock is a row, not a process lock: `holder_id` + `holder_since` with a 10-minute TTL survives a restart, which an in-memory set does not. `Add to dataset` reuses the event-to-dataset path so storage metering, dedupe and audit stay in one place.
