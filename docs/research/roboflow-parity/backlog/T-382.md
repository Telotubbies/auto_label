## User story
As an admin, I want to read what each built-in role may do and to choose what a newcomer gets, so that I can
answer "what does a labeler have" without reverse-engineering the app.

## UX flow (LabelDesk words)
1. **Settings → Roles** (`/:ws/settings/roles`) — above the custom-role list, a `Default role for new joiners`
   card: a dropdown (`Member`, `Billing`, `Admin`), the sentence `Applies to people who arrive by a join link,
   a domain request or single sign-on.` and no Save button — the change applies on selection. [loading: the
   card body is a two-line skeleton] [error: `Could not load the role settings.` + `Try again`]
2. **Built-in roles** — three stacked tables: **Workspace roles** (Owner, Admin, Billing, Member) and
   **Project roles** (Manager, Reviewer, Labeler, Viewer), each row a permission, each cell `Yes`/`—`, read
   only, with the permission key in a monospace sub-line. [empty: `No permissions are defined for this level.`
   — only possible when the API matrix is empty]
3. **A lock** — when the plan or policy forbids changing the default role, the dropdown is dimmed with a lock
   icon and the tooltip `Locked by your plan.`; the table still reads.
4. `[error]` on save: the previous value stays selected and a toast names the server sentence.

## Backend changes
- Models/schema: `Workspace.default_role: Mapped[str] = mapped_column(String(16), default="member")`;
  `ADD COLUMN` block `WORKSPACES` in `app/schema/identity.py` gains `"default_role": "VARCHAR(16) DEFAULT 'member'"`.
  Backfill is the column default; an existing row with NULL reads as `member` in the service.
- Routers: `GET /api/ws/{ws}/permissions` (`routers/rbac.py`) already returns `matrix`, `workspace_roles`,
  `roles`; add `"default_role": c.ws.default_role or "member"`.
  `PATCH /api/ws/{ws}/permissions/default-role` `{role}` → 200 `{default_role}`; `400` for a role outside
  `WORKSPACE_ROLES`; `403` without `workspace.update`.
- Services/jobs: `get_default_role(db, ws) -> str` in `app/rbac.py` (one line, reused by the join paths);
  `routers/workspaces.py` `invite()` uses it when `role` is omitted instead of the literal `"annotator"`.
- Permissions + workspace isolation: read `workspace.read`; write `workspace.update`; the row is `c.ws`.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Frontend changes

- Feature flag: `task_role_matrix`; off ⇒ the Roles page is exactly today's custom-role list.

## Acceptance criteria
- [ ] The built-in workspace and project roles are readable as tables with one row per real permission key.
- [ ] The default role can be changed in one click and the invite form uses it when no role is chosen.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no matrix, no default-role card, invite default unchanged.
- [ ] No permission key is invented in the UI: the table is generated from `/permissions.matrix`.
