## User story
As someone with a freshly labelled first batch, I want to train without learning what a version is, so that my first model arrives from the data I already have.

## UX flow (LabelDesk words)
1. **Train → 1 Dataset** — two options: *Current dataset* ("uses approved images as they are now — creates a version for you") and *Saved version* (the existing select). Current dataset is preselected when the project has no version yet. [empty: no approved images ⇒ the option is dimmed with "Approve images first — training needs at least one." and Start disabled] [loading: the option row shows a spinner while the preview count loads] [error: "The dataset could not be read" + Retry; the saved-version list still works]
2. **The implicit version is named, not anonymous** — after selecting, the block states "Will create v4 · 640 images (512 train / 64 valid / 64 test)" using the project's stored split settings.
3. **Start** — the run's stepper gains one extra stage before *Dataset*: "Snapshot", so the user sees the version being written rather than a silent pause. The created version appears in *Versions* with the same name and recipe, marked "Created by a training run".
4. **Reuse** — a link under the option: "Copy a saved version's preprocessing" (area 4's reuse), which turns *Current dataset* into a version-based recipe with those settings.

## Backend changes
- Models/schema: none new — a `Version` row is created with today's columns. `Version.settings` carries `{"source": "train", "created_by_run": true}` so the Versions list can label it.
- Routers: `POST {P}/train` body gains `mode: "version" | "current" = "version"` and `version_id: str | None`. With `mode="current"`: version_id may be omitted; the route computes the next number, writes `Version(project_id, number=n, name=body.name or f"Auto v{n}", settings=project defaults + {"source": "train"})`, enqueues the **same** `train` job with that `version_id`, and returns the model (whose `version` field now resolves). **400** `"a current-dataset run needs split settings in the project"` when the project has no split ratios.
- Services/jobs: `handlers/training.py::run_train` — before the `materialise` stage, if `v.status != "ready"` call `versioning.generate(db, v, progress_cb, should_stop)` inside the existing `materialise` mark and set `v.status="ready"`, `v.stats`. On failure the version is marked `failed` and the run fails with the version's reason (the model row is `failed`, never `ready`).
- Permissions + workspace isolation: `c.need("admin")` as today; the implicit version is created in `c.project.id`, so a foreign `version_id` still hits the existing "pick a generated version" 400.
- Secrets/safefetch: none.
- OpenAPI: yes — `TrainIn.mode` (regenerate both files).

## Acceptance criteria
- [ ] A first run needs no version: the API creates one numbered version, one train job, and materialises the snapshot before training.
- [ ] The implicit version is visible in Versions with its name, recipe and counts.
- [ ] A failed snapshot fails both rows and never registers a model.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ `mode` ignored, version required, message unchanged.
