## User story
As an ML engineer reading search results, I want to keep a runner-up as a real model, so that "the second best is smaller and almost as good" becomes deployable without re-running anything.

## UX flow (LabelDesk words)
1. **Search results → a candidate dot/row** — *Keep this candidate* on the row. The row states what will happen: "Adds it to Models with its own evaluation."
2. **After keeping** — the row's action becomes *In Models* with a link; the model list gains `<run name> · <variant>`; the candidate's status stays `done` and carries a "kept" badge.
3. **Evaluating immediately** — keeping a candidate whose evaluation has never run enqueues the evaluation job (T-283's endpoint) so its number is comparable; the row shows "Evaluating…" with a progress spinner. [error: "Evaluation failed — the model is still usable" as today's `eval_error` card]
4. **Keeping twice** — the second click is a no-op returning the same model (`200`, not a duplicate).
5. **Caps and failures** — a `failed` or `stopped` candidate can be kept too (weights exist); a failed candidate with no weights shows the action disabled with "no weights were saved".

- **States** — [empty: a candidate with no saved weights shows the action disabled with its reason]. [loading: the promoted row reads "Evaluating…" while the enqueued evaluation runs] [error: an evaluation failure keeps the model usable and shows the existing `eval_error` card].

## Backend changes
- Models/schema: `search_candidates.starred BOOLEAN DEFAULT FALSE`, `search_candidates.model_id VARCHAR(32) DEFAULT ''` (the promoted model). Append to the `search_candidates` definition (T-270 creates it; this card extends it in the same module).
- Routers: `POST {P}/models/{mid}/candidates/{cid}/star` → `200 model_out` (idempotent: a second call returns the same model); **404** for a candidate of another model/project/workspace; **409** when the candidate has no `weights` file ("no weights were saved for this candidate").
- Services/jobs: promotion creates `TrainedModel(id=new_id, …)` copying family, variant, task, classes, `metrics` (candidate headline + `history`), `weights`, `max_credits`, `continued_from=None`, and a `ref` through `model_refs.next_ref`; the candidate gets `starred=True, model_id=…`. Evaluation is **not** run inline — the route enqueues the same job kind T-283 introduces (`eval_model`), so a slow evaluation never blocks the response.
- Permissions + workspace isolation: `c.perm("project.models")` (a manager/reviewer action, no spend); foreign ids → 404.
- Secrets/safefetch: none.
- OpenAPI: yes — regenerate both files.

## Acceptance criteria
- [ ] Keeping a candidate produces exactly one deployable model with the candidate's weights and metrics.
- [ ] The action is idempotent and never duplicates a model or an evaluation job.
- [ ] A candidate with no saved weights refuses to promote with a 409 that says why.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no route, no keep action, search results read-only.

## Notes for the implementer
The parent search model stays the winner; a promoted candidate is an independent model row (its own reference, its own evaluation). Do not copy the parent's `metrics.eval` — that report belongs to different weights.
