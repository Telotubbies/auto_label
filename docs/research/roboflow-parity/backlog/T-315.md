## User story
As an integrator, I want to read a workflow's input and output contract from the workflow itself, so that my client sends the right keys instead of guessing from an API reference.

## UX flow (LabelDesk words)
1. **Workflows → a saved workflow** (`/:ws/:project/workflows`) — the response of the existing list/get now carries `inputs` and `outputs` alongside `blocks`. The editor shows them read-only in the run panel header: "Needs: image · Optional: confidence". [empty: a workflow with one model block declares `image` plus the model's own parameters and `outputs: [{name: "detections"}]`] [loading: unchanged, the list already has a spinner] [error: a save that would produce an undeclared port is refused with a block-numbered 400, the same shape as today's validation errors]
2. **Save** — `PUT /workflows/{id}` re-derives the contract and rejects a block whose input port is not produced by an earlier block, so a saved workflow is callable by construction.
3. **`GET /workflows/{id}`** — a client can read `inputs[].key`, `inputs[].type` ∈ `image | number | string | boolean`, `inputs[].required` and `outputs[].name` to build its payload.

- [ ] A save that consumes a port nothing produces is refused with a 400 naming the block number.
- [ ] A workflow with two producers for one port is refused rather than silently picking one.
- [ ] Empty, loading and error states above all render.

- [ ] Flag off ⇒ unchanged: `task_31` still hides every workflow route.

## Notes for the implementer
Derive, never store: a stored contract would need a backfill and could disagree with `blocks`. The format parameter is a scalar input named `confidence` of type `number`, required `false` — it is what the invoke endpoint (T-316) accepts as an override.
