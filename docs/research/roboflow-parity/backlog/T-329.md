## User story
As a builder, I want to see exactly which check is holding my publish back and who has to approve it, so that "cannot publish" is a task and not a wall.

## UX flow (LabelDesk words)
1. **Workflow editor → header** — a status chip: `Draft v7` (draft ahead), `Live v7`, `Not published`, `Publishing…`. Clicking it opens the publish panel; the Publish button lives beside it and is disabled unless the gate says publishable.
2. **Publish panel** — the check list in the server's order, each row with a tick or a cross, a label and its `detail`; a footer with the draft and live version numbers and, when approval is required, "Approve v7" / "Reject" for a project manager plus "Waiting for a manager" for everyone else. [empty: a brand-new workflow with nothing saved → the panel shows one row, "Save once before publishing." and no buttons] [loading: four skeleton rows while the gate is read] [error: the gate cannot be read → "Publish state could not be read." with "Check again"; the Save button keeps working]
3. **Confirm** — Publish opens a small confirmation naming the version and the destinations it changes: "Serve v7 to the endpoint and to every batch job?" Confirm / Cancel.
4. **Auto-publish switch** — under the check list: "Publish the next saved draft automatically once its checks pass." When on, saving shows a toast "Saved v8 · publishing…" that resolves to "Live v8" or to the first blocking reason. The switch never bypasses the approval row.
5. **After a publish** — the chip turns `Live v7`, the panel collapses, and one line stays: "v7 is live · published 2 h ago by you."

## Acceptance criteria
- [ ] The chip reflects draft-ahead, live, never-published and in-flight states from the server, not from local guesswork.
- [ ] Every check renders with its detail; Publish is disabled until checks and approval both pass, and the headline names the first blocker.
- [ ] Publishing asks one confirmation naming the version, and the panel states what is live and who published it.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] No flag: with `task_328` off the state call is 404 and no chip or panel renders.

## Notes for the implementer
Approval is a role decision, so the panel only *hides* the Approve button — the server's 403 is the gate. Never derive `publishable` in the client from the check list alone; read it from the endpoint.
