## User story
As a member working in the app, I want a warning before the allowance is gone, so that the first signal is not a
failed action mid-task.

## UX flow (LabelDesk words)
1. **Top bar banner** — three stages, one at a time, highest first:
   `80% of your credits are used (24 of 30).` + `See options`;
   `You are near your spending cap (82% of …).` + `Raise cap` / `Buy credits`;
   `Credit-requiring actions are blocked until you raise the cap, buy credits or the cycle resets.` + `See options`.
2. **Consuming stage** — while on-demand spending is live: `You are spending beyond your included credits. Prepaid
   credits cost less per credit.` with `Buy credits`.
3. **Dismissal** — a banner can be dismissed for the session; the 80% and consuming stages return on the next cycle,
   the at-cap stage cannot be dismissed.
4. **`[empty]`** under 80% and flex off → no banner at all, so the top bar is unchanged.
5. **`[error]` out of credits on an action** — the existing 402 toast gains the same link target (`See options`) so
   the banner and the failure point agree.
6. **`[loading]`** the banner never blocks the shell: it appears only after the usage read resolves.

## Backend changes
- Models/schema: none.
- Routers: `GET /api/ws/{ws}/usage` gains `spend_notice: {stage: "none"|"eighty"|"near_cap"|"at_cap"|"consuming",
  percent: float | null, actions: ["raise_cap"|"buy_credits"|"upgrade"]}` computed in one place.
- Services/jobs: `services/billing.py` — `spend_notice(db, ws) -> dict` (pure computation over `credits_left`,
  `flex_headroom` and `prepaid_credits`); no notification, no mail — the notice is in-app only.
- Permissions + workspace isolation: `workspace.read` (every member sees the 80%/at-cap stage); the action links
  resolve to surfaces the caller may open, and a `member` sees `Ask an admin` instead of `Raise cap`.
- Secrets/safefetch: none.
- OpenAPI: yes.

## Frontend changes
- Route: none — the banner is shell chrome.
- Components: `features/shell/SpendBanner.tsx` (new) mounted in `components/shell/TopBar.tsx`;

- API client: `api.workspace`/usage reader already returns the payload; `usageApi` type gains `spend_notice`.
- Feature flag: `task_spend_notices`; off ⇒ no banner and the payload field is absent.

## Acceptance criteria
- [ ] The 80% stage appears inside the app with a link to the options; no mail is sent.
- [ ] The cap stage names the two actions and the at-cap stage says what is blocked.
- [ ] Only one banner shows at a time, most severe first; the at-cap stage cannot be dismissed.
- [ ] Empty, loading and error states above all render (no banner under 80%).
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no banner and no payload field.

## Notes for the implementer
One computation, three stages — the banner must not recompute thresholds. A `member` never sees `Raise cap`, because
they cannot raise it.
