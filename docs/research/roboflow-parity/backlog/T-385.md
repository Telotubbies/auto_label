## User story
As a folder-scoped contractor, I want a project outside my folder to behave as if it does not exist, so that I
never learn what else the workspace is doing.

## UX flow (LabelDesk words)
1. A folder-scoped member opens `/:ws` — the project list contains only projects whose folder has a grant for
   that member (through a role, an auth group or a direct grant); the "your next step" queue is filtered the
   same way because it is built from the same project list.
2. Typing another project's URL (`/:ws/p/<other>`) answers the project-level 404 the shell already renders:
   `This project is not here.` — never a 403 and never a lock icon (a lock would confirm existence).
3. `[empty]` a member whose only folders are un-granted sees `No projects yet. Ask an admin for access to your
   folder.` — the sentence distinguishes "nothing shared with me" from "no projects exist".
4. `[error]` an API read of the filtered project answers 404 with the same body shape as a deleted project.

## Backend changes
- Models/schema: none (T-384).
- Routers: no new routes. Two shared appends:
  `routers/projects.py` list query adds `.where(folder_visible_clause(c))`; `routers/workspaces.py` `home()`
  applies the same clause to its project select.
- Services/jobs: `app/services/folder_access.py` gains
  `visible_folder_ids(db, c) -> set[str] | None` (`None` = unrestricted),
  `can_see_folder(db, c, folder_id) -> bool`,
  `project_visible(db, c, project) -> bool`,
  `folder_visible_clause(c)` (a SQLAlchemy expression or `true()`).
  Rules: owner/admin and any member holding `workspace.members` or `workspace.update` are unrestricted; a member
  is restricted only when at least one grant row exists in the workspace; then a project is visible when its
  `folder_id` is in the member's granted set, and a project with `folder_id IS NULL` stays visible only to
  unrestricted members.
- Permissions + workspace isolation: `deps.project_ctx` raises the existing 404 when `project_visible` is false;
  `deps.apply_project_role` is untouched so role resolution stays one lookup.
- Secrets/safefetch: none.
- OpenAPI: yes (the project list response gains no field but its semantics change — note it in the description).

## Acceptance criteria
- [ ] A folder-scoped member sees only granted projects in the list, the queue and the project route.
- [ ] A project outside the scope answers 404 with the same body as a missing project, never 403.
- [ ] An unrestricted workspace behaves exactly as today, including projects with no folder.
- [ ] Empty, loading and error states above all render.
- [ ] Workspace A cannot see or change workspace B's data (404, not 403, for cross-workspace ids).
- [ ] Flag off ⇒ no filtering anywhere.

## Notes for the implementer
Restriction activates only when the workspace has at least one grant row — otherwise a half-configured folder
would hide every project from every member. The unrestricted set is `owner`, `admin`, holders of
`workspace.members` or `workspace.update`; do not invent a new permission key for it.
